Hoare triples and validity

  • Hoare triple {{ P }} code {{ Q }}
  • Valid: Running code from state satisfying P leads to a state satisfying Q.
    • If run doesn't terminate, then validity makes no claims about it.
    • Code from last lecture always terminated. What about loops?

The rules turn the crank

  • Mechanical: the claim before a line and the line give the claim after
    • No decision to make
  • Forward: the strongest postcondition, x0 for the old value
    • {{ P }} x = e; {{ P[x ↦ x0] and x = e[x ↦ x0] }}
  • Backward: the weakest precondition, a substitution
    • {{ Q[x ↦ e] }} x = e; {{ Q }}
  • Sequence: the claim after one line is the claim before the next

Rule: consequence

{{ A }}
code
{{ B }}
{{ Q }}
  • We can "massage" the claims given by a rule via implication.
  • Goal: show {{ P }} code {{ Q }} is valid. Break it down:
    • {{ A }} code {{ B }} is valid,
    • P implies A, and
    • B implies Q

Rule: conditional

{{ P }}
if (b) {
    {{ P and b }}
    first
    {{ A }}
} else {
    {{ P and not b }}
    second
    {{ B }}
}
{{ A or B }}
{{ Q }}
  • The condition flows into each branch.
  • Mechanically reason through each branch.
  • Merge the resulting postconditions with or.
  • Check the result implies Q.

Definition: loop invariant

Definition: loop invariant

A loop invariant of while (b) { body } is an assertion that holds each time the loop checks condition b.
Before the first iteration, between iterations, and after the last.

Inv:

13long sum(int[] a) {
14    long s = 0;
15    int i = 0;
    {{ Inv: 0 <= i and i <= a.length and
            s = a[0] + ... + a[i - 1] }}
16    while (i < a.length) {
17        s = s + a[i];
18        i = i + 1;
19    }
20    return s;
21}
  • Inv: puts I at the condition check, not before the loop

Rule: while loop

{{ P }}
{{ Inv: I }}
while (b) {
    {{ I and b }}
    body
    {{ I }}
}
{{ I and not b }}
{{ Q }}
b is the loop's condition. I is a claim the programmer supplies. The triple {{ P }} while ... {{ Q }} is valid if three checks pass: (1) P implies I. (2) The triple {{ I and b }} body {{ I }} is valid. (3) I and not b implies Q.

The rule as a picture

Why these checks

  • In the figure, every way into the diamond crosses the arrow labeled I
  • First iteration: P is true, so by (1), I is true
  • Between iterations: each comes at the end of a pass
    • If I was true at the one before, the pass began with I and b
    • So by (2), the pass ended with I
  • After last iteration: b is false, so I and not b after the loop
    • By (3), Q is true there

Each check is a step we know

  • (1) and (3): implications, no code between
    • Each is a use of the rule of consequence
  • (2): a triple about the body
    • No loop in the body, as in sum: Wednesday's rules check it
    • Forward or backward
  • What is new is I
    • For now, I is given

Check (1)

0 <= i                      since i = 0
i <= a.length               since i = 0 and 0 <= a.length
a[0] + ... + a[i - 1] = 0   since i = 0: the sum of no terms
                      = s   since s = 0
  • The claim before the loop, s = 0 and i = 0, has to imply I
  • Each of I's three facts follows, one step to a line
  • The second line: no array has a negative length
  • So check (1) passes

Check (2), line 17

  • {{ I and i < a.length }} s = s + a[i]; i = i + 1; {{ I }}
    • Two lines in a row: the rule for a sequence
  • Line 17: put the claim's sum for s0, the old s
s = s0 + a[i]                      the forward rule
  = a[0] + ... + a[i - 1] + a[i]   since s0 = a[0] + ... + a[i - 1]
  = a[0] + ... + a[i]
  • Between the lines, with i <= a.length dropped:
    • 0 <= i and i < a.length and s = a[0] + ... + a[i]

Check (2), line 18

  • Line 18: the old i is i - 1
    • Put i - 1 for i in each fact of the claim between the lines
0 <= i - 1                  from 0 <= i
1 <= i                      adding 1 to both sides
i - 1 < a.length            from i < a.length
i <= a.length               since i and a.length are integers
s = a[0] + ... + a[i - 1]   from s = a[0] + ... + a[i]
  • That claim implies I, since 1 <= i implies 0 <= i
  • So check (2) passes

Check (3)

a.length <= i                      since not (i < a.length)
i = a.length                       since i <= a.length
s = a[0] + ... + a[i - 1]          from I
  = a[0] + ... + a[a.length - 1]   since i = a.length
  • The calculation ends at the postcondition: check (3) passes
  • The bound: the step to i = a.length used i <= a.length
    • Without it, only a.length <= i, not i = a.length
    • The loop has not changed, so the claim is too weak
  • All three checks pass: the triple for the body of sum is valid

Does the loop end?

  • Variant: an integer upper bound on the passes remaining
    • Bounded below and strictly decreasing, so the loop ends
  • For sum: a.length - i, the elements not yet added
    • An integer, since a.length and i are ints
    • At least 0 at each condition check, since I says i <= a.length
    • Smaller by 1 each pass, since line 18 adds 1 to i
  • So at most a.length passes: sum satisfies its specification

while (true) { }

  • A loop that never ends, with true for I
  • Checks (1) and (2) pass: every claim implies true
  • Check (3): true and not true has to imply Q
    • It is false in every state, so it implies every Q
  • So check (3) passes, whatever Q is
    • Q = false: the checks would prove the postcondition false
  • The three checks pass for a loop that never ends

Finding the invariant

  • So far, the invariant of sum has been given to us
  • Where does an invariant come from?
  • Finding one takes some creativity
  • In simple cases: read I off the postcondition
    • Q says what is true when the loop is done
    • I says how the loop makes progress toward Q

sum: read I off Q

  • Q: s = a[0] + ... + a[a.length - 1]
  • At each condition check, i is the count of elements added so far
  • So we put i for a.length in Q: the main fact of I
    • s = a[0] + ... + a[i - 1]
    • At the exit, i = a.length, so the main fact turns back into Q

sum: the bounds on i

  • From where i starts and where it stops:
    • 0 <= i: line 15 starts i at 0
    • i <= a.length: a pass runs only when i < a.length
  • Check (3) needs the bound i <= a.length
  • So an invariant has two kinds of facts:
    • What has been done so far: s = a[0] + ... + a[i - 1]
    • How far along the loop is: 0 <= i and i <= a.length

Too weak, too strong

    • The calculation for check (3) cannot reach the postcondition
  • Too strong: add 0 < a.length to sum's I
    • Check (1) fails on an empty array
  • A failed check means that the code is wrong
    • or that the claim we chose for I is
  • Here sum is right, so both times the claim is what has to change

What reasoning tells us

  • Lecture 7 closed on three things: here is where each stands for loops

    • A refuting test refutes the argument too, so we still test
  • Arithmetic that is not Java's: the claims are about the integers
    • Java's int wraps: so a bound on the inputs, or a long
  • A claim the rules do not produce: no rule gives I
    • Finding the invariant is the programmer's work
