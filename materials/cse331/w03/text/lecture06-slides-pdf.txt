When a method cannot do its job
 A user's mistake: the user typed something the program cannot use
 A programmer's mistake: some code breaks a promise, a precondition
 A request that cannot be carried out
   Pop an empty stack; Lecture 2's indexOf on a missing value
 The user's 1 + reaches add as a request it cannot carry out
 Separation of concerns: main talks to the user, CalcStack computes
 Today's question: how does a method say no to its client?

Six ways to say no
 A precondition (*): multiply requires 2 <= size()
 A special value (.): pop returns null
 A flag (+): add returns false
 A wrapper (t): top returns an empty OptionalInt
 An exception (/): divide throws one
 A checked exception (-): subtract throws one
 One per operation, on purpose; a real class picks one

int and Integer
 A special value must be one the method never returns otherwise
   -1 for an empty stack's top? The top may be -1
 A primitive type, such as int or boolean, holds a plain value
 A reference type may hold null, which refers to nothing
 Integer: the ints, plus null
 Java converts between them by itself
   int to Integer always works; Integer to int fails on null

try and catch
 throw ends the method at once
 Java looks for code that will catch it; with none, a stack trace
 No exception: the try block runs, and that is all
 An exception named in a catch: its block runs, not a crash
 Think of it as an if on "did the block throw?", with catch as the else

Checked and unchecked
 Unchecked: extends RuntimeException
   Thrown with no throws clause; the client may catch it or not
 Checked: extends Exception, not RuntimeException
   The method says so: throws StackException (line 168)
   Every client catches it, or declares it too
 The compiler tracks the checked kind
 FileNotFoundException, which Lecture 3's Sum caught, is checked

The six, forgotten
 A flag: nothing happens, silently
 A precondition: all bets are off; here, a NullPointerException
 A special value: . prints null, or an int stops the program
 An exception: a stack trace with the method's own message
 A wrapper: a crash at the ask; as an int, it does not compile
 A checked exception: the compiler refuses the program

Let the compiler find the mistake
 The compiler is a tool: it checked one claim about every run
   That main catches StackException, or declares it
 The author chose it: the compiler holds every client to the check
 A mistake it catches never reaches a run, a user, or a test

What a checked exception costs
 Every client must catch it or declare it
   Even one that knows the stack has two numbers
 And so must every method between main and subtract
 The tension: every client pays, in a try or a clause
   In return, the compiler checks every client, before any run




                                                                 49
Choosing a way
 Can the client check first, cheaply? Then a precondition
   And the condition sits in front of whoever reads main
 How convenient is the answer? An if, a try, or a try everywhere
 What happens when a client forgets? Silence, a crash, or the compiler
 Promising to throw strengthens the specification: hard to take back
 A later lecture returns to exceptions in depth

A rule of thumb: which kind of exception?
    Bloch's rule: who caused the problem, and who can recover?
    The client can recover: a checked exception (or a wrapper)
        A file that is not there
    Only a bug can cause it: an unchecked exception (or a precondition)
        A call that breaks a precondition
Joshua Bloch, Effective Java, 3rd ed. (2018), item 70.

A seventh way: make something up
 A bad one: say nothing, and make up an answer
   add could treat a missing number as 0
 JavaScript: an array read past its end gives undefined
   undefined + 1 is NaN, and NaN + 1 is NaN: it travels on
 Java's doubles: NaN is a special value; unchecked, it travels on too
 null, returned where the specification does not say so
