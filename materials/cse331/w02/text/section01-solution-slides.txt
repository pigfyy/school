--- slide 5 ---
Documenting Methods w/ JavaDoc
JavaDoc comments use “tags” to describe what methods do
/**
 * High level description of what function does
 * @param a + What &quot;a&quot; represents + any conditions about a
 * @requires Rules about multiple params
 * @returns Detailed description of return value
 * @throws Condition when errors will be thrown
 */
For methods that mutate variables/state, will have 2 additional tags to describe mutation
 * @modifies states what could be mutated by function
 * @effects Detailed description of guaranteed changes

*Note: @requires, @modifies, and @effects are all unique to 331

// Spec D
// @requires 0 &lt;= lo &lt;= hi &lt;= a.length
// @returns *some* index i with lo &lt;= i &lt; hi and a[i] == x,
//          or -1 if no such index exists

// Impl 1
public static int indexOf(int[] a, int lo, int hi, int x) {
   for (int i = lo; i &lt; hi; i++) {
       if (a[i] == x) {
           return i;
       }
   }
   return -1;
}
When spec B is satisfied, spec D is also satisfied!

Review: Stronger vs Weaker Assertions
An assertion is stronger if and only if it holds in a subset of states
A stronger assertion implies the weaker one 
This means that if the stronger assertion is true, then the weaker assertion must also be true.

Below, Q2 is the stronger assertion as knowing Q2 is true tells us that Q1 is true. However, knowing Q1 is true doesn’t tell us Q2 is true.

a weaker (or equal) precondition, and
a stronger (or equal) postcondition
In this case, we also say S2 is weaker than S1

--- slide 11 ---
Accepting more generic @params increases specification strength (same params w/ less restrictions)
We’ll talk about this later with generics

Adding more to @requires decreases specification strength
Strengthens the precondition (takes in less inputs)
Ex: param List lst must be sorted is more restrictive = stronger precondition = weaker spec than no requirement about order
Specification Strength: Precondition

--- slide 12 ---
Adding more to @returns increases specification strength
Strengthens the postcondition

@throws still specifies behavior, so it is stronger than @requires
Still accepts that input and defines the behavior for it

Specification Strength: Postcondition

Task 2: Mutable Spec/Impl Satisfaction
// Spec A
// @effects if the first occurrence of x in a[0..n] is at index i,
//   then the new values in a[0..n-1] will be the old values of a[0..i]
//   followed by the old values of a[i+1..n], and the new value of a[n-1]
//   is unspecified. else, if x does not occur in a[0..n], leaves a unchanged;  
// @return n - 1 if x was removed, else n

// Spec B
// @effects if x does not occur in a[0..n], leaves a unchanged;
//   otherwise, the new values in a[0..n-1] are a possibly reordered version
//   of the old values of a[0..n] with one fewer occurrence of x,
//   and the new value of a[n-1] is unspecified
// @return n - 1 if x was removed, else n

--- slide 22 ---
Task 2: Mutable Spec/Impl Satisfaction
// Spec C
// @effects if x does not occur in a[0..n], leaves a unchanged;
//   otherwise, if x occurs k &gt; 0 times in a[0..n], then remove all k
//   occurrences of x, leaving remaining elements in the same relative
//   order as before; the new value of elements in a[n-k..n] is unspecified
// @return n - k

// Spec D
// @requires a[0..n] contains no duplicates
// @effects if x does not occur in a[0..n], leaves a unchanged;
//   otherwise, if x occurs in a[0..n] at index i, then the new values
//   in a[0..n-1] will be the old values of a[0..i] followed by the
//   old values of a[i+1..n], and the new value of a[n-1] is unspecified.
// @return n - 1 if x was removed, else n

--- slide 23 ---
Task 2: Implementation 1
// Impl 1
int w = 0;
for (int r = 0; r &lt; n; r++) {
    if (a[r] != x) {
        a[w] = a[r];
        w++;
    }
}
return w;
Impl 1 removes all occurrences of x in a[0..n], leaving remaining elements in order.

Doesn't satisfy A because it requires only one occurrence to be removed.
B not satisfied for same reason as A.
Does exactly what C says.
Also satisfies D because D's precondition (no duplicates) means removing all occurrences is the same thing as removing one occurrence.

Task 2: Implementation 2
// Impl 2
for (int i = 0; i &lt; n; i++) {
    if (a[i] == x) {
        for (int k = i; k &lt; n - 1; k++) {

Impl 2 removes the first occurrence of x in a[0..n] by shifting everything left by one.

Does exactly what A says.
Also satisfies B because B says &quot;possibly reordered&quot;, but reordering is not required, and B doesn't care which occurrence is removed.
Doesn't satisfy C because it requires all occurrences to be removed.
Also satisfies D, since under D's precondition, the only occurrence of x is also the first occurrence of x.

Impl 3 removes the last occurrence of x in a[0..n] by shifting everything left by one.

Doesn't satisfy A because A asks for the first occurrence to be removed, not the last.
Satisfies B because B says &quot;possibly reordered&quot;, but reordering is not required, and B doesn't care which occurrence is removed.
Doesn't satisfy C because it requires all occurrences to be removed.
Also satisfies D, since under D's precondition, the only occurrence of x is also the last occurrence of x.

Task 2: Implementation 4
// Impl 4
for (int i = 0; i &lt; n; i++) {
    if (a[i] == x) {
        a[i] = a[n - 1];
        return n - 1;
    }
}
return n;

Impl 4 overwrites the first occurrence of x with a copy of a[n-1].

Doesn't satisfy A because it requires relative order to be preserved, but now a[n-1] got moved into the relative position that used to be occupied by x.
Satisfies B because B allows reordering as long as there is one fewer occurrence of x, which there is, because Impl 4 overwrote one.
Doesn't satisfy C because C requires removing all occurrences of x.
D not satisfied for same reason as A.
