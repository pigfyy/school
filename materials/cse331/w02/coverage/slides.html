How many tests are enough?

  • Our eleven tests all ran lines 19 and 20, and never the loop
  • Fifty below 100 would be no better: the number is not what matters
  • Every allowed input: \(2^{31} - 1\) for isPrime, each needing its answer
  • Lecture 2's check: every input within a bound, none outside it

One test is never enough

  • Suppose isPrime always returned true
    • The test on 7 expects true, and passes
    • The test on 8 expects false, and fails
  • One test cannot catch it: the answer may be the one it expects
  • So every method needs at least two tests

Coverage

Our eleven tests all ran the same part of the method. What matters is which parts of the method the tests run.
  • Which parts has a set of tests run? The code says, not the specification
  • Lecture 4 read the specification. Now read the code
  • Coverage: how much of the code a set of tests has run
    • From the code: clear-box testing. From the specification: black-box
  • Three measures, each catching what the last one missed

Statement coverage

  • Our eleven tests ran lines 19 and 20, and no test ran the loop

Definition

A set of tests has statement coverage of a method if every statement that some allowed input reaches is run by some test.

  • Not enough, by this measure: 2 to 12 never ran the loop. 121 did
  • Enough, by this measure: 2, 100, and 101 pass, and the mistake stays

Branch coverage

  • Every if has two branches: condition true, condition false
    • An if with no else still has a false branch, and it is empty

Definition

A set of tests has branch coverage of a method if every branch that some allowed input takes is run by some test.

  • Our two tests of min have it; the second found the mistake

Paths

  • The two passing tests ran every branch, but never this combination
  • A path through the method is one combination of branches
    • quadrant has four, and testing every path finds the mistake
  • We do not ask for paths: they multiply
    • Ten ifs in a row: \(2^{10}\) paths, over a thousand
    • A loop: a path for every number of times its body can run
  • One more measure, for loops, which branches do not measure

  • The loop's body: how many times does it run in each test?

  • findsTheFirstMatch, findsSomeMatch: 5 at index 0. Once

Loop coverage

Definition

A set of tests has loop coverage of a method if, for every loop in it, some test runs the loop's body zero times, some test runs it once, and some test runs it more than once.

  • Zero times: the code after the loop must be right when it did nothing
  • Once: the body must be right on its own
  • More than once: what the loop carries from one run to the next

When to stop

A method's tests are enough when there are at least two and, between them, they have run all an allowed input can reach:
  • Every statement
  • Both branches of every if
  • Every loop's body zero times, once, and more than once
  • Every method that calls itself with zero, one, and more than one call

Until then, the list says which test to write next. Then you may stop.

The second list of James Wilcox and Kevin Zatloukal's "Testing" (2025).

Three things about the list

  • Only allowed inputs count, as tip 1 says
    • A statement only a disallowed input reaches is not on the list
  • The measures nest: loops bring branches, branches bring statements
    • Plan for loops and branches, and get statements for free
  • In wide use: coverage tools report statement and branch coverage
    • Loop coverage you count yourself, as we did for IndexOfTest
    • Homework holds a method's tests to the whole list

A boundary, read off the code

  • The condition k * k < n divides inputs at k * k == n
    • A test should sit on that line: a perfect square
  • Lecture 4's boundaries: the specification. This one: the code
  • The list does not ask for it; a careful tester writes it anyway

Outside the list

  • A missing case: in the specification, and in no line of the code
    • No statement, branch, or loop to run, so the list asks for no test
    • Its test comes from reading the specification, as Lecture 4 did
  • The Therac-25: six patients overdosed in the 1980s
    • An edit to the prescription within the machine's eight seconds
    • The task that set the magnets never noticed the edit
    • The mistake was in the timing of two tasks, outside the list

Testing refutes, never confirms

  • Lecture 1: testing can refute a claim about every run, never confirm it
    • Short of testing every allowed input
  • Completing the list: a good reason to believe, not knowledge
  • A tool confirms one claim: the one it was built to check
  • Reasoning, after Monday, confirms a claim about every run

The floor

  • The list says when you may stop, not that you must
  • Above the list: how much more depends on what a mistake would cost
    • A steering program: every path, every boundary read off the code
    • An engineering judgment, on every program you write
  • Below the list: no judgment to make
    • The list, plus Lecture 4's cases and boundaries
    • The least any code you deliver gets, whatever the deadline

That least is the floor. The motto says whose job it is.

Test code is code

  • Lecture 2's check was a program: a loop over every small array
    • A loop that skipped the empty range would have reported success
  • Keep tests simple: one call and one assertEquals, checked by eye
    • A test with a loop in it needs its own tests
  • A clever test: write two plain ones instead

Testable by design

  • A method is hard to unit test when:
    • It is large, or does several jobs at once
    • It reads or writes outside its arguments and return: a file, the screen
  • Lecture 2 split Sum into readList and sumList
    • A test of sumList: one call, one assertEquals, no keyboard
    • The split that lets you understand a program lets you test it

What tests tell us

  • A test confirms a claim about its own run
  • Coverage says how many such runs, and which: read off the code
  • The expected answers still come from the specification

What you owe

The floor is the price of admission to calling yourself an engineer. You don't get to cost-benefit your way below the baseline. The curve tells you how far up to go; the floor tells you what you owe no matter what. If you don't test your code at least this much, you are failing due diligence as an engineer.
