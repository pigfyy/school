Representation invariant

Definition: representation invariant

A representation invariant (RI) of a class is a claim about its fields that is true of every object of the class whenever no method of the class is running. The constructor makes it true. Every method may assume it when called and must make it true again before it returns. An implementation should document its representation invariant with a comment like // RI: ... beside the fields.

Abstract invariant: the abstract state. RI: the concrete state, the fields

The RI settles it

65    String front = queue.remove(0);
66    members.remove(front);
68    return front;
  • The RI: members holds exactly the NetIDs in queue
  • Every method must make it true again before it returns
  • Removing the front from queue means removing it from members too
  • Without that line, next returns with the RI false: next is wrong
  • join and size may assume the RI, and the client saw them misbehave
    • Because they ran from a state the RI forbids: not their bug

Reasoning finds the mistake where it was made; a test would see it a call later

checkRep

  • Catch a bug as soon as the RI is violated

Definition: checkRep

A checkRep method of a class checks the class's representation invariant in code: it reads the fields, computes each clause of the RI from them, and throws an exception if any clause is false. It is private, since it is the implementer's check and not part of the specification, and it changes no field.

FastQueue's checkRep

Where to call checkRep

  • A method that changes the object, as join and next do, is a mutator
  • The code quality guide: call checkRep
    • at the end of the constructor;
    • at the beginning and end of every mutator method;
    • at the beginning of every non-mutator method.
  • checkRep builds a set from the whole list, at every check
    • So join is fast only once the checks are off

Abstraction function

Definition: abstraction function

The abstraction function (AF) of a class maps each value of the fields that the representation invariant allows to the abstract state it stands for. The AF is a mathematical function, not code. An implementation should document its abstraction function with a comment like // AF(this) = ... beside the fields.

  • RI: which field values are allowed. AF: what they stand for

Abstraction function, as a map

  • Defined only where the RI is true
  • Many values of the fields, one abstract state; no arrow goes back

The problem

  • A specification is written about the abstract state
  • An implementation is written about the concrete state, its fields
  • Between the promise and the code, a gap: what do the fields stand for?

What correct means

  • The specification is about the queue; the body is about the fields
  • The AF connects them
  • The RI is assumed before and owed after

What correct means, the rule

Rule: a method of an abstract data type is correct

A method with precondition P and postcondition Q, written about the abstract state, is correct exactly when the Hoare triple {{ RI and P(AF(this)) }} the method's body {{ RI and Q(AF(this)) }} is valid and every call that begins with P true terminates, where RI is the representation invariant and AF is the abstraction function.

Representation exposure

Definition: representation exposure

Representation exposure is a reference, held by code outside a class, to a changeable object among the class's fields. Through it, that code can change the fields without calling any method of the class, so the representation invariant and every specification can be broken by code the class does not control. To prevent it, copy in a changeable object a client passes that becomes part of the fields, and copy out a changeable field that a method returns.

Copy in: line 31 of FastQueue.java. Copy out: its line 73

Strings are safe to share

  • No method of String can change a string
    • So a method that returns a String field exposes nothing
  • An int holds a plain value: the client gets a copy of the number
  • A List, a Set, an array: copy in, copy out
  • A class is correct when every method is correct by the rule
    • and the class has no representation exposure

Java 25's documentation of String: "Strings are constant; their values cannot be changed after they are created"
