        CSE 331: Implementing an abstract data type

lecture

Course motto: Your job is to deliver code that you know works.

A specification is written about the abstract state, the queue
as the client thinks of it. An implementation is written about
the concrete state, its fields. The specification says what every
method must do, but in abstract terms: the students waiting,
front first. The body does its work in concrete terms: a list, a
set. So between the promise and the code there is a gap, and
nothing yet says how to cross it: which values of the fields are
allowed, which abstract state a value of the fields stands for,
and so whether a body does what its specification says. This
lecture closes the gap with two additions: a claim about the
concrete state, the representation invariant, and a function from
the concrete state to the abstract state, the abstraction
function. Together they say what it means for a method, and then
a class, to be correct, and they show why no code outside the
class may reach the fields.

FastQueue: a faster join

Recall Wednesday's half sheet: a queue that keeps the students
twice, in a list for the order and in a set, so that join's
check for a student already waiting asks the set instead of
walking the list. A HashSet answers in "constant
time", however long the queue.1 Here is that class,
FastQueue. Its check is faster. But now two fields hold the
same students, and every change to one has to be made to the
other.

75import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.NoSuchElementException;
import java.util.Set;

/**
 * A help queue kept as a list and a set, so that join's check for
 * a student already in the queue takes the same time however long
 * the queue is.
 */
public class FastQueue implements HelpQueue {
    // The students waiting, front first.
    private List<String> queue;
    // The same students, for a fast lookup.
    private Set<String> members;
    // RI: no NetID is in queue twice, and members holds exactly
    //     the NetIDs in queue.
    // AF(this) = the help queue of the students in queue, front first.

    public FastQueue() {
        queue = new ArrayList<String>();
        members = new HashSet<String>();
        checkRep();
    }
    /** @requires no NetID is in netids twice
     *  @effects makes a queue of the students given, front first */
    public FastQueue(List<String> netids) {
        // A copy, so that the client cannot change the queue through
        // the list it passed.
        queue = new ArrayList<String>(netids);
        members = new HashSet<String>(netids);
        checkRep();
    }

    private void checkRep() {
        if (!members.equals(new HashSet<String>(queue))) {
            throw new IllegalStateException("members is not the queue");
        }
        if (members.size() != queue.size()) {
            throw new IllegalStateException("someone is in queue twice");
        }
    }

    public int size() {
        checkRep();
        return members.size();
    }

    public void join(String netid) {
        checkRep();
        if (members.contains(netid)) {
            throw new IllegalArgumentException(netid + " is in the queue");
        }
        queue.add(netid);
        members.add(netid);
        checkRep();
    }

    public String next() {
        checkRep();
        if (queue.isEmpty()) {
            throw new NoSuchElementException("nobody is waiting");
        }
        String front = queue.remove(0);
        members.remove(front);
        checkRep();
        return front;
    }

    public List<String> waiting() {
        checkRep();
        return new ArrayList<String>(queue);
    }
}

Here is the problem in two sentences. A specification is written
about the abstract state, so it says nothing about how the fields
must agree with one another. When the fields drift apart and a
client sees a promise broken, nothing in the specification says
which method's code is wrong; the representation invariant does.

Representation invariants

Definition: representation invariant

A representation invariant (RI) of a class is a claim about
its fields that is true of every object of the class whenever
no method of the class is running.

The constructor makes it true. Every method may assume it when
called and must make it true again before it returns. An
implementation should document its representation invariant
with a comment like // RI: ... beside the fields.

In the example from the previous section, lines 17 and 18 of
FastQueue.java make a claim of this kind. join and size may
assume the RI when they are called, so they are right to trust
the set. next must make the RI true again before it returns,
and without line 66 it does not. So next is the method that is
wrong.

The RI is not Wednesday's abstract invariant, though
both definitions say "whenever no method ... is running". The two
claims differ in what each is about:

The abstract invariant was a claim about the abstract
  state, the students waiting: a student is in the queue at most
  once. It is there for
  the client's benefit. HelpQueue's specifications keep it true,
  so a client can rely on the abstract invariant with any class
  that satisfies them.

The RI is a claim about FastQueue's concrete state, the
  values of its fields queue and members. It is there for the
  implementer's benefit. Each class has its own, and not every
  class needs one written down: ListQueue and LinkedQueue
  have no members to keep in step, and neither has an RI
  comment. Wednesday's "at most once" does not appear in
  FastQueue's. Its first half says that no NetID is in the list
  queue twice, a claim about a field that a client never sees.

Whenever no method of the class is running says when the RI
has to be true. Lecture 8's loop invariant was placed
the same way: its definition puts the claim at the point where the
loop checks its condition, and nowhere inside the body. In
Lecture 8's sum, the invariant includes
s = a[0] + ... + a[i - 1]. sum's line 17 adds a[i] to s,
so s becomes the sum of the first i + 1 elements. So between
sum's lines 17 and 18, that claim is false unless a[i] is 0.
sum's line 18 adds 1 to i, and the invariant is true again at
the next condition check.

The RI is not always true either. It is true between every two
calls to the class's methods, and it may be false inside a method.
Even in FastQueue.java as written, the RI is false between line 65
and line 66: the list has lost the front, and the set still has
it. Line 66 makes the RI true again before next returns.

A claim written in a comment is one that a method can forget, as
next without line 66 did, so the next section turns the RI into
code.

Checking the representation invariant with checkRep

The RI on lines 17 and 18 is a claim about two fields. Java can
compute each part of the claim from the fields' values. So the
class can check its own RI, and throw an exception each time it
finds the RI false. This section introduces the method that does
that: checkRep, the private method on lines 36 to 43.

Each if checks one clause of the RI. Line 37 checks the second
clause, that members holds exactly the NetIDs in queue.
new HashSet<String>(queue) makes a set of the NetIDs in the list,
and equals compares that set with members. If the two sets
differ, line 38 throws, with the message
"members is not the queue".

Line 40 checks the first clause, that no NetID is in queue twice.
A set drops a repeat: the set of [ada, ada] is {ada}. So a list
with a repeat is longer than its set. By line 40, line 37 has
passed, so members is the set of the list. If the list is longer
than members, line 41 throws, with the message
"someone is in queue twice". If neither check fails, checkRep
returns and does nothing else.

Lines 38 and 41 both throw IllegalStateException. Java's
documentation says that this exception signals "that a method has
been invoked at an illegal or inappropriate time".3 Every
method of FastQueue may assume the RI when it is called. So a
call to any of them while the RI is false comes at such a time.

FastQueue's checkRep checks FastQueue's RI. Any class with
an RI can have one:

Definition: checkRep

A checkRep method of a class checks the class's
representation invariant in code: it reads the fields,
computes each clause of the RI from them, and throws an
exception if any clause is false.

It is private, since it is the implementer's check and not
part of the specification, and it changes no field.

This is Lecture 6's defensive programming, turned
on the class's own fields. There, a method with a precondition was
under no obligation to check it, and checked it anyway, as a good
citizen. Here, every method may assume the RI when it is called,
and FastQueue checks it anyway. The check costs something and
promises nothing to the client. What it buys is a failure in the
method that made the mistake, on the call that made it.

Which methods should call checkRep, and where? The course's code
quality guide gives a rule, in its section
checkRep. The rule uses a word the notes have not:
a method that changes the object, as join and next change the
queue, is a mutator. The guide says to call checkRep in
three places:

at the end of the constructor;

at the beginning and end of every mutator method;

at the beginning of every non-mutator method.

FastQueue keeps the rule. Each constructor checks once, at its
end: line 24, and line 33. join and next are mutators, so each
checks twice: join on lines 51 and 57, and next on lines 61 and
67. size and waiting change nothing, so each checks once, at
its start: size on line 46, and waiting on line 72.

Why these places and no others? A method that changes nothing
leaves the fields as they were, so it cannot make the RI false.
So a non-mutator does not check at its end. A constructor is
different. When a constructor starts, queue and members are
both null. So the RI is false, and a checkRep at the start
would throw. The constructor may not assume the RI. It must make
the RI true. Every method after it may assume what the call before
it left. So the RI a method assumes at its start was checked
already, at the end of the last call that changed the object.

Then why check at the start at all? The section
Copy in, copy out answers that.

The guide's list says nothing of private methods, but one kind of
method should not check: a private one. Only the class's own code
can call a private method. So a private method may be
called in the middle of another method, with the RI false, as it
is between lines 65 and 66. A check at the start of such a method
could throw though nothing is wrong.

Now the cost that the section FastQueue: a faster join
put off. Line 37 builds a new set from the whole list, at every call
to checkRep. With two hundred students waiting, that set gets two
hundred NetIDs. A join calls checkRep twice, so each join walks
the list twice, though its own check on line 52 never does.
ListQueue's join walked the list at most once. So FastQueue as
written does more work in each join than ListQueue does. Its
join is fast only once the checks are off.

The code quality guide's section
Defensive programming says which checks to keep.
In production (the program as its users run it), check only the
fast parts of the RI. A flag turns on the slow parts during
debugging and testing. This lecture is debugging and testing, and
the checks caught the forgetful next on its own call, on line
67. So it keeps every check on.

The RI says which values of queue and members are allowed. It
does not say what those values mean: which abstract state a list
and a set stand for. The next section changes the fields, and
asks what they stand for.

A faster next

FastQueue made join faster, and left next as it was. Its
next removes the front student with queue.remove(0), on line 65
of FastQueue.java, just as line 24 of ListQueue.java does. An
ArrayList keeps its elements in an array, in order. So when
remove takes out the first element, it moves every element after
it one place to the left, to close the gap.4 With two
hundred students waiting, each next moves the other hundred
and ninety-nine. So the longer the queue, the longer each next
takes to run.

No element comes after the last one, so removing the last
element of an ArrayList moves nothing. So let's keep the queue
in two lists, and add to or remove from each list only at its end:

join adds the student at the end of one list, the inbox.

next removes the student at the end of the other list, the
  outbox. The outbox holds the front of the queue last, so its
  last student is the next one served.

When the outbox runs dry, next refills it, moving the inbox
  over in reverse. The student who joined first lands at the end
  of the outbox.

Between joining and being served, each student is moved from the
inbox to the outbox once. The set stays, for join's check. (The
class's comment, on line 8, calls the two lists stacks. A
stack is a collection that is added to and taken from at one
end only, so the last one in is the first one out.) Here is that
class, FasterQueue:

95import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.NoSuchElementException;
import java.util.Set;

/**
 * A help queue kept as two stacks and a set: join adds at the end of
 * one list, next removes from the end of the other, and the set
 * answers join's check, so that neither walks the whole queue.
 */
public class FasterQueue implements HelpQueue {
    // The students who joined since the last refill, oldest first.
    private List<String> inbox;
    // The students ahead of them, with the front of the queue last.
    private List<String> outbox;
    // The same students, for a fast lookup.
    private Set<String> members;
    // RI: no NetID is in inbox or outbox twice, or in both, and
    //     members holds exactly the NetIDs in inbox and outbox.
    // AF(this) = the help queue of the students in outbox, last to
    //     first, then the students in inbox, first to last.

    public FasterQueue() {
        inbox = new ArrayList<String>();
        outbox = new ArrayList<String>();
        members = new HashSet<String>();
        checkRep();
    }
    /** @requires no NetID is in netids twice
     *  @effects makes a queue of the students given, front first */
    public FasterQueue(List<String> netids) {
        // A copy, so that the client cannot change the queue through
        // the list it passed.
        inbox = new ArrayList<String>(netids);
        outbox = new ArrayList<String>();
        members = new HashSet<String>(netids);
        checkRep();
    }

    private void checkRep() {
        Set<String> waiting = new HashSet<String>(inbox);
        waiting.addAll(outbox);
        if (!members.equals(waiting)) {
            throw new IllegalStateException("members is not the queue");
        }
        if (members.size() != inbox.size() + outbox.size()) {
            throw new IllegalStateException("someone is in the queue twice");
        }
    }

    public int size() {
        checkRep();
        return members.size();
    }

    public void join(String netid) {
        checkRep();
        if (members.contains(netid)) {
            throw new IllegalArgumentException(netid + " is in the queue");
        }
        inbox.add(netid);
        members.add(netid);
        checkRep();
    }

    public String next() {
        checkRep();
        if (members.isEmpty()) {
            throw new NoSuchElementException("nobody is waiting");
        }
        // When the outbox runs dry, move the inbox over in reverse, so
        // that the front of the queue is at the end of the outbox.
        if (outbox.isEmpty()) {
            for (int i = inbox.size() - 1; i >= 0; i--) {
                outbox.add(inbox.get(i));
            }
            inbox.clear();
        }
        String front = outbox.remove(outbox.size() - 1);
        members.remove(front);
        checkRep();
        return front;
    }

    public List<String> waiting() {
        checkRep();
        List<String> list = new ArrayList<String>();
        for (int i = outbox.size() - 1; i >= 0; i--) {
            list.add(outbox.get(i));
        }
        list.addAll(inbox);
        return list;
    }
}

Abstraction functions

Definition: abstraction function

The abstraction function (AF) of a class maps each value of
the fields that the representation invariant allows to the
abstract state it stands for.

The AF is a mathematical function, not code. An implementation
should document its abstraction function with a comment like
// AF(this) = ... beside the fields.

In the example from the previous section, what crosses the gap is a
function from the concrete state to the abstract state, and
FasterQueue's comment on lines 21 and 22 gives it: the queue is the
students in outbox, last to first, then the students in inbox,
first to last. That is today's second addition. Let's read
FasterQueue's fields by its AF as students come and go. Start with
a new FasterQueue, and join ada, bob, and eve. Each join adds to
the inbox on line 62 and to the set on line 63. So inbox is [ada,
bob, eve], outbox is [], and members is {ada, bob, eve}. The
outbox holds nobody, and the inbox, first to last, is ada, bob, eve.
So these fields stand for the queue ada, bob, eve, the order the
three joined.

Now call next. The outbox is empty, so the loop on lines 75 to 77
adds eve, then bob, then ada to the outbox. Line 78 empties the
inbox. Line 80 removes ada, the last student of the outbox,
and line 81 removes ada from the set. So inbox is [], outbox is
[eve, bob], and members is {bob, eve}. The outbox, last to first,
is bob, eve, and the inbox adds nobody. So these fields stand for
the queue bob, eve. That is right: ada was served, and bob is at
the front.

The comment on lines 21 and 22 says, for each value of the fields:
if the fields look like this, here is what the client should be
thinking. A client of this queue, after the one next, should be
thinking bob, eve.

Other values of the fields stand for the same queue. Here is
another way to reach bob, eve. ada and bob join, so inbox is
[ada, bob]. next moves them over in reverse, so outbox is [bob,
ada], and serves ada, so outbox is [bob] and inbox is []. Then
eve joins. Now inbox is [eve], outbox is [bob], and members
is {bob, eve}. The outbox, last to first, is bob, and then the
inbox adds eve. So these fields stand for bob, eve too. In all,
three values of the fields stand for the queue bob, eve. They
differ in how many students, counted from the front, the outbox
holds: none, bob alone, or both. (With none, inbox is [bob, eve]
and outbox is [].) The drawing below shows two of them.

So the comment goes one way, from the concrete state to the
abstract state. Given the fields, the comment names one queue.
Given the queue bob, eve, no one value of the fields is the
value for it. So no function goes back the other way, from the
queue to the fields.

Two queues, three values of the fields.

The definition says that the AF is not code, and the comment on
lines 21 and 22 shows why. It reads like a function: given this,
it says what queue this stands for. But a function in Java
returns a Java value. A queue of students is the abstract
state, and no Java method returns that. So the comment describes
a mathematical function. The client does
not know the fields, so the client cannot read it. The function is
the implementer's alone, and every method relies on it. By the
comment, for one, the end of the inbox is the back of the queue,
so join adds there.

Here is what three of the definition's phrases mean:

That the representation invariant allows says where the AF
  is defined: only on values of the fields that the RI allows.
  Take fields where inbox is [bob], outbox is
  [bob], and members is {bob}. bob is in both lists, so the RI
  is false. Read by lines 21 and 22, these fields would be the
  queue bob, bob. But a student is in the queue at most once, so
  no queue is bob, bob. These fields stand for nothing, and the AF
  need not say what they mean.

A mathematical function, not code rules out reading the
  comment as a method. No method of FasterQueue computes the AF.
  (waiting comes close: it lists the students in the order that
  lines 21 and 22 give. But what it returns is a Java list, a
  value in the program, and not the queue itself.)

A comment like // AF(this) = ... is the form of lines 21
  and 22. this is the object whose fields the AF maps.

The fields bob, bob show a requirement that every RI must meet.
Whenever the RI is true of the fields, the abstract state they
stand for must satisfy the type's abstract invariant: a student
is in the queue at most once. Written with AI for the abstract
invariant: RI(this) implies AI(AF(this)).
FasterQueue's RI meets it. No NetID is in either list twice, or
in both, so the queue that lines 21 and 22 read off the two lists
has each student at most once. An RI that allowed the fields bob,
bob would let the fields stand for a queue no client can be
promised.

What correct means for an ADT method

Let's put FasterQueue's size beside its specification. Here

This is the gap the paragraph at the top of these notes
described. size's specification is in abstract terms.
HelpQueue.java has no fields, so no line of it mentions one.
size's body is in concrete terms. No line of the body mentions

abstraction function, from the concrete state to the abstract

the fields stand for a queue of students. The specification is
about that queue.

So what do we check? In Lecture 7, a method satisfies its
specification exactly when the triple of its
specification around its body is valid, and every call that
begins with the precondition true terminates. Lecture 10 asked
the same of an implementation: the fields may change,
as long as each method still satisfies its specification.
But for a method of an ADT, the specification's claims do not
meet the body's. size's postcondition is a claim about the
abstract state, the students waiting. The claims between the
body's lines are about the concrete state: inbox, outbox, and
members. So the triple to check is the
specification's translation, read through the AF:

The precondition P becomes P(AF(this)): P is true of
  the abstract state that the fields stand for. That is P with
  the abstract state replaced by AF(this), the substitution of
  Lecture 7's rules for an assignment.

The postcondition Q becomes Q(AF(this_0), AF(this)),
  where this_0 is the object as it was when the method was
  called. A postcondition may compare two states. next's does:
  the queue after the call is the queue before it with its front
  removed. So Q takes the abstract state from before the call
  and the one after. Lecture 7's
  rule for an assignment wrote x0 for a
  variable's old value. this_0 does the same for an object.

One more claim goes in, at both ends. The constructor made the RI
true, and every earlier call left it true. So before the body,
the method may assume the RI. The next call will assume the RI
too. So after the body, the method owes it. Here is the whole
condition, as a rule:

Rule: a method of an abstract data type is correct

A method with precondition P and postcondition Q, written
about the abstract state, is correct exactly when the Hoare
triple

{{ RI and P(AF(this)) }}
the method's body
{{ RI and Q(AF(this_0), AF(this)) }}

is valid and every call that begins with the precondition true
terminates, where RI is the representation invariant, AF is
the abstraction function, and this_0 is the object as it was
when the method was called. The body may assume the invariant and
the precondition, and must leave the invariant true and the
postcondition true of what the fields now stand for.

The rule's triple has two parts that Lecture 7's triples did not,
both this lecture's: the RI, a claim about the concrete state,
and the AF, the function from the concrete state to the abstract
state. The rule's last sentence, may assume and must leave,
is the second paragraph of the RI's definition in the triple's
shape. The RI that every method may assume when called sits in
the precondition. The RI that every method must make true again
before it returns sits in the postcondition. Correct is the word
for a method that meets the rule. Each loop in FastQueue.java and
FasterQueue.java counts i down to 0, and no method calls itself.
So every method in this lecture terminates.
So, as in Lecture 7, the triple is the whole question: a correct
method satisfies its specification, as long as no code outside
the class changes its fields (the section
Copy in, copy out comes back to this).

The translation is the new work. Once the triple is written about
the fields, the argument is Lecture 7's forward reasoning, as
before. Let's argue size on FasterQueue. size has no

The half sheet's second question asks why FastQueue calls
checkRep at the start of a method, and not only at the end. The
section
Checking the representation invariant with checkRep
found that the RI a method assumes at its start was checked
already, at the end of the last call that changed the object.
Now we can say why the start check is there anyway. Between two
calls, code that is not the class's may have changed the fields,
through an alias. The change comes after the method returns, so a
check at the end of that method cannot see it. So checkRep runs
at the start of a method too. The check at the start catches the
change on the next call, as line 72 did in both drafts, rather
than in some wrong answer later. The code quality
guide's section checkRep gives the same reason.

Each draft gave code outside FastQueue a reference to a list in
its fields. This definition names that mistake:

Definition: representation exposure

Representation exposure is a reference, held by code outside
a class, to a changeable object among the class's fields.
Through it, that code can change the fields without calling
any method of the class, so the representation invariant and
every specification can be broken by code the class does not
control. To prevent it, copy in a changeable object a
client passes that becomes part of the fields, and copy out
a changeable field that a method returns.

Here is what the definition's words mean:

A reference to a changeable object needs both of its
  parts. First, the object must be changeable. Java's
  documentation says that "Strings are constant; their values
  cannot be changed after they are created".5 So a method
  that returns a String field exposes nothing. The client holds
  a reference to the field's string, but no method of String
  can change the string through it. Second, the client must hold
  a reference. int is a primitive type, which holds
  a plain value, so a method that returns an int field hands the
  client a copy of the number. Nothing the client does to that
  number reaches the field. So exposure needs a reference that
  the client can change the fields through.

Copy in and copy out are the two fixes we saw. Copy in is
  line 31: the constructor keeps a new list, not the client's.
  Copy out is line 73, and line 113 in Book: the method returns
  a new list, not the field's. The code quality guide's section
  Avoid representation exposure asks for both.

Look back at the draft that keeps the client's list. Only its
constructor differs from
FastQueue.java, and only on line 31. That constructor still
leaves the RI true. So an argument by the rule of the section
What correct means for an ADT method, for any method of
FastQueue.java, is right for the draft too. Yet in the draft,
waiting threw an exception that its specification never
mentions. So a method that is correct by the rule satisfies its
specification only when no code outside the class changes the
fields between calls. For a class as a whole, then, we count one
more thing as part of being correct. A class is correct when
every method is correct by the rule and the class has no
representation exposure.
