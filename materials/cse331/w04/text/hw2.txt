public static int f(int n) {

Task 2 — Crosscheck Your Tests

It's hockey season! Kyle Sherman wants to know how many estimated points his
favorite forward, Sherman Kyle, will score this season. He has written the
following function to help him out.

/**
 * Calculates the total estimated points scored by a forward playing on a
 * line in a 4-line rotation, over a range of shifts in a game. Line k is
 * on the ice for exactly the shifts s with s mod 4 = k.
 *
 * @param startShift         the shift number to begin calculations, inclusive
 * @param endShift           the shift number to end calculations, inclusive
 * @param lineNumber         the forward's line in the rotation (0-based,
 *                           for example, 3 for the "fourth line")
 * @param avgPointsPerShift  the average points the forward scores per shift
 *                           when his line is on the ice
 * @requires 0 <= lineNumber <= 3
 *           0 <= avgPointsPerShift
 *           startShift <= endShift
 * @return the total estimated points scored in that range
 */
public static int totalPoints(int startShift, int endShift,
                              int lineNumber, int avgPointsPerShift) {
    if (lineNumber < 0 || 3 < lineNumber
        || avgPointsPerShift < 0 || endShift < startShift) {
        throw new IllegalArgumentException();
    }

    int totalPoints = 0;
    for (int shift = startShift; shift < endShift; shift++) {
        if (shift % 4 == lineNumber) {
            totalPoints = totalPoints + avgPointsPerShift;
        }
    }

    return totalPoints;
}

Consider the following three tests, A, B, and C, written as one JUnit
method. Determine whether together they meet our coverage requirements:
statement, branch, and loop coverage. Count only what allowed inputs can
reach, as Lecture 5
does. For each kind of coverage, explain which of A, B, and C provide it,
alone or together, or what they miss.

@Test
void testTotalPoints() {
    // A
    assertEquals(6, totalPoints(4, 5, 0, 6));

    // B
    assertEquals(12, totalPoints(10, 24, 1, 4));

    // C
    assertEquals(0, totalPoints(9, 9, 3, 5));
}

Senior developer Emily peeks over Kyle's shoulder, claiming that while the
tests pass, the implementation fails to satisfy the specification under
specific inputs. Identify and write out a test case that would reveal this
and explain why the current tests failed to catch it.

Now imagine a more complex function with many more lines (maybe a function
to calculate total Kraken wins this season). Weigh the pros and cons of using
coverage-based testing as your only safety metric. What role does testing
actually play if it cannot provide a proof of correctness?

Task 3 — Nothing But Net-Pay

Zach and James, the new co-general managers of the Seattle Storm, want to add
some new players to the team. Zach and James have received a scouting report
of players, each with a name and a desired salary in millions of dollars.
Your job is to implement a method that chooses some players from the scouting
report to form a roster whose total salary is within a required range.

This problem has coding parts and written parts. Submit your code to the
"HW2 Coding" assignment
on Gradescope. Submit your written answers along with the rest of the
problems to the "HW2 Written"
assignment on Gradescope.
AI use is not permitted for this problem.

buildRoster below.

    public static record Player(String name, int salary) { ... }

     *                       Must not be null, and none of the players it
     *                       contains may be null.
     * @param minimumSalary The minimum total salary of the roster in millions
     *                      of dollars. Must be non-negative.
     * @param maximumSalary The maximum total salary of the roster in millions

     *   - minimumSalary <= maximumSalary

    public static List<Player> buildRoster(
        final Player[] scoutingReport,
        final int minimumSalary,
        final int maximumSalary

Notice that the specification places some requirements on the returned
roster, but there can still be multiple allowed return values for a
particular input. Write two implementations (one for Zach, one for James) of
buildRoster, in GeneralManager1.java and GeneralManager2.java, that both
satisfy the specification and, on some allowed input, return different lists.
In a comment within each implementation, briefly describe how that
implementation chooses its rosters.

Write unit tests for both of your implementations of buildRoster, in
GeneralManager1Tests.java and GeneralManager2Tests.java. Your tests
should meet
Lecture 5's coverage standard
and test only allowed inputs. Each test file runs only against your own
implementation, so a test may expect the exact roster your code returns;
parts (d) and (e) take up tests that must pass on any correct
implementation.

Give an example input, one that meets the precondition, where your two
implementations return different lists, and show what each returns.

Consider your example input from part (c). Suppose we want to write a unit
test that calls buildRoster on this input, and we want this unit test to
pass on both of your implementations of buildRoster. (Each class declares
its own Player, so the test builds the same names and salaries for each.)
Explain why this is more challenging than writing a unit test for a single
implementation.

How might we overcome the challenge from part (d) and write a unit test that
will pass on any correct implementation of buildRoster?

In this problem, you will practice proving correctness of code with
conditionals using forward and backward reasoning. Recall from lecture that
we can use assertions (true/false claims at specific program points) to
reason about what is true before and after each line of code.

In this task and the next, fill in each blank by applying the reasoning
rules as lecture gives them. You may simplify a claim, but do not weaken it;
when you do, write the simplified claim on its own line under the original,
as the notes do. You may name a variable's old value as lecture does,
bonus0 for bonus. Treat the arithmetic in the claims as exact.

Task 5 — The Reign Remains the Same

Zach and James's co-GM duties have expanded: they also handle kit orders for
the Seattle Reign's youth academy. Code snippets A and B below both claim to
compute the total cost of ordering one kit (jersey, shorts, socks, etc.) for
every team in the academy, given the price of each piece in a kit; both
order for t = 4 teams. Zach wrote snippet A; James wrote snippet B.
Naturally, neither will admit the other's is also correct.

We will define \(\textsf{cost}(\text{kit})\) to make the invariant more concise.

If kit is empty, then \(\textsf{cost}(\text{kit}) = 0\).

If kit is not empty, then \(\textsf{cost}(\text{kit})\) = the sum of the
  elements of kit.

We will also define \(\textsf{mult}(\text{kit}, t)\).

If kit is empty, then \(\textsf{mult}(\text{kit}, t)\) returns an empty
  array.

If kit is not empty, then \(\textsf{mult}(\text{kit}, t)\) returns each
  element of kit \(\cdot\ t\).

We write kit[i:n] for the elements of kit from index i up to, but not
including, index n; kit[n:n] is empty. Each invariant below says that the
whole equals what is done so far plus what is left: for A the cost of the
full order, and for B the cost of one kit, which B multiplies by t at the
end.

A. (Zach's version)

int zCost = 0;
int t = 4;
int i = 0;
int n = kit.length;
{{ Inv: 0 <= i and i <= n and
        cost(mult(kit0, t)) = zCost + cost(mult(kit[i:n], t)) }}
while (i != n) {

    {{ Q2: ________________________________ }}

    {{ Q1: ________________________________ }}

    {{ Q0: ________________________________ }}
}
{{ zCost = cost(mult(kit0, t)) }}
