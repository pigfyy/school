A specification for a method

  • A method's runs are its calls
  • So its specification says what every call must do
    • As seen from the code that makes the call
  • Client: code that calls a method
    • For example, main is a client of sumList

Client and user

  • A program's user owes it nothing
    • They may type anything at all
    • So the user manual covers every input
  • A method's client can be held to a promise
    • It is code, by a programmer who can read the specification
  • So a method's specification has two parts
    • What it asks of its client, and what it promises in return

Method specification

  • Precondition: an assertion where the method is called
    • The client must make it true
  • Postcondition: an assertion where it returns or throws
    • The implementer must make it true
    • The implementer may assume the precondition

Meeting a specification

A method meets its specification if every call that begins with the precondition true ends with the postcondition true.
  • A call that breaks the precondition: no promise
    • Any value, any exception, or never returning
    • The method still meets its specification

Homework 1 says satisfies where we say meets; the two mean the same.

Assertions become promises

  • The claim at (1): what readList promises
    • About the list it returns
  • The claim at (2) about sum: what sumList promises
    • About the number it returns
  • Preconditions: short
    • readList asks nothing of its client
    • sumList asks only for a list that is not null

A specification in Java

/**
 * Returns the element in the middle of a list.
 *
 * @param list the list to look in; must be non-null
 * @requires list has an odd number of elements
 * @return the element with as many elements before it as after it
 */
static int middle(List<Integer> list) {
    return list.get(list.size() / 2);
}

Writing it in Java

  • Where: just above the method, in a comment starting /**
  • First: a sentence saying what the method does
  • Then: each part of the specification, behind a tag
    • A word starting with @
  • javadoc: turns these comments into web pages
    • Like the pages for ArrayList and Scanner

The six tags

Tag Says Part of the
@param what a parameter is for precondition
@requires a precondition too long for one @param precondition
@return what the method returns postcondition
@throws which exception it throws, and when postcondition
@modifies the parameters the method may change postcondition
@effects how those parameters change postcondition

@requires, @modifies, and @effects are this course's, from Liskov and Guttag.

Procedural abstraction

Procedural abstraction is using a method through its specification alone.
  • Clients: rely on nothing it does not promise
  • Implementer: may change anything it does not promise
  • Abstraction barrier: the specification, as the line between them

The abstraction barrier

  • On one side, main relies on the promises and nothing else
  • On the other, sumList may add up the list from the end
    • Same promises: main needs no change and no new argument
  • A large program is argued correct one method at a time
    • Each against the specifications of the methods it calls

Choosing a specification

  • A method can often have more than one reasonable specification
/**
 * Searches for a value in part of an array.
 *
 * @param a the array to search; must be non-null
 * @param lo the index where the range to search begins
 * @param hi the index just past where the range to search ends
 * @param x the value to search for
 * ... and one of the specifications below ...
 */
static int indexOf(int[] a, int lo, int hi, int x)

Five specifications

Spec Requires Returns If there is no match
A a match a match no promise
B the smallest match -1
C the largest match -1
D some match -1
E the smallest match NoSuchElementException
  • A match: an index i with lo <= i < hi and a[i] == x
  • All five also require 0 <= lo <= hi <= a.length

Four implementations

// Implementation 1
for (int i = lo; i < hi; i++) {
    if (a[i] == x) {
        return i;
    }
}
return -1;
// Implementation 2
for (int i = lo; i < hi; i++) {
    if (a[i] == x) {
        return i;
    }
}
throw new NoSuchElementException();
// Implementation 3
int i = lo;
while (a[i] != x) {
    i++;
}
return i;
// Implementation 4
for (int i = hi - 1; i >= lo; i--) {
    if (a[i] == x) {
        return i;
    }
}
return -1;

Stronger and weaker

  • Stronger, for assertions: P is stronger than Q
    • If Q is true whenever P is
  • Stronger, for specifications: S1 is stronger than S2
    • If every implementation that meets S1 also meets S2
  • Weaker: the reverse; Q is weaker than P, S2 than S1
  • Incomparable: neither stronger nor weaker than the other

Same precondition

B, C, D, and E share one, so we compare only their postconditions:

  • B and C are each stronger than D
    • The smallest or largest match is in particular some match
  • B and C are incomparable
    • On an array with x twice, the smallest and largest differ
  • E is incomparable with B, C, and D
    • Where x is absent, they promise -1 and E an exception

A asks more

  • Where x occurs, A and D promise the same: a match
  • Where x does not, a call breaks A's precondition
    • A promises nothing about that call
  • An implementation that meets D handles every call
    • So it meets A too: D is stronger than A

The rule

S1 is stronger than S2 when S1's precondition is weaker than or the same as S2's, and, on every call where S2's precondition is true, S1's postcondition is stronger than or the same as S2's.
  • So each of B, C, D, and E is stronger than A

All five compared

A B C D E
A X W W W W
B S X --- S ---

D S W W X ---
E S --- --- --- X

The row against the column: S stronger, W weaker, --- incomparable.

Which is better?

  • Stronger: promises the client more
    • B obliges indexOf to find the first match
  • Weaker: leaves the implementer more choices
    • D lets indexOf search from either end
    • Each choice is a case the client must handle
A good specification rules out exactly the implementations its clients cannot use.

Changing a specification

Change Cannot break Can break
Strengthening a client the implementation
Weakening the implementation a client
  • Strengthening keeps every promise a client relied on
  • Weakening makes no promise the old specification did not
  • With only your own code as clients, fix both sides at once
  • With a thousand clients, a specification can only grow stronger

Writing a client

A client is correct if it works with every implementation that meets the specifications it relies on.
  • Working with the implementation it happens to run with is not enough

Is count correct?

static int count(int[] a, int x) {
    int c = 0;
    int i = indexOf(a, 0, a.length, x);
    while (i != -1) {
        c++;
        i = indexOf(a, i + 1, a.length, x);
    }
    return c;
}

Does x occur?

indexOf(a, 0, a.length, x) != -1
  • B, C, and D promise -1 exactly when x is absent: correct
  • A: when x is absent, the call breaks A's precondition
  • E: the same call throws where the client expects -1

Knowing a program in pieces

  • One method at a time: each meets its own specification
    • The specifications of what it calls stand in for their code
  • Each client: works with every implementation the specifications allow
  • What procedural abstraction is for:
    • No one has to hold the whole program in their head
    • Clients stay as they are when a rewrite keeps the promises
