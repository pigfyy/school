Two programs

program. The server kept the "book", the messages visitors had
posted. On every request it built the whole page from the book
and sent the page as text. The browser drew what it was sent.
Every change you saw on the page was a new page from the server.

In the first guestbook, a post was POST /, and the server
answered it with a whole new page. Here the post goes to
/api/messages, the path the program asked for the messages on,
and the server sends no page back. The page you are looking at is
still the one the browser drew at the start, and the program
changed it in place. That is the point of moving the work into the
browser: the page can change without the server sending it again,
so a message appears as soon as the server answers.

That raises three questions. How does a program change a page
the browser has already drawn? What does the program do while
the server is slow to answer? And what does the program in the
browser know about the server?

The page is a tree

What the server sent on the first request was a string of
characters, index.html as it is on the disk. But look at what
the tags do. A tag opens, holds other tags, and closes: the
<body> holds the heading, the list, the two boxes, the button,
and the script. The browser reads the string and builds a tree
from it, one node per tag, each tag's children under it. Then it
draws the page on the screen from the tree: the heading in large
type, the boxes, the button. An id is a name given to a tag so
that a program can find it. Here is the tree for this page,
beside the page as the browser draws it. A line joins each node to
what it draws, and the nodes the program looks up are labeled by
their id:

Definition: DOM

The DOM (Document Object Model) is the page as the browser
keeps it: a tree with one node per tag, that a program in the
browser can read and change. When the tree changes, the
browser redraws the page from it.

A web page, then, is a data structure, a tree like the ones you
built in the intro courses. Like any data structure, a program can
inspect it and change it. You can be that program. Your browser
has a console, in its developer tools, where you type a line
of JavaScript and the browser runs it in the current tab. In
Chrome it is in the menu under More tools › Developer
tools, on the Console tab, or press
Ctrl+Shift+J
(Option+Command+J on a Mac).
Here are two lines typed into the console on the guestbook page,
each followed by what the console printed back:

> document.getElementById("messages")
<ul id="messages">…</ul>

> document.getElementById("messages").innerHTML = "<li>hi</li>"
'<li>hi</li>'

document is the tree, and getElementById searches it for the
node whose id is the string given. So the first line finds the
list, the <ul> with the id messages, and the console prints
it. In Chrome, hovering over what it printed highlights the list
on the page: that is the node. The second line changes the node.
innerHTML is the HTML inside a node, and setting it replaces
the node's children with what the string says, one <li> here.
The page now shows hi in the list. The terminal running the
server prints nothing, since no request was sent. The tree
changed, and the browser redrew the page from it.

Nothing stops you doing this on any page. Open the console on a
newspaper's front page, find the headline's node, and set its
innerHTML to what you like, and the page reads as you wrote
it. The change is in your browser's tree and nowhere else. The
newspaper has not changed, and nobody else sees it.

app.js does to the tree what you just did, from a function.

16// Puts the messages on the page, one list item each, in place of
// whatever the list held before.
function show(messages) {
  const list = document.getElementById("messages");
  list.innerHTML = "";
  for (const message of messages) {
    const item = document.createElement("li");
    item.textContent = message;
    list.appendChild(item);
  }
}

The function is handed a list of messages. It finds the list node,
as the console did, and empties it. Then, for each message, it
makes a new <li> node, sets the node's text to the message, and
adds the node to the list as its last child. Until that last step
the new node is in no tree. In the first guestbook the server
wrote one <li> per message into the page's text. Now the program
in the browser makes one <li> node per message in the page's
tree, and the browser redraws.

If you know Java, you can read this. A few spellings differ.
function starts a function, with no return type and no types on
its parameters. const declares a variable that will not be
reassigned, where Java would name a type. The for loop says of
where Java's says :. What the code does is nothing new.

One line of show deserves a second look. Line 13 sets
textContent, where the console set innerHTML. Setting
innerHTML parses the string as HTML. A message of <b>hi</b>
would come out as hi in bold. A message holding an <img> tag
with an onerror attribute could run code in every visitor's
browser. That is the cross-site scripting hole the first guestbook
had, which
its second exercise
closed by escaping the message on the server. Setting
textContent puts the characters in the tree as text, so a tag in
a message shows as the characters typed, and nothing is parsed. As
long as the program sets text and not HTML, the escaping comes
for free.

Asking the server

show is handed the messages, and nothing in it says where they
come from. The second piece of app.js asks the server for them:

async function load() {
  const response = await fetch("/api/messages");
  const messages = await response.json();
  show(messages);

fetch is a function the browser provides. Given a path, it sends
a request for that path to the server the page came from: here
GET /api/messages, the third request the server's terminal
printed.
The server does not answer this path with a page. It answers with
the messages as data, in a form the program can read. Here is the
answer, as curl shows it, after ada's post:

$ curl http://localhost:9331/api/messages
["ada: hello"]

Definition: JSON

JSON (JavaScript Object Notation) is a way of writing a
value as text: a list in square brackets, a string in double
quotes, and so on. Text in that form can travel between
programs, in any languages, and each reads it back as a value
in its own language.

Line 21 of load reads the response's body as JSON:
response.json() turns the text ["ada: hello"] into a list
with one string in it. Line 22 hands the list to show, which
draws it. That is how the messages got onto a page that held
none. The program asked for them as data, and put them in the
tree itself.

What fetch returns

load has two words you have not seen before: async before
function on line 19, and await before fetch and
response.json() on lines 20 and 21. To see what they do, here
is the console again, on the page with ada's message posted,
doing what load does one line at a time. (The console also
prints undefined after the const line, as it does after any
declaration. The session leaves that out, and cuts the response's
line to its status.)

> fetch("/api/messages")
Promise {<pending>}

> const response = await fetch("/api/messages")

> response
Response {status: 200, …}

> await response.json()
['ada: hello']

The first line is the surprise. fetch does not return the
response. It returns at once, before any response has come back,
and what it hands back is a promise, marked pending.

Definition: promise

A promise is a value that stands for a result that may
not have arrived yet. await, written before a promise, waits
until the result arrives and then gives the result itself.
Inside a function, await is allowed only if the function is
declared async.

The second line of the session awaits the promise and gets the
response: a value with a status, 200 here, and a body. Reading the
body is slow too, since the body may still be arriving over the
network. So response.json() returns a promise as well, and a
second await gives the list. That is why load has two
awaits: one for the response to arrive, and one for its body to
be read.

Why would a language want this? A request to a server can take a
long time, and while the browser waits, the user is still there.
They can click a button, scroll, resize the window. A program
that stopped dead at every fetch would stop the page with it.
So fetch does not stop. It starts the request and returns a
promise, and await says: pause this function here, let the
browser do whatever else is ready, and come back when the result
arrives. What "pause" means is the hardest idea in the lecture,
so it has a section below. First, the rule in the box's
last sentence.

Suppose you remember to await fetch and response.json(), and you
write load that way, but leave off the word before function:

3
4
5

7function load() {
  const response = await fetch("/api/messages");
  const messages = await response.json();
  show(messages);
}

The browser refuses to run the file, with an error in the console:

Uncaught SyntaxError: await is only valid in async functions and the top level bodies of modules

Not only load fails. The browser reads the whole file before
running any of it, and refuses app.js as a whole, so nothing
in it runs: the list stays empty and the button does nothing.
For this course, the rule is that a function that uses await
is declared async, as load is on line 19. (The console is
looser. The session above awaited outside any function, and the
console allowed it. The rule is for code you write and turn in.)

One more thing the session shows. A response has a status, and
200 means the request was understood and answered. A server can
answer with other statuses, such as 404 for a path it does not
have. A request can also get no answer at all, if the server is
down. Each of those is a different kind of failure, and a program
that talks to a server has to decide what to do for each: tell the
user the server cannot be reached, or that the thing they asked
for is gone, or something else again.

37// Sends the name and message typed in, and shows what comes back.
async function post() {
  const fields = new URLSearchParams();
  fields.append("name", document.getElementById("name").value);
  fields.append("message", document.getElementById("message").value);
  const response = await fetch("/api/messages", {
    method: "POST",
    body: fields,
  });
  const messages = await response.json();
  show(messages);
  document.getElementById("message").value = "";
}

Lines 27 to 29 build the fields. A URLSearchParams is a map from
names to strings, and .value on an input's node is whatever the
user has typed in the box. Line 30 is fetch again, with a second
argument the GET did not need. The argument is an object, written
in braces as names and values, and it says that the method is POST
and the body is the fields. The browser sends the fields encoded
as the first guestbook's form sent them, name=ada&message=hello,
so the server reads the body with the same parseForm. The server
answers a POST with the messages, the new one included, so lines
34 and 35 are load's last two lines: read the JSON, draw the
list. Line 36 empties the message box. load and post are both
async, since each has an await in it. show is an
ordinary function.

Then the last two lines of the file, which run once, when the
browser first runs the program:

Line 39 connects the button to post. It finds the button's node
and sets its onclick to the function post. There are no

From then on, a click on the button is an event, and post is
what the browser runs for it. The button is in no form, so without
this line a click would do nothing. Line 40 calls load once.
After that, nothing in the program runs until an event.

One more thing to try. Post a message, then press the browser's

The page came from a GET, so refresh asks for the page again,
then the program, then the messages. The message is still there,
since the server has it.

One thing at a time

Here is an experiment. Change the server so that it waits ten
seconds, with Thread.sleep, before it answers a request to
/api/messages. (Java makes you put that call in a try block.)
Start the server again. A visit now shows the page at once, with
an empty list, and the messages arrive ten seconds later. And
during those ten seconds, while load is waiting at line 20 for
its response, you can type a name and a message and press Post.
post runs and sends the POST at once. The server's terminal
prints POST /api/messages only when the ten seconds are up,
since this server handles one request at a time.

The browser runs your program on one thread, so it never runs two
of its functions at once: JavaScript runs one thing at a time. Yet
while load is waiting, a click runs post. How can both
be true?

The answer starts from something you saw in the first guestbook.
Its server has no loop in it.
Its main makes an HttpServer, hands it handle, starts it,
and returns. The program keeps running because the loop is inside
HttpServer: wait for a request, call handle, wait again. Now
look at app.js. Its one loop is the for in show, which only
makes list items. Nothing in the file waits for a click. And yet a
click runs post. So the browser has a loop of the same kind.

Definition: event loop

The browser runs a program in the page from an event
loop: wait for an event, run the function registered for
it, and wait again. A click is an event. A response arriving
is an event. The function the loop runs for an event is its
callback.

That is one half of the answer: the browser runs a loop, and
post is the callback the loop runs for a click. The other half
is what await does. When load reaches the await on line 20,
it sends the request, and then it stops. Stopping means returning:
load returns to whoever called it, with its place marked so that
it can go on from line 21 later. What it returns is a promise, as
every async function returns one, and line 40 ignores it. Line
40 is the last line of the file, so the browser is then back at
the loop, and the loop runs whatever is ready next, a click's
post among them. When the response arrives, that is an event
too, and its callback is the rest of load, from line 21 on.

So await cuts a function in two. The part before the await
runs now, and then hands the browser back to the loop. The part
after runs later, as a callback, when the promise's result
arrives. Between the halves, the loop runs what else is ready. A
function with two awaits is cut twice: load runs in three
pieces, and so does post. Here is one run of the slowed server,
with time running left to right. The figure draws each function's
last two pieces as one box, since in this run nothing else was
ready between them:

The page loads, and line 40 calls load. It runs to its
   await on line 20, sends GET /api/messages, and hands the
   browser back. Its request is out.

Post is clicked, while the server is still asleep. The loop
   runs the click's callback, post, which runs to its own
   await on line 30, sends the POST, and hands the browser
   back. Now two requests are out, and nothing is running.

load's response arrives. The loop runs the rest of load:
   line 21 reads the body, and line 22 draws the list.

post's response arrives, and the loop runs the rest of
   post, which draws the list again, now with the new message.

Read the row of boxes first. The loop runs one box at a time, left
to right, and never two at once. That is what "one thing at a
time" means. Now read the dashed lines. The two waits overlap, and
during them nothing is running at all. That is why the browser is
never stuck on the network. Only one of your functions is ever
running. Any number of them may be set aside waiting for a
promise, and each comes back in the middle of itself after other
code has run.

Three things follow from the picture.

Where does control go at an await? Back to whoever called
  the function, which for a callback is the browser's event loop,
  and from there to whatever event is next: a click, a resize,
  another function's response arriving. You do not know which.
  You only know where your function will resume: at the await,
  which then gives the promise's result.

What changed while you were away? Anything the code that
  ran in between could change: a global, a field, the page's
  tree. Before an await, your function is the only JavaScript
  running, and nothing changes unless it changes it. After one,
  that is no longer true.

How is the pausing done? From JavaScript you cannot see
  how, and you do not need to. The language promises only that
  the function resumes after the await with the promise's result.

Last, and most important: the figure shows one possible run. Had
the server been quick, load would have finished before anyone
clicked, and the row would be load's two boxes and then
post's. Had post's response arrived first, the rest of post
would have run before the rest of load. The events come in
whatever order the user and the network give them, and each order
is another run, with the boxes in another order. In practice the
responses come fast, so the program only feels sequential. A test
that posts a message and sees it on the page has confirmed one
order and says nothing about the rest.

Definition: concurrency

A program is concurrent when more than one task is in
progress at once and the order of their steps is not the
program's to choose. In the browser the steps are large:
one callback runs at a time, and a function gives up its
turn only at an await.

This changes what a claim about the program is about. Until now a
run was fixed by its input. Now a run is fixed by its input and by
the order its events come in, so a description of what the program
does is a claim about every order. You have met this before,
with a class. Its methods may be called in any order, so you
wrote a
representation invariant,
a claim about its fields that is true whenever no method is
running, which every method may assume when called and must make
true again before it returns. A function in the page is cut at
each await, and
between any two of its pieces any other callback may run. So an
await is a method boundary in disguise. Treat it as one: make
the invariant true before it, and assume only the invariant after
it. The invariant is about what another callback can reach: a
global, an object both can see, the page's tree. Your function's
own locals are still yours, since no other callback can
reach them.

Who is the client?

The guestbook is now two programs, and a request is one program
calling the other. For the request load sends, the program in
the browser is the client. It calls the server as code calls a
method, with a request in place of a call and a response in place
of a return value, and it relies on what the server promises. The
server is the implementation. And the specification between
them is
the server's manual,
the comment at the top of Guestbook.java:

The first change is that the server no longer builds a page. For
/, it reads index.html from the disk and sends the bytes as
they are, with the status 200 and the type text/html. For
/app.js it does the same with the program's file. That is how
servers send files: read the bytes, send the bytes. So the
browser's first two requests get the page and the program, each
exactly as it sits on the disk in the directory the server runs
in. The third
path is for the program. On /api/messages, a POST adds the
message first, reading the fields with parseForm as the first
guestbook did. Then POST and GET alike get the book's messages as
JSON. So post in the browser can redraw from the answer without
asking again. Any other path gets 404, the icon's among them. The
first guestbook sent the page to every path.

The JSON is written by hand, in json:

95    /** @return the strings as a JSON array, each in double quotes */
    private static String json(List<String> strings) {
        List<String> quoted = new ArrayList<String>();
        for (String s : strings) {
            quoted.add("\"" + s.replace("\\", "\\\\")
                .replace("\"", "\\\"").replace("\n", "\\n") + "\"");
        }
        return "[" + String.join(", ", quoted) + "]";
    }

Each message goes in double quotes, with three characters escaped:
a backslash, a quote, and a newline. The strings are joined with
commas inside square
brackets. In practice a library writes the JSON, from any value
and not only a list of strings.

What does the client know about the server? Only the manual.
It never sees the book or the server's code. It sends a request
and gets back text. So the manual is the server's
specification, and app.js relies on it as a caller relies on
a method's specification.

Read line 18 again. It promises the messages posted so far, as
JSON. It does not say that the JSON is a list, that each
element is a string, or that a string is a name, a colon, and
the message. The server does all three, in json and in
Book, but the manual promises none of it. So show relies on
what the server does, not on what the manual promises. The
manual is at fault: a specification of a method that returns
JSON has to say what the JSON looks like, and this one leaves
the shape open.

Suppose the server's author changes the JSON to a list of objects,
each with a name field and a message field. The server still
satisfies the manual, since the messages still come back as JSON.
In Java a change like that is a change to a return type, and a
caller that used the old type stops compiling. Here no compiler
sees both programs. The new server runs, the old app.js runs,
and show puts [object Object] in every list item, since that
is what an object becomes as text. Web systems often break this
way: the specification leaves something open, the clients rely on
what the server happened to send, and then the server changes it.

A good manual promises the shape. Then a client that relies on
the shape relies on the specification alone. A change to the
shape is then a change to the specification, and the server's
author knows the clients have to change too. Many teams that
build web systems write that promise in a form a tool can check,
called a schema.

Exercises

Each answer is folded under its question. Write yours first.

1. Write the sentence the manual should have about the JSON,
so that show relies on a promise and not on what the server
happens to send.

Answer

The sentence. After line 20:

The messages are a JSON list of strings, oldest first, each
the poster's name, a colon, a space, and the message.

What relies on it. Line 21 of app.js relies on the body
  being JSON. The for on line 11 relies on it being a list. Line
  13 relies on each element being a string, since it puts the
  element in the page as text. The order the list comes in is the
  order the page shows, so the sentence promises that too.

Who it binds. With the sentence in the manual, a change to
  the JSON's shape is a change to the specification, and the
  server's author knows to change the client with it. Without it,
  the client relies on what the server happens to send, and the
  server's author can change that without breaking the manual.

2. In the figure, the server handled load's GET before
post's POST, and the responses reached the browser in that
order. Suppose the server handled them in the same order, but
load's response was slow on the network and reached the browser
after post's. List the boxes the event loop runs, in order,
and say what the page shows at the end.

Answer

The boxes. load to its await; post to its await;
  the rest of post; the rest of load.

The page. post's response holds the new message, since the
  server added it before answering, so the rest of post draws a
  list with the message in it. load's response was built from
  the book as it stood when the server handled the GET, before the
  message was added. So the rest of load then draws a list
  without it. The page ends with the message gone from the list,
  though the book has it, until something calls load again.

The lesson. Nothing in load is wrong on its own, and
  nothing in post is. The run that goes wrong is one order of
  the same events. A test that posts and sees the message on the
  page confirms its run; another order is another run the test
  never saw.

3. Take the word async off line 19 of app.js, reload the
page, and press Post. What happens, and why does the button
do nothing?

Answer

What happens. The console shows the error from the section
  on what fetch returns, the list stays empty, and the button
  does nothing.

Why. The browser reads the whole file before running any of
  it, and an await outside an async function is a syntax
  error, so it refuses the whole file. Line 39, which gives the
  button its callback, never ran, so a click is an event with no
  callback. Line 40 never ran either, so the list is empty.
