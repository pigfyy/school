Lecture 11 · Fri Oct 23

Room in the table, nowhere to go

Slide 29 inserts 76, 40, 48, 5, 55 and 47 into a table of size 7 with quadratic probing. After five inserts, two slots are still empty. Where does 47 go?

Nowhere. 47 % 7 = 5, and quadratic probing tries \(5 + i^2\): indices 5, 6, 2, 0, 0, 2, 6, … The empty slots are 1 and 4, and \(i^2 \bmod 7\) is only ever 0, 1, 2 or 4, so the probe path never reaches them. Slide 30's guarantee needs a prime table size and \(\lambda < \frac12\). Here \(\lambda = \frac57\). Fixing that is rehashing.

Lecture 9 · slides 3–30 · Mon Oct 19 · Weiss 4.4

AVL insert, start to finish

Slides 3–27 repeat Friday's material: the balance rule, the slide-32 and slide-39 inserts, the two single rotations, and the double rotations. Week 3's pages cover them in detail. Here is the summary, then the new example.

Insert summary (slide 27). Do a BST insert, then update the heights of the new node's ancestors, from the leaf up. At the deepest unbalanced node:

  • LL (left subtree of the left child): rotate right.
  • RR (right subtree of the right child): rotate left.
  • LR (right subtree of the left child): rotate left at the left child, then right at the node.
  • RL (left subtree of the right child): rotate right at the right child, then left at the node.

Done after reaching the root or applying one case.

Insert 1, 2, 5, 3, 4 (slides 28–29)

Inserting 5 makes 1 unbalanced: right, then right, so RR and a left rotation at 1, giving 2 with children 1 and 5. Then 3 goes to 5's left, which is fine. Then 4 goes to 3's right, and 5 is unbalanced: from 5 the key went left (to 3), then right. That's LR: rotate left at 3, then right at 5. The slide's three arrows are exactly these three rotations. Result: 2 with children 1 and 4; 4 with children 3 and 5.

// slide 30
insertHelper(key, value, root) {
  if (root == null) return new Node(key, value);
  if (root.key < key) root.right = insertHelper(key, value, root.right);
  else root.left = insertHelper(key, value, root.left);
  if (isUnbalanced(root)) root = rotate(root);
  return root;
}

The recursion unwinds from the new leaf up, so the first unbalanced node it meets is the deepest one.

Quick check: when 4 is inserted, which case applies at 5?

Quick check: how many single rotations does the whole sequence 1, 2, 5, 3, 4 take?

Teaching notes
  • Ask the room to do 1, 2, 5, 3, 4 on paper first (slide 28 has no answers), then step through it. Most people stop after the first rotation and miss that 4 creates a zig-zag.
  • Recall the definition of height for the class: a leaf is 0, an empty subtree −1. Heights are what the code stores and compares.

Lecture 9 · slides 31–35 · Mon Oct 19

Minimal AVL trees

Slide 31 asks: for an AVL tree of height \(h\), what is the minimum number of nodes? With \(h = 0\) it's 1 node; with \(h = 1\) it's 2. In general, take a root, give it one subtree of height \(h - 1\) (it needs one to reach height \(h\)), and make the other as short as the balance rule allows, height \(h - 2\). Both subtrees should themselves be minimal.

\[M(h) = M(h-1) + M(h-2) + 1,\qquad M(0) = 1,\ M(1) = 2.\]

\(h\)012345678910
\(M(h)\)12471220335488143232

Why \(\Theta(\log n)\) (slides 34–35). \(M(h) > F(h)\), the Fibonacci numbers, and \(F(h) \approx \phi^h\) with \(\phi > 1.6\). So an AVL tree of height \(h\) has at least \(\phi^h\) nodes, and at most \(2^{h+1} - 1\). With \(n\) nodes, \(n \ge \phi^h\) gives \(h \le \log_\phi n\): every operation is \(O(\log n)\), and \(\Omega(\log n)\) because even a full tree is that tall.

Quick check: \(M(6)\).

Quick check: the greatest height an AVL tree with 100 nodes can have.

Teaching notes
  • Slide 33 draws the minimal trees without keys. Have students check each one: every node's subtrees differ by exactly 1 or are both empty. Removing any leaf would either shrink the height or break the balance.
  • "Greatest height with \(n\) nodes" = the largest \(h\) with \(M(h) \le n\). For 100 nodes, \(M(8) = 88 \le 100 < 143 = M(9)\), so 8. A full tree with 100 nodes has height 6.

From arrays to hash tables

Dictionary data structure (slide 7)insertfinddelete
Sorted array\(\Theta(n)\)\(\Theta(\log n)\)\(\Theta(n)\)
Binary search tree\(\Theta(\text{height})\)\(\Theta(\text{height})\)\(\Theta(\text{height})\)
AVL tree\(\Theta(\log n)\)\(\Theta(\log n)\)\(\Theta(\log n)\)
Hash table (worst case)\(\Theta(n)\)\(\Theta(n)\)\(\Theta(n)\)
Hash table (average)\(\Theta(1)\)\(\Theta(1)\)\(\Theta(1)\)

The AVL tree is an ordered dictionary: keys must be comparable. A hash table is unordered: instead of comparing keys, each key has a hash function (slide 8). AVL delete is "not covered this quarter" (slide 5); Java's TreeMap uses a red-black tree, a cousin with a more relaxed shape (slide 6).

A "really big array" (slides 9–10). Treat each key as a number and give it its own index: arr[key] = value. Every operation is \(\Theta(1)\). The problem: the array has to be as big as the range of keys.

Hash tables (slide 11). Use a small array. A hash function turns the key into an integer, and it should "scatter" the keys as if assigning them randomly. Store the key and value at hash % table.length. When two keys land on the same index, that's a collision, and we need a collision-resolution strategy.

Caller ID (slide 12). Key: a phone number as a string. Hash: the number as an integer, \(h(\text{"2068675309"}) = 2068675309\). With table size 10 it goes to index \(2068675309 \bmod 10 = 9\).

What influences running time (slide 13): how long hashing takes; how likely collisions are (the hash function's quality, and the array size compared to the number of values); and what we do on a collision.

Keys that are objects (slide 14). Equal objects must hash the same: if a.equals(b), then a.hashCode() == b.hashCode(). If you override equals(), override hashCode() consistently too.

Quick check: with table size 7 instead of 10, at what index does "2068675309" go?

Quick check: you override equals on Point so points with the same x and y are equal, but keep Object's hashCode. What goes wrong in a hash table?

Teaching notes
  • Ask the room for the problems with the really big array before slide 11: memory for every possible key, and keys that aren't small integers at all.
  • Average \(\Theta(1)\) versus worst \(\Theta(n)\): the worst case is every key colliding. The rest of the two lectures is about making that unlikely and cheap.

Lecture 10 · slides 15–20 · Wed Oct 21

Good hash functions

Properties of a "good" hash function (slide 15). It maps objects to integers and is:

  • Consistent: equal keys hash to the same integer; hashing the same key twice gives the same result (deterministic).
  • Uniform: it can use every index of a fixed-size array, at roughly equal rates.
  • Effective: it's hard to find two unequal keys with the same hash; a small change to the key gives a big change in the hash (the "avalanche effect").
  • Efficient: it's fast to compute.

A bad one (slides 16–17): the first digit of a phone number. Consistent, yes. Uniform, no: no US number starts with 0 or 1, and in this class 2 is by far the most likely. Effective, no: \(h(\text{"2068675309"}) = h(\text{"2068675305"}) = 2\). Efficient, yes.

Four hashes for strings (slides 18–19)

For \(s = s_0 s_1 \dots s_{m-1}\) with ASCII codes \(a(s_i)\):

HashProperties (slide 19)
\(h_1(s) = a(s_0)\)consistent, efficient
\(h_2(s) = \sum_{i=0}^{m-1} a(s_i)\)consistent, efficient, possibly uniform
\(h_3(s) = \sum_{i=0}^{m-1} a(s_i)\cdot 31^i\)consistent, efficient, uniform, effective
\(h_4(s) = 2\cdot\sum_{i=0}^{m-1} a(s_i)\cdot 31^i\)consistent, efficient, effective

\(h_2\) gives every anagram the same hash ("cat" and "act"). \(h_4\) is always even, so with an even table size it never uses an odd index: not uniform.

Exact integers. Java's int would wrap around for long strings; the indices here use the true values.

Computing \(h_3\) quickly (slide 20). Don't call Math.pow. For \(m = 4\), \(h_3 = s_0 + 31(s_1 + 31(s_2 + 31\cdot s_3))\), which is a loop from the last character down:

for (i = m-1; i >= 0; i--) {
  h = 31*h + s[i];
}

Quick check: \(h_2(\text{"cat"})\), with c = 99, a = 97, t = 116.

Quick check: which property does \(h_4\) lose compared with \(h_3\)?

Teaching notes
  • Type "cat" then "act" in the calculator: \(h_1\) and \(h_3\) differ, \(h_2\) doesn't. Then set the table size to 10 and look at \(h_4\)'s index column.
  • Why 31: an odd prime, so multiplying spreads bits without losing them. The slides don't dwell on it; Java's String.hashCode uses the same polynomial, highest power first.

Lecture 10 · slides 21–30 · Wed Oct 21

Separate chaining

The ideal insert just does arr[h % table.length] = (key, value), but two different keys can map to the same index: a collision (slide 21). Two strategies (slide 22): separate chaining, where each index holds a secondary data structure such as a linked list, and open addressing, where we use a different spot in the table (Friday).

Separate chaining (slides 23–25). Compute \(i = h(k) \bmod \text{table.length}\), then call insert, find or delete on the structure at table[i]. (Insert checks for the key first: no duplicates.)

Load factor (slides 26–30)

The load factor \(\lambda = \frac{n}{\text{length}}\) is the average number of items per bucket. With a linked list per bucket, an unsuccessful find expects \(\lambda\) comparisons (it scans the whole bucket), and a successful find expects \(\frac{\lambda}{2}\). To keep the expected time \(\Theta(1)\), pick a constant and resize the array whenever \(\lambda\) exceeds it.

Slides 28–30 draw three tables of length 10 holding 3, 8 and 15 items: \(\lambda = 0.3\), \(0.8\) and \(1.5\). A load factor above 1 is fine for chaining.

Quick check: after inserting 12, 22, 7, 42, 5, 17 into the size-10 table, what is \(\lambda\)?

Quick check: with \(\lambda = 1.5\), how many comparisons does a successful find expect?

Teaching notes
  • The size-7 preset shows why the average-case claim needs a good hash: 10, 24, 3, 17 and 31 all leave remainder 3. \(\lambda = 1\), but finding 31 takes 5 comparisons.
  • The buckets don't have to be lists. With an AVL tree per bucket, operations cost what the tree costs (Lecture 11, slide 33).

Section 4: AVL trees

The section reviews the AVL properties, names the four rotation cases on one picture, and plants two full trees. Everything below follows the section slides and the worksheet's official solutions.

AVL tree: a BST (order property) where every node has at most 2 children and its subtrees' heights differ by at most 1 (structural property). Find, insert and delete are \(O(\log n)\), against \(O(h)\) for an unbalanced BST.

Problem 0: the ABCs

Keys must be comparable; values can be any type. An AVL tree beats a HashMap when you need order: iterating keys in sorted order, or finding the next and previous key (EX4 uses this). It beats a plain BST when the input might be sorted, because balancing prevents the degenerate chain.

Section 4: practice

The worksheet's problems, answerable here and checked against the official solutions. The trees were also built by running the lecture's AVL insert (checks/cse332/w04/verify.mjs).

1. Problem 0: the ABCs of AVL trees

What are the constraints on the types you can store in an AVL tree? When is an AVL tree preferred over a HashMap?

  1. What does an AVL tree do with keys that a hash table never does?
  1. Keys must be comparable, because every operation compares them. Values can be anything, as in any dictionary.
  2. An AVL tree keeps keys in order: you can iterate in sorted order, or find the next or previous key, cheaply. A hash table scatters them.
  3. Keys comparable; values any type; prefer an AVL tree when you need sorted order (iteration, next/previous key), and over a plain BST when input may be sorted.

2. Problem 1: left rotation references

\(p\) is \(a\)'s left child and the lowest problem node; the insert went into \(Z\) (the right subtree of \(p\)'s right child \(c\)). Rotate left at \(p\). What does each reference become?

  1. After the rotation, \(c\) is where \(p\) was, \(p\) is \(c\)'s left child, and \(Y\) (keys between \(p\) and \(c\)) needs a new parent.
  1. \(c\) replaces \(p\) under \(a\): a.left = c.
  2. \(Y\) = c.left moves to p.right (it holds keys greater than \(p\), less than \(c\)).
  3. \(p\) becomes \(c\)'s left: c.left = p. Then update the heights of \(p\) and \(c\).
  4. a.left = c; p.right = c.left; c.left = p.

3. Problem 2: let's plant an AVL tree

Insert 10, 4, 5, 8, 9, 6, 11, 3, 2, 1, 14 into an empty AVL tree.

  1. After 10, 4, 5 the tree is 5(4, 10). Keep a running drawing with heights.
  2. Rotations happen on inserting 5, 9, 6, 11, 2 and 1.
  1. 5: LR at 10 → 5(4, 10). 8: no rotation. 9: LR at 10 → 5(4, 9(8, 10)).
  2. 6: 5 is unbalanced; the key went right (9) then left (8): RL → 8(5(4, 6), 9(, 10)).
  3. 11: RR at 9 → 10(9, 11) under 8. 3: no rotation. 2: LL at 4 → 3(2, 4). 1: LL at 5 → 3(2(1), 5(4, 6)). 14: no rotation.
  4. LR; RL; 6; 8 3 2 1 5 4 6 10 9 11 14 (root 8, height 3), as in the official solution.

4. Problem 3: MinAVL trees

Draw an AVL tree of height 4 with the minimum possible number of nodes.

  1. Root, a minimal tree of height 3 on one side, a minimal tree of height 2 on the other.

Open addressing: linear probing

Linear probing (slides 17–20). On a collision, use the next open space. Insert tries \(i = h(k) \bmod \text{length}\), then \((i+1)\), \((i+2)\), \((i+3)\), …, all mod the length. Find follows the same path until it finds \(k\) or reaches an empty cell.

Delete is hard (slides 21–24)

Insert A, B, C, D, E, all mapping to 3: they fill 3–7. Simply emptying B's slot breaks finds for C, D and E, because a find would stop at the hole. Slide 21 fills the hole by sliding C, D, E down. But slide 22 (A, B, E map to 3; C, D to 5) can't move C or D into index 4: that's before their home, so only E moves. Slide 23 shows wrap-around: with A, B, E mapping to 8 and C, D to 0, E moves from 2 up to 9.

Option 1 (harder): plug the hole with a later key whose probe path passes the hole, and repeat from where that key was. Option 2 (easier): tombstones. Leave a marker meaning "something was deleted here". A find doesn't stop at a tombstone; an insert may reuse the first tombstone it passed (slides 25–26).

Downsides (slide 27). As \(\lambda\) approaches 1, contiguous blocks grow; any collision with a block makes it bigger, and bigger blocks get more collisions. That feedback loop is primary clustering. And \(\lambda\) can't exceed 1: there's nowhere left to put anything.

Quick check: a find reaches a tombstone. What does it do?

Quadratic probing (slide 28). Try \(i = h(k)\), then \((i + 1^2)\), \((i + 2^2)\), \((i + 3^2)\), \((i + 4^2)\), …, all mod the length.

Using quadratic probing (slide 30). After table.length probes, the indices repeat. If table.length is prime and \(\lambda < \frac12\), you're guaranteed to find an open spot within table.length/2 probes. It helps with linear probing's clustering, but not when many keys hash to the same index.

Secondary clustering (slide 31). Quadratic probing jumps \(i^2\) away, so it doesn't grow big blobs (no primary clustering). But two keys that start at the same index follow exactly the same probe sequence. That's secondary clustering, and a probe that depends on the key avoids it:

Double hashing (slide 32). With two good hash functions \(h\) and \(g\): try \(i = h(k)\), then \(i + g(k)\), \(i + 2g(k)\), \(i + 3g(k)\), …, mod the length.

The slides leave \(g\) open. This widget uses \(g(k) = 7 - (k \bmod 7)\), which is never 0.

Lecture 11 · slides 33–35 · Fri Oct 23

Rehashing, and the summary

Rehashing (slide 34). When \(\lambda\) gets too large, make a new array roughly twice as long (probably still prime) and re-insert every item by applying the hash function again: items map to different indices in the new table. "Too large" means about \(\lambda < 2\) for separate chaining, and \(\lambda < \frac12\) for open addressing.

Summary so far (slide 33). Separate chaining is easy: with unsorted linked lists, find, insert and delete are proportional to the load factor on average; with another structure per bucket (say an AVL tree) they cost what that structure costs. Open addressing uses probing and has clustering issues as the table fills. Why use it? Less memory allocation (no list nodes), which can make it faster, and a simpler data representation.

Final word (slide 35). The hash table is one of the most important data structures: efficient find, insert and delete, but operations based on sorted order are not efficient. Use a good hash function (good distribution, uses enough of the key, cheap to compute) and keep the table a good size (prime; the preferred \(\lambda\) depends on the type of table). Hash functions have uses beyond tables, such as cryptography and checksums.

Quick check: an open-addressing table of size 7 needs rehashing. With "roughly double, and prime", what is the new size? (Take the first prime at least \(2 \times 7\).)

Quick check: when rehashing, why not copy each item to the same index in the new array?

Week 4 cheat sheet

Print with Ctrl+P; only this page prints.

AVL insert

BST insert; update heights from the leaf up; at the deepest unbalanced node: LL → rotate right; RR → rotate left; LR → left at the left child, then right; RL → right at the right child, then left. One case, done.

Rotation references (Section 4)

Right at \(p\) (child \(b\)): a.left = b; p.left = b.right; b.right = p. Left at \(p\) (child \(c\)): a.left = c; p.right = c.left; c.left = p. Then fix heights.

Minimal AVL trees

\(M(h) = M(h-1) + M(h-2) + 1\): 1, 2, 4, 7, 12, 20, 33, 54, 88, 143, 232. Greatest height with \(n\) nodes: largest \(h\) with \(M(h) \le n\). \(h \le \log_\phi n\).

Hash functions

Consistent, uniform, effective, efficient. Equal objects must hash the same (override hashCode with equals).

\(h_3(s) = \sum a(s_i)\,31^i\); Horner: h = 31*h + s[i] from the last character.

Separate chaining

Index \(h(k) \bmod\) length; operate on that bucket. \(\lambda = n/\text{length}\). Unsuccessful find \(\approx \lambda\), successful \(\approx \lambda/2\). Keep \(\lambda < 2\).

Open addressing

Linear \(h + i\); quadratic \(h + i^2\); double \(h + i\cdot g(k)\), all mod length. Keep \(\lambda < \frac12\) (and a prime size for quadratic). Delete with tombstones: finds skip them, inserts reuse them.

Linear: primary clustering. Quadratic: secondary clustering. Double hashing avoids both.

Rehashing

New array about twice as long, prime; re-insert every key with \(h(k) \bmod\) new length.

Dictionaries compared

AVL tree\(\Theta(\log n)\) all; keeps order
Hash table\(\Theta(1)\) average, \(\Theta(n)\) worst; no order
Sorted arrayfind \(\Theta(\log n)\), insert/delete \(\Theta(n)\)
