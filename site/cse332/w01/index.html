What this lecture is for

The first topic of CSE 332 is data structures: specific "classic" ones, and how to tell which is better for a job. The second is how to analyze algorithms. To compare data structures, you first need to separate two questions:

What do I need? Which operations, and how they behave. That's the ADT.

How is it built? How the data is stored, and the steps for each operation. That's the data structure.

Lecture 1 teaches that split on two ADTs you already know from CSE 12x, the queue and the stack. Then it builds one ADT, the queue, in two very different ways. Both give the same answers. They store the items differently, and that difference is what Lecture 2 learns to measure.

After this lecture you should be able to

  1. Say whether something is an ADT, a data structure, an algorithm or an implementation, and why the difference matters. ADTs and terminology
  2. Describe the queue ADT and the stack ADT: what each one is, its operations, and how FIFO differs from LIFO. Linked queue, Stacks
  3. Explain how a linked queue stores its items, and what every line of its enqueue and dequeue does. Linked queue
  4. Explain how a circular array queue stores its items: what front and back mean, why % wraps around, and why it keeps a size. Circular array queue
  5. Trace any sequence of operations on either queue by hand. Exercises
  6. Say what each queue is good and bad at, which is the setup for Lecture 2. Linked vs. circular array

Lecture 1 · Wed Sept 30

ADTs and terminology

Key idea. An ADT describes what a kind of data does: the user's view. A data structure is one way to make that happen: the implementer's view. One ADT can have many data structures.

You've already seen this split

List<String> names = new ArrayList<>();

The left side, List, says what you'll do with names: add, remove, get the item at an index. The right side, ArrayList, says how the items are stored. Change it to new LinkedList<>() and the rest of your program still works, because it only ever used the List operations.

That's the whole idea. List plays the part of the ADT. Array list and linked list are two data structures for it.

The four terms

From most abstract to most concrete, with the queue as the example at every level:

ADTA mathematical description of a "thing" and its set of operations. Example: the queue, first in first out, with enqueue, dequeue and isEmpty.
Data structureAn organization of data, plus a family of algorithms that implement an ADT. Example: a circular array queue, which is an array plus front and back indices.
AlgorithmA high-level, language-independent description of a step-by-step process. Example: dequeue in a circular array means read the slot at front, then move front forward one slot.
ImplementationThe data structure's organization and algorithms, written in a programming language. Example: your ArrayQueue.java for Exercise 0.

What an ADT pins down

The topic summary says an ADT gives two things: the notion (what it represents) and the operations. Section 1 splits the notion into the behavior and the type of data it holds. The behavior matters most: a stack and a queue both add and remove items, and only their behavior says which item comes out.

ADTNotionOperationsSome data structures
ListAn ordered collection you can index intoadd, remove and get, each at an indexarray list, linked list
SetAn unordered collection with no duplicatesadd, remove, containsbinary search tree, hash set
QueueYou can only reach the item that's been in longest (FIFO)enqueue, dequeue, peek, isEmptylinked queue, circular array queue
StackYou can only reach the item added most recently (LIFO)push, pop, peek, isEmptylinked list, array list (resizable array)

Why keep them separate

  • The user can't tell the difference. Any data structure that keeps the ADT's promises can replace another. Test: "Could I swap it, and would the user notice?" If they wouldn't notice, it's a data structure.
  • The difference shows up in cost. Same answers, but different time and memory. Measuring that is the rest of the course, starting with Lecture 2.
  • Build for the ADT and nothing more. A queue never asks for the item at index 5, so a queue's data structure doesn't have to make indexing fast. That's why list and queue get different data structures.

Most data structures here use one of two designs. With linked nodes, each item sits in its own object that points to the next one. With a resizing array, the items sit side by side in an array that gets copied into a bigger one when it fills. Lecture 1 builds a queue each way.

Linked queue

The queue ADT. A collection of items you interact with in a "First In, First Out" (FIFO) way, like a line at a coffee shop. enqueue adds a new item. dequeue removes the oldest item. isEmpty says whether any items are left.

Key idea. Keep the items in a chain of nodes, oldest first. Items leave from one end and join at the other, so keep a reference to each end.

The picture

  • front points at the oldest item, the next one to leave.
  • back points at the newest item, the last one to arrive.
  • Each node points to the item enqueued after it. So the arrows run from old to new, which is the order items leave in.

Why keep back at all? dequeue works at the front and enqueue works at the back. Without back, every enqueue would have to walk the whole chain to find the last node. With it, both operations take a few steps, however long the queue is.

Pick an operation, then press Next line. Watch which reference changes on each line, and read why.

The two empty-queue cases.

  • Removing the last item: front becomes null, but back would still point at the node just removed. The if (front == null) line sets back to null as well, so both say "empty". Try "dequeue() the last item" above.
  • Adding to an empty queue: back is null, so back.next crashes. The lecture's code doesn't handle this case. Your Exercise 0 code must.

Lecture 1

Circular array queue

Key idea. Keep the items side by side in an array. Don't move the items. Move two indices, and let them wrap from the last slot back to slot 0, as if the array were a circle.

Why a circle?

  1. Plain idea: keep the oldest item in slot 0. But then every dequeue has to shift every other item left one slot, and that gets slower as the queue grows.
  2. Better: leave the items where they are and keep an index, front, to the oldest one. dequeue just moves front forward.
  3. New problem: as items come and go, the used part of the array creeps right. It reaches the end while slots at the start sit empty.
  4. Fix: when an index goes past the last slot, wrap it back to 0. Now the free slots at the start get reused.

What the fields mean

  • front is the index of the oldest item.
  • back is the index of the first open slot, where the next item will go. It is not the last item, which is the most common mix-up.
  • size is how many items are in the queue. The queue is the size slots starting at front, wrapping if needed.
  • (i + 1) % queue.length is "one slot forward, wrapping". With length 10: 3 → 4, 8 → 9, and 9 → 0.

Step through the code

Try "enqueue(5) into the last slot" to watch back wrap. Faded numbers are old values that are no longer in the queue.

Linked vs. circular array

Key idea. To the user, the two queues are identical: the same operations always return the same values. Underneath, they spend memory and time differently. Choosing between them is the kind of decision this course is about.

The lecture asked the room for each one's benefits and drawbacks and filled them in live, so there's no official list to copy. This table is worked out from how the two queues work. The week overview runs both queues side by side on the same buttons, so you can see they always agree.

Linked queueCircular array queue
StorageEach item gets its own node objectItems sit side by side in one array
Extra memoryOne next reference stored with every itemThe unused slots in the array
Room to growNever full: each enqueue just makes a new nodeFixed length: when it fills, resize() has to copy every item into a bigger array
Work per operationA few steps, however many items there areA few steps, however many items there are, except for the enqueue that triggers a resize
Empty casefront and back are null, which the code must watch forsize == 0, since front == back also happens when full

So which is better? It depends on what you care about, and "it depends" isn't a good enough answer for this course. Lecture 2 gives you a way to measure: count how many steps each operation takes as the number of items n grows. It also shows why the occasional costly resize averages out to a small cost per operation.

Lecture 1 · Section 1 · Weiss 3.6

Stacks

Key idea. A stack is a "Last In, First Out" (LIFO) collection, sometimes called FILO. Think of a stack of plates: you add to the top and take from the top.

Operations

  • push: add a new item onto the stack.
  • pop: return the most recently pushed item and remove it.
  • peek: return the most recently pushed item without removing it.
  • isEmpty: are there items still on the stack?

Stack vs. queue: one difference

Queue (FIFO)Stack (LIFO)
Items go in atthe backthe top
Items come out fromthe front, the other endthe top, the same end
Next outthe oldest itemthe newest item

Both ADTs add and remove, and only the behavior differs. That's what the earlier page meant by an ADT pinning down behavior. It also changes what a data structure has to do: a queue works at both ends, which is why the linked queue keeps front and back. A stack only ever works at one end.

Data structures for a stack (Section 1): a linked list or an array list (a resizable array). These are the same two designs as the queue. Building both is Exercise 0, so this site doesn't show the code.

Exercise 1: ADT: Queue

In a few words: what is a queue, and what operations does it need?

  1. Think of a line at a coffee shop. Who gets served next?
  2. You need a way to add, a way to remove, and a way to ask whether there's anything left.
  1. A collection of items that we interact with in a "First In First Out" (FIFO) way.
  2. Enqueue adds a new item to the queue. Dequeue removes the "oldest" item from the queue.
  3. IsEmpty indicates whether or not there are items still on the queue. (Section 1 also lists Peek.)

Exercise 2: ADT: Stack

In a few words: what is a stack, and what operations does it need?

  1. Think of a stack of plates. Which plate do you take?
  2. There are four operations: one adds, one removes, one looks without removing, and one checks for nothing left.
  1. A "Last In First Out" (LIFO) collection of items (sometimes called FILO).
  2. push adds a new item onto the stack. pop returns the most recently pushed item and removes it.
  3. peek returns the most recently pushed item without removing it. isEmpty says whether there are items still on the stack.

Exercise 3: trace the circular array queue

This practices the circular array queue: a queue stored in an array, where front is the index of the oldest item, back is the index of the next open slot, and both wrap around to 0 at the end of the array. Here is the lecture's code:

enqueue(x){
    queue[back] = x;
    back = (back + 1) % queue.length;
    size++;
}
dequeue(){
    // Assumes queue is not empty
    first = queue[front];
    front = (front + 1) % queue.length;
    size--;
    return first;
}

Java generics

Section 1 starts with an icebreaker and reviews ADTs from the user's point of view (operations, behavior, data type) and data structures from the implementer's. Then it builds every example around one small ADT.

Pair ADT. One object which holds an ordered pair of items. Operations: set first, get first, set second, get second. Data structure: an object with a first and a second field.

From IntPair to LikePair<T>

public class IntPair {
    private int first;
    private int second;
    public IntPair(int first, int second){
        this.first = first;
        this.second = second;
    }
    public int getFirst(){ return first; }
    ...
}
public class LikePair<T> {
    private T first;
    private T second;
    public LikePair(T first, T second){
        this.first = first;
        this.second = second;
    }
    public T getFirst(){ return first; }
    ...
}

IntPair only works with integers; for doubles or strings you'd re-implement the class. With generics we treat the type itself almost like a field. <T> says "the type of thing in this pair will be called T", and then T is used like int or String. You pick T when you construct one: LikePair<String> lp = new LikePair<>("A", "B");

Java generics. Java is strongly typed and must know what type of thing every collection holds. ArrayList<String> myArrayList = new ArrayList<>(); The type goes inside <>; the ArrayList code itself is written for any kind of Object.

Several type parameters, arrays, and bounds

  • UnlikePair<A,B>: the first item has type A, the second type B. That's how HashMap takes a key type and a value type.
  • Tuple<T>: Java doesn't allow new T[5]. The workaround is (T[]) new Object[5]: make an array of Objects and cast it. (The reason is "type erasure", from Java adding generics after its first release.)
  • LikeAnimalPair<T extends Animal>: extends requires T to be Animal or a subclass of it. Now LikeAnimalPair<Dog> holds two dogs and no cats.

Common mistake. <T extends Animal> doesn't mean "any animals". Once you pick T, both items must be that T. LikeAnimalPair<Animal> can hold a Dog and a Cat, since both are Animals. LikeAnimalPair<Dog> can only hold Dogs.

Why count operations?

Key idea. A stopwatch measures one program on one computer on one input. We want a property of the algorithm, so we count the steps it takes as a function of the input size.

Why it matters

We care about two things in an algorithm. Correctness: does it do what's intended? Performance: how much time and how much memory does it use? Performance matters because the gap between a good and a bad algorithm can be enormous. The course's running-time reading timed two correct sorting algorithms:

ItemsSelection sortPermutation sort
53.2 ms104.6 ms
104.4 ms164,403.8 ms (2.7 minutes)
146.6 msabout 26 minutes
157.1 msnot tried; estimated over 6 hours

Both give the right answer. One is useless past about a dozen items. We'd like to predict that before writing and timing the code.

Why not just time it?

  • Too much varies. Hardware, the operating system, the Java version, other programs running, and how well it was coded all change the time. If your code beats a classmate's on your laptop, that says nothing about the algorithms.
  • The input you picked may not be the hard one. Testing can miss the worst-case input.
  • A time doesn't explain growth. One measurement doesn't tell you what happens when \(n\) doubles.
  • You need code first. We often want to judge an algorithm before anyone implements it.

What we measure instead

Running time is a function \(f(n)\). Its input is the size of the algorithm's input: the number of items in a list, characters in a string, pixels in an image. Its output is a count of operations, such as additions, comparisons or array accesses.

This fixes every problem above. A faster computer does the same operations, just quicker, so \(f\) doesn't change. You can count from the algorithm without running it. And because \(f\) is a function of \(n\), you can ask what happens as \(n\) grows.

Always know the units. What is \(n\) counting, and what operation is \(f(n)\) counting? "The running time is \(n^2\)" means nothing until you say \(n^2\) of what, for an input of size \(n\) measured how.

Which operations to count

You don't have to count every primitive step. Pick the operations that matter:

  • Necessity: any algorithm for the problem has to do them.
  • Frequency: they're among the most frequent, up to a constant factor.
  • Magnitude: each one is expensive.

For sorting, that's usually comparisons: one item < or > another. Counting just these gives the same growth as counting everything, with far less work.

Quick check: you run the same algorithm on a computer that's twice as fast. What happens to its running-time function \(f(n)\)?

Quick check: you're analyzing a sorting algorithm. Which operation is the best one to count?

Worst, best, average, amortized

Key idea. Inputs of the same size can take different amounts of work. Before counting, decide which input you're counting for. Usually that's the worst one.

ScenarioWhat \(f(n)\) counts
Worst caseThe most steps on the hardest input of size \(n\)
Best caseThe fewest steps on the easiest input of size \(n\)
Average caseThe average steps over random inputs. The answer depends on what "random" means.
AmortizedThe most total steps over \(M\) hardest operations in a row, divided by \(M\): the cost per operation over a long run

See the difference on linear search

This code checks a list for \(k\), item by item, and stops as soon as it finds it:

public static boolean contains(List<Integer> a, int k){
    for(int i=0; i< a.size(); i++){
        if (a.get(i) == k)
            return true;
    }
    return false;
}

Comparisons (a.get(i) == k) for each target, on a list of 10 items

Click a target. The best case is the first item; the worst is the last item or a target that isn't there.

Why worst case is the usual choice

A worst-case bound is a guarantee: no input of size \(n\) takes more than \(f(n)\) steps. A best case says almost nothing, since nearly any search is fast when the target comes first. An average case needs you to know what inputs look like. So when someone says "the running time", they mean worst case unless they say otherwise.

Counting operations

Key idea. Statements in a row add. A loop multiplies its body by the number of times it runs. An if/else costs its check plus its slower branch. Then keep only the fastest-growing term.

The rules for worst case

Code shapeCost
Statements one after anotherAdd their costs
A loopAdd up every iteration. If each costs the same: cost per iteration × number of iterations
if / elseThe cost of the check + the cost of the slower branch (worst case doesn't know which branch runs)
A method callThe cost of the method's body
RecursionSolve a recurrence (week 3)

    Amortized analysis

    Key idea. An ArrayList add is usually cheap, but sometimes it has to copy the whole array. The copies are rare enough that, spread over all the adds, each add costs only about 2.

    The code

    public void add(int value){
    if(data.length == size)
        resize();
    data[size] = value;
    size++;
}
private void resize(){
    int[] oldData = data;
    data = new int[data.length*2];
    for(int i = 0; i < oldData.length; i++)
        data[i] = oldData[i];
}

    Units: \(n\) is the number of items in the list. We count array writes: 1 for data[size] = value, plus 1 for each element resize() copies.

    • Usually: there's room, so add writes one value. Cost 1.
    • When full: resize() makes an array twice as long and copies all \(n\) items into it, then writes. Cost \(n + 1\).

    So the worst case of one add is \(O(n)\). But that worst case can't happen often. Right after a resize the array is half empty, so the next resize is as many adds away as the copy just made.

    Watch it happen

    Each bar is one add. Most are 1 tall. The tall ones are the adds that resized, and each is taller than the one before it, but they get farther apart at the same rate.

    Adding it up

    Start with an array of length \(c\). Group the adds by when the next resize happens:

    AddsWritesCopies charged to these addsCost
    first \(c\)\(c\)\(c\)\(2c\)
    next \(2c\)\(2c\)\(2c\)\(4c\)
    next \(4c\)\(4c\)\(4c\)\(8c\)
    \(7c\) in all\(14c\)

    \[\frac{\text{total cost}}{\text{number of adds}} = \frac{14c}{7c} = 2.\]

    Every group's copies equal its number of adds, so each add pays for one write plus one copy. That's the amortized cost: about 2 per add, whatever \(c\) is.

    The same idea with parking

    Parking costs $10 a day. If you're caught without paying, you get a warning. On the third warning you pay a $25 fine and the warnings reset. Paying every day costs $10 a day. Never paying costs $0, $0, then $25: an occasional big cost, averaged over the cheap days around it.

    Quick check: what's the average cost per day if you never pay, in dollars? (round to the cent)

    Binary search

    Key idea. If the list is sorted, one comparison with the middle item rules out half the list. Halving again and again reaches 1 item after about \(\log_2 n\) steps, which is far fewer than \(n\).

    Linear search (the contains on the scenarios page) checks items one by one: up to \(n\) comparisons. If the list is sorted, it wastes that.

    Binary search

    public static boolean binary_contains(List<Integer> a, int k){
    int start = 0;
    int end = a.size();
    while(start < end){
        int mid = start + (end-start)/2;
        if(a.get(mid) == k)
            return true;
        else if(a.get(mid) < k)
            start = mid+1;
        else
            end = mid;
    }
    return false;
}
    • The items still in play are indices start up to, but not including, end.
    • If a.get(mid) < k, then, because the list is sorted, k can't be at mid or anywhere left of it. So start = mid+1.
    • If a.get(mid) > k, it can't be at mid or to its right. So end = mid.
    • When start == end, nothing is left in play: k isn't there.

    Why about \(\log_2 n\) iterations

    Call end - start the gap: how many items are still in play. Each iteration cuts it roughly in half.

    After this many iterations0123…\(x\)
    Gap\(n\)\(n/2\)\(n/4\)\(n/8\)…\(n/2^x\)

    The search is down to one item when \(n / 2^x = 1\), which means \(2^x = n\), or \(x = \log_2 n\). For a million items that's about 20 iterations, where linear search could need a million comparisons.

    Worst case, counted exactly

    For each \(n\), this runs binary_contains on a sorted list of \(n\) items for every possible target (each item, and each gap between items) and keeps the most iterations.

    The exact worst case is \(\lfloor \log_2 n\rfloor + 1\) iterations. The +1 is the last iteration, which runs when the gap is 1. It's the same bucket as \(\log_2 n\): \(O(\log n)\).

    Comparing running times

    Key idea. Which algorithm is faster can depend on \(n\). For big \(n\), the one whose count grows faster always loses, whatever the constants. \(O\), \(\Omega\) and \(\Theta\) are precise ways to say "grows no faster than", "at least as fast as" and "at the same rate as".

    Three algorithms, same answers

    Their worst-case running times are A: \(10n + 900\), B: \(100n - 50\), C: \(\frac{n^2}{100}\). Which is best? Change the range and watch the order change.

    Show \(n\) up to

    • Small \(n\): C is best by far. For the very smallest \(n\), B even beats A.
    • A little later: A passes B for good. Both grow like \(n\), and A's 10 per item is less than B's 100.
    • Past about a thousand: C becomes slower than A, and later slower than B too. From then on it only falls further behind: \(n^2\) eventually passes any constant times \(n\). (Exercise 8 finds the exact crossover points.)

    Small inputs are fast with almost any algorithm. What separates algorithms is large \(n\), so we compare how running times grow and ignore constant factors, which depend on the machine and the code anyway. In that sense A and B are "the same" (both linear), and C is worse (quadratic).

    The definitions

    \(f \in O(g)\): \(f\) grows no faster than \(g\).

    \[\exists c>0.\ \exists n_0>0.\ \forall n\ge n_0.\ f(n) \le c\cdot g(n)\]

    \(f \in \Omega(g)\): \(f\) grows at least as fast as \(g\). The same, with \(\ge\):

    \[\exists c>0.\ \exists n_0>0.\ \forall n\ge n_0.\ f(n) \ge c\cdot g(n)\]

    \(f \in \Theta(g)\): both. \(f\) grows at the same rate as \(g\). Just as \(x = y\) exactly when \(x \le y\) and \(x \ge y\).

    Read the \(O\) definition piece by piece:

    • "there's some \(c\)" lets you scale \(g\) up by any constant. That's how the definition ignores constant factors: \(10n + 900\) is \(O(n)\) because some multiple of \(n\) gets above it.
    • "there's some \(n_0\)" lets you ignore small \(n\). The inequality only has to hold from \(n_0\) on. That's how it ignores the +900, which matters at small \(n\) and not at large \(n\).
    • "for all \(n \ge n_0\)" means forever after, not just at the values you tried. A plot or a table can suggest a bound, but only the definition proves it.

    To prove \(f \in O(g)\), you name one \(c\) and one \(n_0\) and show the inequality holds for every \(n \ge n_0\). Any pair that works is enough, and you don't have to explain how you found it.

    Find \(c\) and \(n_0\)

    The verdict checks every integer \(n \ge n_0\) exactly, not just the ones plotted. Try making \(c\) smaller and see how \(n_0\) has to grow.

    Quick check: put C's running time \(\frac{n^2}{100}\) in a bucket.

    Quick check: true or false? "\(O\) means worst case and \(\Omega\) means best case."

    2. \(\frac{n^2}{100} > 10n + 900 \iff n^2 - 1000n - 90000 > 0\). Find the positive root.
    1. \(10n + 900 < 100n - 50 \iff 950 < 90n \iff n > 10.5\), so \(n = 11\).
    2. \(n^2 - 1000n - 90000 = 0\) has positive root \(500 + \sqrt{340000} \approx 1083.1\), so \(n = 1084\). Check: \(C(1083) = 11{,}728.89 < 11{,}730 = A(1083)\), and \(C(1084) = 11{,}750.56 > 11{,}740\).
    3. 11; 1084; C (it's \(\Theta(n^2)\), and A and B are \(\Theta(n)\)).

    9. Prove A is \(O(n)\)

    This practices a big-O proof on algorithm A from exercise 8, \(A(n) = 10n + 900\).

    \(f \in O(g)\) means: there are constants \(c > 0\) and \(n_0 > 0\) with \(f(n) \le c\cdot g(n)\) for every \(n \ge n_0\). To prove it, name one \(c\) and one \(n_0\) that work and show why.

    Here \(f(n) = 10n + 900\) and \(g(n) = n\). Find \(c\) and \(n_0\) with \(10n + 900 \le c\cdot n\) for all \(n \ge n_0\), and write the one-line reason in your work.

    1. Squeeze: for \(n \ge 1\), \(900 \le 900n\).
    2. Or keep \(c\) small and let \(n_0\) do the work: with \(c = 11\), when is \(900 \le n\)?
    1. For \(n \ge 1\): \(10n + 900 \le 10n + 900n = 910n\). So \(c = 910\), \(n_0 = 1\) works.
    2. Another choice: \(c = 11\). Then \(10n + 900 \le 11n \iff n \ge 900\), so \(n_0 = 900\).
    3. Any valid pair proves it, e.g. \(c=910, n_0=1\) or \(c=11, n_0=900\).

    10. \(4n^2 + 8n + 10 \in O\!\left(\tfrac14 n^3\right)\)

    A big-O proof from the course's Asymptotics handout. Here \(f(n) = 4n^2 + 8n + 10\) and \(g(n) = \tfrac14 n^3\).

    \(f \in O(g)\) means: there are constants \(c > 0\) and \(n_0 > 0\) with \(f(n) \le c\cdot g(n)\) for every \(n \ge n_0\). To prove it, name one \(c\) and one \(n_0\) that work and show why.

    Find \(c\) and \(n_0\) with \(4n^2 + 8n + 10 \le c\cdot\tfrac14 n^3\) for all \(n \ge n_0\).

    1. For \(n\ge1\), replace \(8n\) with \(8n^2\) and \(10\) with \(10n^2\). Neither makes the left side smaller.
    2. Then compare \(22n^2\) with \(c\cdot\frac14 n^3\).
    1. For \(n \ge 1\): \(4n^2+8n+10 \le 22n^2 \le 22n^3\).
    2. \(22n^3 = 88 \cdot \tfrac14 n^3\).
    3. \(c = 88\), \(n_0 = 1\) (the handout's answer; other pairs work too).

    11. \(4n^2 - 8n + 10 \in O(2n^2)\)

    Another big-O proof from the Asymptotics handout. Here \(f(n) = 4n^2 - 8n + 10\) and \(g(n) = 2n^2\). The minus sign is new.

    \(f \in O(g)\) means: there are constants \(c > 0\) and \(n_0 > 0\) with \(f(n) \le c\cdot g(n)\) for every \(n \ge n_0\). To prove it, name one \(c\) and one \(n_0\) that work and show why.

    Find \(c\) and \(n_0\) with \(4n^2 - 8n + 10 \le c\cdot 2n^2\) for all \(n \ge n_0\).

    1. Dropping \(-8n\) only makes \(f\) bigger, so it's enough to bound \(4n^2+10\).
    1. \(4n^2-8n+10 \le 4n^2+10 \le 14n^2\) for \(n\ge1\).
    2. \(14n^2 \le c\cdot 2n^2\) with \(c = 14\) (even \(c=7\) works).
    3. \(c = 14\), \(n_0 = 1\). The handout notes \(c = 5\) also works, from the same argument.

    12. \(4n^2 - 8n + 10 \in \Omega(2n^2)\)

    The same functions as exercise 11, now the other direction: a lower bound. \(f(n) = 4n^2 - 8n + 10\) and \(g(n) = 2n^2\).

    \(f \in \Omega(g)\) means: there are constants \(c > 0\) and \(n_0 > 0\) with \(f(n) \ge c\cdot g(n)\) for every \(n \ge n_0\). It's the \(O\) definition with \(\ge\) instead of \(\le\).

    Find \(c\) and \(n_0\) with \(4n^2 - 8n + 10 \ge c\cdot 2n^2\) for all \(n\ge n_0\).

    1. Dropping the \(+10\) only makes \(f\) smaller.
    2. For large enough \(n\), \(-8n \ge -n^2\). How large?
    1. \(4n^2-8n+10 \ge 4n^2-8n\). For \(n \ge 8\), \(8n \le n^2\), so this is \(\ge 3n^2 \ge 2n^2\).
    2. \(c = 1\), \(n_0 = 8\) (the handout's answer; it notes \(n_0 = 3\) also works).

    Terminology

    ADT: mathematical description of a thing + its operations (the user's view). Data structure: data organization + algorithms implementing an ADT (the implementer's view). Implementation: that in a language. Algorithm: language-independent step-by-step process.

    Queue (FIFO) & stack (LIFO)

    Queue: enqueue, dequeue (oldest), isEmpty (+ peek). Stack: push, pop (newest), peek, isEmpty.

    Linked queue: front = oldest node, back = newest; set back = null when the last node leaves.

    Circular array: back = first open slot; advance with (i + 1) % queue.length; isEmpty uses size because front == back when empty and when full.

    Generics

    class LikePair<T> · class UnlikePair<A,B> · bound: <T extends Animal> · no new T[n]; use (T[]) new Object[n].

    <A extends Comparable<A>>: A compares to itself.

    Worst-case counting guide

    • Consecutive statements: add.
    • Loops: sum the iterations (time per iteration × iterations).
    • Conditionals: the check + the slowest branch.
    • Calls: the body's time. Recursion: a recurrence.

    Scenarios

    Worst: max over inputs of size \(n\). Best: min. Average: over random inputs. Amortized: max total over \(M\) consecutive ops ÷ \(M\).

    ArrayList add: \(O(n)\) worst case, constant amortized (\(14c/7c = 2\)).

    Asymptotic notation

    \(f\in O(g) \iff \exists c>0, n_0>0.\ \forall n\ge n_0.\ f(n)\le c\, g(n)\)

    \(f\in \Omega(g) \iff \exists c>0, n_0>0.\ \forall n\ge n_0.\ f(n)\ge c\, g(n)\)

    \(\Theta(g) = O(g)\cap\Omega(g)\). These compare functions, not cases.
