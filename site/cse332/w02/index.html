Lecture 3 claims \(n^{50} \in O(1.1^n)\). At \(n = 100\), \(n^{50}\) has 101 digits and \(1.1^{n}\) is about 13,781. So is the claim wrong?

Lecture 3 · Mon Oct 5 · Algorithm Analysis 2

What this lecture is for

Lecture 2 turned an algorithm into a function: input size in, number of steps out. Now we need to compare those functions. Exact counts aren't the right thing to compare. They depend on which operations you count and on the machine, and every algorithm is fast on small inputs.

So Lecture 3 compares functions by how they grow for large \(n\), ignoring constant factors. It makes that precise with \(O\) (at most), \(\Omega\) (at least) and \(\Theta\) (both), each defined with two constants you get to choose: a multiplier \(c\) and a starting point \(n_0\). Then it shows how to prove a bound, which parts of a function you may drop, and how to use the notation without mixing up "which case" with "which bound".

The question. Does \(f\) grow at most as fast as \(g\), at least as fast, or the same?

The tool. \(f \in O(g)\) when \(f(n) \le c\cdot g(n)\) for every \(n \ge n_0\), for some \(c\) and \(n_0\) you pick.

After this lecture you should be able to

  1. Explain why binary search takes about \(\log_2 n\) loop iterations in the worst case, and why the base of the log doesn't matter. Binary search
  2. Say why we compare running times by their long-term growth and ignore constant factors. Comparing running times
  3. State the definitions of \(O\), \(\Omega\) and \(\Theta\), and say what \(c\) and \(n_0\) each let you do. The definitions
  4. Prove a bound like \(10n + 100 \in O(n^2)\): pick \(c\) and \(n_0\), then show the inequality for every \(n \ge n_0\). Proving a bound
  5. Put a function in its simplest \(\Theta\) class, and say which parts you may drop and which you may not. What you can drop
  6. Decide claims like \(n^{50} \in O(1.1^n)\) and justify them. True or false?
  7. Keep "which case" (worst, best) separate from "which bound" (\(O\), \(\Omega\), \(\Theta\)), and say \(\Theta\) when you mean it. Case vs. bound, Using the notation

Why binary search is \(\log_2 n\)

Key idea. Each iteration of binary search throws away at least half of the range that could still hold \(k\). After \(x\) iterations about \(\frac{n}{2^x}\) items are left, so it runs out after about \(\log_2 n\) iterations.

public static boolean contains(
        List<Integer> a, int k){

        if (a.get(i) == k)
            return true;
    }
    return false;
}
// use the order: halve the range each time
public static boolean binary_contains(
        List<Integer> a, int k){
    int start = 0;
    int end = a.size();
    while(start < end){
        int mid = start + (end-start)/2;
        if(a.get(mid) == k)
               return true;
        else if(a.get(mid) < k)
               start = mid+1;
        else
               end = mid;
    }
    return false;
}

Why each line of binary_contains is there

  • start and end mark the part of the list that could still hold \(k\): indices start up to, but not including, end. At first that's the whole list.
  • mid = start + (end-start)/2 is the middle of that range.
  • If a.get(mid) < k, then \(k\) can only be to the right of mid, because the list is sorted. So start = mid+1 throws away mid and everything left of it.
  • Otherwise \(k\) can only be left of mid. end = mid throws away mid and everything right of it (end itself is never a candidate).
  • while(start < end) stops when the range is empty: \(k\) isn't there.

The number to watch is the gap, end - start: how many candidates are left.

Watch the gap halve

Try \(k = 5\): the gaps go 10, 5, 2, 1, so binary search takes 4 iterations to find the very first item, which contains finds in 1. Binary search wins in the worst case, not on every input.

The halving argument. At the start the gap is \(n\). One iteration keeps either mid - start or end - mid candidates, and each is about half the gap. So after \(x\) iterations the gap is about \(\frac{n}{2^x}\). It can't shrink past 1 and still have something to look at, so the loop runs about until

\[\frac{n}{2^x} = 1 \quad\Longrightarrow\quad 2^x = n \quad\Longrightarrow\quad x = \log_2 n.\]

Exactly: the worst case is \(\lfloor\log_2 n\rfloor + 1\) iterations, because the loop still runs once when the gap is 1. For \(n = 1024\) that's 11. Either way it's \(\Theta(\log n)\).

Worst case for any \(n\)

The worst path always keeps the larger half, so the gap goes \(n \to \lfloor n/2\rfloor \to \dots \to 1\), one iteration per gap. The checks for this site ran binary_contains in Java on every possible target and got the same counts.

What's the base of the log?

It doesn't matter for \(O\). \(\log n\) with no base means \(\log_2 n\). If an algorithm took \(\log_5 n\) steps instead, that's

\[\log_5 n = \frac{\log_2 n}{\log_2 5},\]

and \(\log_2 5\) is just a constant, about 2.32. Constants hide inside the \(O(\,)\), so \(O(\log_5 n)\) and \(O(\log_2 n)\) are the same set.

Base \(c\):

The last column never changes as \(n\) grows: it's the constant \(\log_2 c\).

What measured times showed

The lecture also graphed measured running times. On small lists the binary search curve sat above linear search. On larger lists linear search climbed past it and kept going. What wins on small inputs can lose on big ones. That's why the next page compares running times by their long-term behavior.

Comparing running times

Key idea. Which algorithm is cheapest can depend on \(n\). So compare running times by what happens for large \(n\), and ignore constant factors, because those depend on who counted and on the machine.

Three algorithms, same answers

Three algorithms give the same output on every input. Their worst-case running times are

  • A: \(10n + 900\)
  • B: \(100n - 50\)
  • C: \(\dfrac{n^2}{100}\)

Which one is best?

A = 10n + 900B = 100n − 50C = n²/100

It depends on \(n\). C is the cheapest of the three up to \(n = 1{,}083\), and A is cheapest from 1,084 on. B beats A only up to \(n = 10\). An answer that changes with \(n\) isn't useful, so we decide what kind of comparison we want.

What we want from a comparison

  • Long-term behavior. Almost every algorithm is fast on small inputs. The inputs where speed matters are the big ones.
  • Ignore constant coefficients. Different people count different operations, which gives different coefficients for the same algorithm. Even counting the same operations, they take different amounts of time on different computers.
  • Ignore non-dominant terms. Constant coefficients matter more than lower-order terms: \(2n^2 > n^2 + n\) for every \(n > 1\). If we've already agreed to ignore coefficients, the lower-order terms have to go too.

Under those rules, A and B are the same kind of function: both grow like \(n\). C grows like \(n^2\), so for large enough \(n\) it loses to both, whatever the constants are. The next page turns "grows like" into a definition.

\(O\), \(\Omega\), \(\Theta\)

Key idea. \(f \in O(g)\) means: from some point \(n_0\) on, \(f\) stays at or below \(c\) times \(g\), for one constant \(c\) you choose. \(\Omega\) flips the inequality to \(\ge\). \(\Theta\) means both.

Read them as comparisons

WriteThinkMeans, for large \(n\) and up to a constant
\(f \in O(g)\)\(f \le g\)\(f\) grows at most as fast as \(g\): an upper bound
\(f \in \Omega(g)\)\(f \ge g\)\(f\) grows at least as fast as \(g\): a lower bound
\(f \in \Theta(g)\)\(f = g\)both: a tight bound

\(\Theta\) works like equality for numbers: \(x = y\) exactly when \(x \le y\) and \(x \ge y\). The comparison is about long-term size, not equal outputs: \(3n^2 + 17\) and \(n^2\) are never equal, but they're in the same \(\Theta\).

The definitions

\(O(g(n))\): the set of functions with asymptotic behavior less than or equal to \(g(n)\): upper-bounded by a constant times \(g\) for large enough \(n\). Click each part:

\(\equiv\)

Click any part of the definition.

\(\Omega(g(n))\): the set of functions with asymptotic behavior greater than or equal to \(g(n)\):

\[f \in \Omega(g(n)) \equiv \exists c>0.\ \exists n_0>0.\ \forall n\ge n_0.\ f(n) \ge c\cdot g(n)\]

\(\Theta(g(n))\): "tightly" within a constant of \(g\) for large \(n\): \(\Theta(g(n)) = \Omega(g(n)) \cap O(g(n))\).

Why each piece is there

  • \(c\) lets you ignore constant factors. \(5n^3 \in O(2n^3)\): pick \(c = 3\), and \(5n^3 \le 3\cdot 2n^3\). Without \(c\), \(5n^3\) wouldn't be at most \(2n^3\), and the comparison would care about coefficients we said we can't trust.
  • \(n_0\) lets you ignore small inputs. C beat A for every \(n\) up to 1,083 on the last page. \(n_0\) says "from here on", so those early values don't count.
  • The order matters: \(\exists c, n_0\) first, then \(\forall n\). You choose one \(c\) and one \(n_0\), and then they must work for every \(n \ge n_0\). If you could choose a new \(c\) for each \(n\), any function would be \(O\) of any other (take \(c = f(n)/g(n)\)), and the definition would say nothing.

\(O(n^2)\) is a set

\(f \in O(g)\) is membership. \((3n^2 + 17) \in O(n^2)\), because \(3n^2 + 17\) and \(n^2\) have the same asymptotic behavior. People also write "\(3n^2 + 17\) is \(O(n^2)\)" and "\(3n^2 + 17 = O(n^2)\)". That "=" means "is in", so it only reads one way: nobody writes \(O(n^2) = 3n^2 + 17\).

Move \(c\) and \(n_0\)

Pick the upper or lower bound for \(3n^2 + 17\) against \(n^2\). Each dot is one \(n\). Green: the inequality holds at that \(n\). Red: it fails at an \(n \ge n_0\), which the definition doesn't allow. Grey: \(n < n_0\), ignored. A pair \(c, n_0\) proves the claim when no red is left anywhere, including past the right edge. Try \(c = 3\), then \(c = 4\), and look for the smallest \(n_0\) that works.

Proving a bound

Key idea. To prove \(f \in O(g)\), name a specific \(c\) and \(n_0\), then show \(f(n) \le c\cdot g(n)\) for an arbitrary \(n \ge n_0\). You find \(c\) and \(n_0\) in scratchwork first. The proof only states them and shows they work.

Why the proof has that shape

Big-O is an "exists \(c, n_0\), for all \(n\)" statement: an exists with a for-all inside.

  • To prove an "exists", show one that works. Give specific values: "Let \(c = 10\) and \(n_0 = 10\)." Not "for some big enough \(c\)".
  • To prove a "for all", take an arbitrary \(n \ge n_0\), one you know nothing else about, and show the inequality for it. You can't check infinitely many \(n\) one at a time, and a picture only shows a few.

Example 1: \(10n + 100 \in O(n^2)\)

Scratchwork. We need \(10n + 100 \le c\cdot n^2\). The algebra looks easier with \(c = 10\), because then we can divide by 10: we need \(n + 10 \le n^2\).

To choose \(n_0\), ask when "add 10" matters less than "multiply by \(n\)". If \(n \ge 10\), then \(n + 10 \le 2n\), and \(2n \le 10n\), and \(10n \le n^2\). So \(n + 10 \le n^2\). Use \(c = 10\), \(n_0 = 10\).

Proof

Let \(c = 10\) and \(n_0 = 10\). Show that for all \(n \ge 10\), \(10n + 100 \le 10n^2\).

\[\begin{aligned} &10n+100 \le 10n^2\\ \equiv\ & n + 10 \le n^2\\ \equiv\ & 10 \le n^2 - n\\ \equiv\ & 10 \le n(n-1)\end{aligned}\]

This is true because \(n(n-1)\) is strictly increasing and \(10(10-1) > 10\).

  • Why "\(\equiv\)" on every line: each step can be undone (divide by 10, subtract, factor), so proving the last line proves the first.
  • Why the last sentence finishes it: at \(n = 10\) the right side is \(90 \ge 10\), and it only grows from there. So it holds at every \(n \ge 10\), not just the ones we tried.
  • 10 isn't the only \(n_0\). With \(c = 10\), the inequality already holds from \(n = 4\). A proof needs one pair that works, not the smallest.

Example 2: \(13n^2 - 50n \in \Omega(n^2)\)

Scratchwork. We need \(13n^2 - 50n \ge c\cdot n^2\). Divide by \(n\): \(13n - 50 \ge c\cdot n\). It looks simpler with \(c = 13\). Then we need \(13n - 50 \ge 13n\), which means \(-50 \ge 0\).

That didn't work, and it tells us why. The left side is always 50 short of \(13n\). So \(c\) has to be less than 13, to leave room for the 50. Try \(c = 12\): \(13n - 50 \ge 12n\) simplifies to \(n \ge 50\). Use \(c = 12\), \(n_0 = 50\).

Proof

Let \(c = 12\) and \(n_0 = 50\). Show that for all \(n \ge 50\), \(13n^2 - 50n \ge 12n^2\).

\[\begin{aligned} &13n^2 - 50n \ge 12n^2\\ \equiv\ & n^2 - 50n \ge 0\\ \equiv\ & n - 50 \ge 0 \quad(\text{since } n \ge 50, n \ne 0)\\ \equiv\ & n \ge 50\end{aligned}\]

Because we chose \(n_0 = 50\), the inequality holds for all \(n \ge n_0\).

Why "\(n \ne 0\)" is written down: the third line divides by \(n\). That step is only reversible when \(n\) is positive, and \(n \ge 50\) guarantees it.

Try your own \(c\) and \(n_0\)

Any pair that works is a proof. Find other pairs for the two examples. The last claim, \(n^2 \in O(n)\), is false: watch what happens to the red dots as you raise \(c\).

Common mistakes

  • Handing in only the scratchwork. The proof starts with "Let \(c = \dots\) and \(n_0 = \dots\)", then argues for an arbitrary \(n \ge n_0\).
  • Choosing \(n_0\) from a picture. A plot shows a few values of \(n\); the proof has to cover all of them.
  • Letting \(c\) depend on \(n\), as in "pick \(c = n\)". \(c\) is fixed before \(n\) is.
  • Dividing by something that might be 0 or negative without saying why it can't be.

Quick check: the proof of \(10n + 100 \in O(n^2)\) above ends with "\(n(n-1)\) is strictly increasing and \(10(10-1) > 10\)". Why are both halves needed?

What you can drop

Key idea. To find a function's \(\Theta\) class, keep only its fastest-growing term and drop that term's constant factor. Log bases can go too. Exponents, bases of exponentials, and the logs themselves stay.

The rules

  • If several expressions are added, ignore all but the biggest: if \(f\) grows faster than \(g\), then \(f(n) + g(n) \in \Theta(f(n))\).
  • Ignore multiplicative constants: \(c\cdot f(n) \in \Theta(f(n))\) for any constant \(c > 0\).
  • Ignore the bases of logarithms.
  • Don't ignore constants that aren't multipliers or added terms: constants in exponents, and bases of exponentials. Don't ignore logarithms themselves.

Why you may drop them

Every rule follows from the definition. Each one is the \(c\) at work.

  • Constant factors. \(5n^3\) vs \(2n^3\): \(c = 3\) gives \(5n^3 \le 3\cdot 2n^3\), and \(c = 1\) gives \(5n^3 \ge 1\cdot 2n^3\). So they're in the same \(\Theta\). There are no units here anyway: \(3n^2\) versus \(5n^2\) means nothing when we can't count operations that accurately.
  • Lower-order terms. For \(n \ge 1\), \(n \le n^2\) and \(1 \le n^2\). So \(2n^2 + 8n + 3 \le 2n^2 + 8n^2 + 3n^2 = 13n^2\). A smaller term costs at most a bigger constant on the dominant term, and constants are already ignored. As \(n\) grows, their share shrinks toward nothing.
  • Log bases. \(\log_c n = \frac{\log_2 n}{\log_2 c}\): a constant factor again.

Why you may not drop the others

The test is the ratio. If \(f(n)/g(n)\) grows without bound, no constant \(c\) can keep \(f \le c\cdot g\).

  • Exponents: \(n^3/n^2 = n\), unbounded. So \(n^3 \notin O(n^2)\).
  • Bases of exponentials: \(3^n/2^n = 1.5^n\), unbounded. So \(3^n \notin O(2^n)\).
  • Constants in exponents: \(2^{n+1} = 2\cdot 2^n\) is fine, because the +1 turns into a multiplier. But \(2^{2n} = 4^n\): the 2 changed the base.
  • The log itself: \(n\log n / n = \log n\), unbounded. So \(n\log n \notin O(n)\), even though \(\log n\) grows slowly.

    True or false?

    Key idea. To decide \(f \in O(g)\), ask whether \(f/g\) stays bounded as \(n\) grows. "Eventually" can be far away, but once it starts it has to last forever.

    How to decide

    1. Simplify both sides to their \(\Theta\) classes.
    2. Ask which grows faster in the long run. Any exponential \(b^n\) with \(b > 1\) beats any polynomial; any polynomial \(n^k\) beats any power of \(\log n\).
    3. \(O\) holds if \(f\) grows no faster than \(g\). \(\Omega\) holds if \(f\) grows no slower. \(\Theta\) holds if both do.
    4. Justify it: for \(O\), say why \(f \le c\cdot g\) for large \(n\). For "false", say why every \(c\) eventually fails.

    The classifier below reports all three relations at once. \(O\) and \(\Omega\) can both be true (that's \(\Theta\)), or exactly one can be.

    Case vs. bound

    Key idea. "Worst case" or "best case" picks which function you analyze. \(O\), \(\Omega\) and \(\Theta\) say what you know about that function. The two choices are independent: any bound can go with any case.

    A common misconception: "\(\Omega\) means best case and \(O\) means worst case." It's wrong, and generated text often says it. \(O\) says "at most" (think \(\le\)), \(\Omega\) says "at least" (think \(\ge\)). You can say \(\le\) or \(\ge\) about the worst case, and about the best case.

    Two separate questions

    Take linear search (contains) on a list of \(n\) items.

    1. Which function? The worst case is the input that takes longest (the item is missing): \(W(n) = n\) comparisons. The best case is the easiest input (the item is first): \(B(n) = 1\).
    2. What do I know about it? \(W(n) \in \Theta(n)\). \(B(n) \in \Theta(1)\). Also true: \(B(n) \in O(n)\), a loose upper bound on the best case, and \(W(n) \in \Omega(1)\), a weak lower bound on the worst case.

    Why use \(O\) or \(\Omega\) instead of \(\Theta\)?

    • Sometimes you can't be sure your analysis is tight. Then an upper or a lower bound is what you can honestly claim.

    Using the notation well

    Key idea. Say \(\Theta\) when you know it. Say what you analyzed: the algorithm or the problem, time or space, which case, which bound. And remember that \(O\) hides constants, which can decide things for real input sizes.

    Say \(\Theta\) when you mean it

    A common error is to say \(O(f(n))\) when you mean \(\Theta(f(n))\). If \(f(n) = n\), then "\(f(n) \in O(n)\)" is true, but it only gives the upper bound: \(f(n) = n\) is also \(O(n^5)\). So "this algorithm is exactly \(O(n)\)" is incomplete. Say it's \(\Theta(n)\). That also tells the reader it is not, for example, \(O(\log n)\).

    What we are analyzing

    The most common thing to do is give an \(O\) or \(\Theta\) bound on the worst-case running time of an algorithm. Each of those words is a choice. True statements about binary search:

    Common \(\Theta(\log n)\) running time in the worst case.
    Less common \(\Theta(1)\) in the best case (the item is in the middle).
    Less common \(\Omega(\log\log n)\) in the worst case. True, but weak: it only says the algorithm isn't really, really fast.
    Good to know The find-in-sorted-array problem is \(\Omega(\log n)\) in the worst case: no algorithm can do better (without parallelism).

    A problem can't usefully be "\(O(f(n))\)", since you can always write a slower algorithm. When people say it, they mean some algorithm for it is that fast.

    Analysis can be about the problem or the algorithm (usually the algorithm); time or space (usually time; or power, or dollars); the best, worst or average case (usually worst); and an upper, lower or tight bound (usually upper or tight).

    Where \(O\) can mislead

    \(O\) is about large \(n\), independent of any computer or coding trick. You can still be misled about trade-offs. \(n^{1/10}\) grows faster than \(\log n\), but the crossover is around \(5\cdot10^{17}\). For inputs smaller than about \(2^{58}\), the \(n^{1/10}\) algorithm is the cheaper one.

    40

    Decided exactly: \(2^{k/10} > k \iff 2^k > k^{10}\), compared with big integers.

    Comparing \(O(\,)\) at small \(n\) can mislead too. Quicksort is \(O(n\log n)\) expected and insertion sort is \(O(n^2)\) expected, yet insertion sort is faster for small \(n\). Sorting comes later in the course.

    Timing vs. Big-O

    Use the right tool. To evaluate an algorithm, use asymptotic analysis: study the algorithm itself, mathematically, as a function of \(n\), and prove things about it. To evaluate an implementation (hardware or software), timing is useful: in the real world we do want to know whether implementation A runs faster than B on data set C, like when benchmarking graphics cards.

    1. Halving the gap

    This practices the lecture's argument for why binary search takes about \(\log_2 n\) loop iterations. Here is the lecture's binary search on a sorted list a of \(n\) items:

    public static boolean binary_contains(
        List<Integer> a, int k){
    int start = 0;
    int end = a.size();
    while(start < end){
        int mid = start + (end-start)/2;
        if(a.get(mid) == k)
               return true;
        else if(a.get(mid) < k)
               start = mid+1;
        else
               end = mid;
    }
    return false;
}

    The gap is end - start, the number of items that could still hold \(k\). It starts at \(n\), and each iteration of the while loop roughly halves it. After \(x\) iterations about \(\frac{n}{2^x}\) items are left. One iteration is one pass through the loop body. The worst case is a \(k\) that makes the loop run as many times as possible.

    1. \(\frac{n}{2^x} = 1\) means \(2^x = n\). For the loop counts, write down the gaps: \(n, \lfloor n/2\rfloor, \dots, 1\). Each gap is one iteration.
    2. \(2^{20} = 1{,}048{,}576\). Is \(1{,}000{,}000\) above or below that?
    1. \(2^{12} = 4096\), so \(x = 12\).
    2. For \(n = 2^{20}\), the gaps are \(2^{20}, 2^{19}, \dots, 2^0 = 1\). That's 21 gaps, so 21 iterations. The loop still runs when the gap is 1.
    3. For \(n = 10^6\): \(2^{19} = 524{,}288 \le 10^6 < 2^{20}\), so \(\lfloor\log_2 10^6\rfloor = 19\) and the worst case is \(19 + 1 = 20\).
    4. 12; 21; 20. All are \(\lfloor\log_2 n\rfloor + 1\), which is \(\Theta(\log n)\).

    2. The base of the log

    This practices the lecture's claim that the base of a log doesn't matter inside \(O(\,)\). The tool is the change-of-base rule: \(\log_c n = \frac{\log_2 n}{\log_2 c}\), so changing the base only divides by a constant.

    1. \(\log_2 8\) is a small whole number.
    2. For the last two, the ratio of the two functions is a constant both ways round. What does that give you for \(c\)?
    1. \(\log_2 8 = 3\), so \(\log_8 n = \frac{\log_2 n}{3}\).
    2. At \(n = 2^{30}\): \(\frac{30}{3} = 10\). Check: \(8^{10} = 2^{30}\).
    3. \(\log_5 n = \frac{1}{\log_2 5}\log_2 n \le 1\cdot\log_2 n\), so \(c = 1\) works. And \(\log_2 n = (\log_2 5)\cdot\log_5 n\), so \(c = \log_2 5 \approx 2.32\) works the other way.

    What this lecture is for

    A queue serves the oldest item first. Lots of real problems need the most important item first instead: an emergency room, an operating system choosing which program runs next. That's a new ADT, the priority queue.

    The priority queue ADT

    Key idea. A priority queue hands back the most important item, by convention the one with the smallest priority value, no matter when it arrived.

    Pharmacy vs. emergency room

    Pharmacy: a queue. First come, first served. The next person is whoever has waited longest.

    Emergency room: a priority queue. Patients are seen by need. Someone who just arrived with an emergency goes first.

    The ADT

    Notion: a collection of items and their priorities, with quick access to (and removal of) the top-priority item.

    • insert(item, priority): add a new item with the given priority.
    • extract: remove and return the top-priority item, usually the one with the smallest priority value.
    • isEmpty: are there items left?

    Why smallest? Priorities are like rankings: "you're my number one priority" means most important. Making the largest value most important instead takes only small changes.

    Priorities must be comparable. Unlike a stack or a queue, a priority queue has to compare items: is \(x\) less than, equal to, or greater than \(y\)? Any type works as long as you can use < or compareTo. In lecture the item is often just an int that is also its own priority.

    Ties: two items with the same priority may come out in either order. An ER line would probably serve them first come, first served; the ADT doesn't promise that.

    A trace

    insert(5,5)  insert(6,6)  insert(3,3)
print(extract)
insert(1,1)
print(extract)
print(extract)
insert(8,8)
print(extract)
print(extract)

    Keep a list of what's waiting. Each extract takes the smallest item in the queue right now, not the smallest ever inserted and not the oldest. Note the 1: it arrives after 5 and 6, and still leaves before them.

    Uses: treating patients by severity; running programs ("critical" before "interactive" before "compute-intensive"); forwarding network packets by urgency; data compression; graph algorithms later in the course; and sorting: insert everything, then extract repeatedly.

    Complete trees are short

    Key idea. A heap is always a complete binary tree: every level is full except the bottom one, which fills from the left. That shape forces the height to be about \(\log_2 n\).

    Binary and complete

    • Binary tree: every node has at most 2 children.
    • Complete tree: all levels are full, except the bottom one, and the bottom level is filled left to right with no gaps.
    • Height: the number of edges on the path from a node down to its deepest descendant. A tree's height is its root's height. The tree here has height 3.

    Why the height is \(\Theta(\log n)\)

    Count the most nodes a binary tree of height \(h\) can hold: one root, then at most twice as many on each next level.

    \[1 + 2 + 4 + \dots + 2^h = 2^{h+1} - 1.\]

    So a tree with \(n\) nodes needs a height \(h\) with \(n \le 2^{h+1} - 1\). The smallest such \(h\) is \(\lceil\log_2(n+1)\rceil - 1\), which is \(\Theta(\log n)\). A complete tree fills each level before starting the next, so it always has exactly that smallest height.

    Why insist on this shape

    1. Speed. Insert and extract will each make one trip between the root and a leaf. A short tree means a short trip: \(\Theta(\log n)\).
    2. Storage. Every complete tree with \(n\) nodes has the same shape, with no gaps. Lecture 5 uses that to store the tree in an array.

    The heap property

    Key idea. The min-heap property: every node's priority is \(\le\) its children's. That alone puts the minimum at the root, and it says nothing about siblings or cousins.

    The two rules of a (min) heap

    1. Keep the items in a complete binary tree.
    2. Maintain the min-heap property: every node's priority is \(\le\) its children's priorities. (A max-heap flips it: every node \(\ge\) its children.)

    Why the minimum is at the root

    Start at any node and walk up toward the root. Each step goes to a parent, and a parent is \(\le\) its child. So the values never go up as you climb, and the root is \(\le\) every node. The same argument works for any subtree: each node holds the smallest value in its own subtree.

    What it does not require

    The property only compares a node with its own children, and so with its own ancestors. It says nothing about nodes in other branches. In this valid min-heap, the 3 on the bottom level is smaller than the 5 a level above it. That's fine: 5 isn't an ancestor of 3.

    This is why a heap is cheaper to maintain than a sorted list. Fixing a sorted list after a change can mean moving everything. Fixing a heap only means fixing one path.

    Insert: percolate up

    Key idea. Put the new item in the next open spot, so the tree stays complete. Then swap it with its parent while it's smaller. Only the path from the new spot up to the root can be broken, so that path is all you fix.

    Why each step

    • Next open spot first. The shape rule decides where the tree grows: the leftmost empty place on the bottom level (or a new level, if the bottom is full). Fix the shape first, the order second.
    • Compare only with the parent. Before the insert, everything was a valid heap. The new item is a leaf with no children, so the only rule it can break is "parent \(\le\) child" with its own parent.
    • Swapping up is safe. Say the new item \(x\) is below parent \(P\), with sibling \(S\). The old parent \(P\) moves down; it was already \(\le\) everything below it, so it's fine there. And \(x < P \le S\), so \(x\) is a fine parent for \(S\). The only link that can still be wrong is \(x\) and its new parent.
    • Stop when \(x\) is not smaller than its parent, or when \(x\) reaches the root.

    This is called percolate up: take a node that may be smaller than its parent and repeatedly swap it with its parent until it isn't.

    Step through it

    the moving itembeing comparedjust swapped

    Cost. Each swap moves the item up one level, so there are at most \(h\) swaps, where \(h\) is the height: \(\Theta(\log n)\) in the worst case. The worst case is a new item smaller than everything, which climbs all the way to the root.

    Extract: percolate down

    Key idea. The minimum is the root, so save it. To keep the tree complete, move the bottom-right item into the root. Then swap that item down with its smaller child until it's \(\le\) both children.

    Why each step

    • Save the root first. It's the answer, and the next step writes over it.
    • Why the bottom-right item. A tree with one fewer item has to lose exactly that spot to stay complete. So that item has to move somewhere, and the root just became empty.
    • Why it goes down. It came from the bottom, so it's probably too big for the top. Everything else is still in heap order; only the moved item can be out of place.
    • Why the smaller child. The child that moves up becomes the parent of the other child. The smaller one can do that. The larger one would end up above a smaller value: a new violation.
    • Stop when the item is \(\le\) both children, or when it's a leaf.

    This is called percolate down: take a node that may be larger than a child and repeatedly swap it with its smallest child until both children are larger.

    Step through it

    the moving itembeing comparedjust swapped

    Why both operations are \(\Theta(\log n)\)

    Both percolates move one item along one path between the root and a leaf, one level per swap. So each does at most \(h\) swaps, and \(h \in \Theta(\log n)\) because the tree is complete. Percolate up makes one comparison per level (with the parent); percolate down makes two (with both children), so it does up to \(2h\) comparisons. A constant factor doesn't change the class: both are \(\Theta(\log n)\) in the worst case.

    Common mistakes

    • Swapping with the left child, or the larger child, instead of the smaller one.
    • Moving the root's smaller child up into the root instead of moving the last item. That leaves a hole and breaks the shape.
    • Forgetting that the moved item can stop partway down, above two larger children.

    What a bound leaves open

    Key idea. \(f \in O(n)\) only says \(f\) grows at most like \(n\). It doesn't say how small \(f\) is. So a statement about \(f\) is "always true" only if it holds for every function that fits, "always false" if it holds for none, and "sometimes true" otherwise.

    The method: test the extremes

    Picture the growth classes in a row, slowest first. \(f \in O(n)\) puts \(f\) somewhere from the bottom (a constant, like \(f = 1\)) up to \(n\) (like \(f = n\)). Running times are at least a constant, so that's the whole range.

    1. Try the biggest \(f\) allowed, \(f = n\), and the smallest, \(f = 1\).
    2. If the statement holds for both (and so for everything between), it's always true.
    3. If it fails for both, it's always false.
    4. If one passes and one fails, it's sometimes true.

      Writing a Big-O proof

      Key idea. A proof of \(f \in O(g)\) declares \(c\) and \(n_0\), takes an arbitrary \(n \ge n_0\), and shows \(f(n) \le c\cdot g(n)\). How you found \(c\) and \(n_0\) is your own scratchwork, and stays out of the proof.

      The shape of a proof

      Show: \(10n + 100 \in O(n^2)\).

      Technique: find \(c > 0\) and \(n_0 > 0\) such that for all \(n \ge n_0\), \(10n + 100 \le c\cdot n^2\).

      The section picks \(n_0 = 6\) where the lecture picked 10. Both work (the smallest that works with \(c = 10\) is 4). The proof never has to say how the numbers were found.

      Proof

      Let \(c = 10\) and \(n_0 = 6\). Show that for all \(n \ge 6\), \(10n + 100 \le 10n^2\).

      \[\begin{aligned} &\equiv n + 10 \le n^2\\ &\equiv 10 \le n^2 - n\\ &\equiv 10 \le n(n-1)\end{aligned}\]

      This is true because \(n(n-1)\) is strictly increasing and \(6(6-1) > 10\).

      Method 1: by parts

      Split \(f\) into terms and bound each term by a multiple of \(g\). Then add.

      Why it works: if \(a(n) \le c_a\, g(n)\) for \(n \ge n_a\) and \(b(n) \le c_b\, g(n)\) for \(n \ge n_b\), then \(a(n) + b(n) \le (c_a + c_b)\, g(n)\) for every \(n\) past both, so use \(c = c_a + c_b\) and \(n_0 = \max(n_a, n_b)\).

      Worksheet 1d: \(7n^2 + 3n \in O(n^4)\).

      Scratchwork: for \(n \ge 1\), \(n^2 \le n^4\) and \(n \le n^4\). So \(7n^2 + 3n \le 7n^4 + 3n^4 = 10n^4\). That suggests \(c = 10\), \(n_0 = 1\).

      Proof

      Let \(c = 10\) and \(n_0 = 1\), and consider an arbitrary \(n \ge n_0\). We have \(7n^2 \le 7n^4\) and \(3n \le 3n^4\), since \(n \ge 1\). Adding these, \(7n^2 + 3n \le 10n^4\), as required.

      By parts is awkward for \(\Omega\). For \(\Omega\) each term would need to be at least a positive multiple of \(g\). A term like \(-8n\) or a constant like \(10\) can never be at least \(c\cdot n^2\), so the split fails. For \(\Omega\), drop the terms that only make \(f\) bigger instead.

      Method 2: the squeeze

      Find a function \(f'\) that sits between them, \(f(n) \le f'(n) \le c\cdot g(n)\), and is easy to compare with both. It's a way to choose \(c\) and \(n_0\); it may not show up in the final proof.

      Worksheet 1e: \(n + 2n\log_2 n \in O(n\log_2 n)\).

      Scratchwork: \(n \le n\log n\) as long as \(\log n \ge 1\), which means \(n \ge 2\). Then \(n + 2n\log n \le n\log n + 2n\log n = 3n\log n\). That's \(f' = 3n\log n\), and \(c = 3\), \(n_0 = 2\) works.

      Proof

      Let \(c = 3\) and \(n_0 = 2\). For an arbitrary \(n \ge n_0\): \(n \le n\log n\) (since \(n \ge 2\), \(\log n \ge 1\)) and \(2n\log n \le 2n\log n\). Adding, \(n + 2n\log n \le c\cdot n\log n\), as required.

      Common mistakes

      • Putting the search for \(c\) and \(n_0\) in the proof. The proof declares them, plugs them in, and explains why the inequality holds.
      • Saying "for large \(n\)" instead of giving a number for \(n_0\).
      • Forgetting where a step needs \(n_0\): "\(n \le n\log n\)" is false at \(n = 1\), which is why 1e's \(n_0\) is 2.

      Writing a \(\Theta\) proof

      Key idea. \(f \in \Theta(g)\) means \(f \in O(g)\) and \(f \in \Omega(g)\). So a \(\Theta\) proof is two proofs, and each one gets its own \(c\) and \(n_0\).

      Worked example: \(2n^2 + 5 \in \Theta(4n^2)\)

      Part 1: \(O\)

      Let \(c = 1\) and \(n_0 = 3\). We show that for all \(n \ge n_0\), \(2n^2 + 5 \le c\cdot 4n^2\).

      Start with the left side. \(2n^2 + 5 \le 3n^2\), because \(n^2 > 5\) whenever \(n \ge 3\). And \(3n^2 \le 4n^2\). So \(2n^2 + 5 \in O(4n^2)\).

      Part 2: \(\Omega\)

      Let \(c = \tfrac12\) and \(n_0 = 1\). We show \(2n^2 + 5 \ge c\cdot 4n^2\).

      \(c\cdot 4n^2 = 2n^2\), and \(2n^2 + 5 \ge 2n^2\) for every positive \(n\). So \(2n^2 + 5 \in \Omega(4n^2)\).

      Since both hold, \(2n^2 + 5 \in \Theta(4n^2)\).

      • Why different constants are fine: the two parts are two separate statements. Each has its own "there exist \(c\) and \(n_0\)".
      • Why the \(O\) part needed \(n_0 = 3\): it trades the \(+5\) for an extra \(n^2\), and \(5 \le n^2\) only from \(n = 3\) on.
      • Why the \(\Omega\) part was easy: dropping the \(+5\) can only make \(f\) smaller, and that's the safe direction for a lower bound.

        buildHeap
        
  
        
    
        Key idea. Floyd's buildHeap puts all \(n\) items into the array as given, then calls percolateDown(i) for \(i\) = size down to 1. Working from the bottom up means that when it's \(i\)'s turn, both subtrees under \(i\) are already heaps.
        
  
        

  
        Building a heap from scratch
        
  
        
    
        Suppose you have \(n\) items and want a heap of them. Put them in the array in any order: the shape is already a complete tree, but the order breaks the heap property in many places. Two ways to fix it:
        
    
          
      
        1. Percolate up: insert the items one at a time. Each insert is \(O(\log n)\), so \(O(n\log n)\) in all.
          2. 
      
        2. Percolate down: Floyd's method, below. It's \(\Theta(n)\).
          3. 
    
        
  
        
  
        buildHeap(){
    for(int i = size; i>0; i--){
        percolateDown(i);
    }
}
        

  
        Why this order
        
  
        
    
          
      
        • percolateDown(i) needs heaps below \(i\). It only moves one item. It works when the only thing wrong in \(i\)'s subtree is the item at \(i\) itself.
          • 
      
        • Going from the back guarantees that. Every index below \(i\) is bigger than \(i\), so it was handled earlier. By the time the loop reaches \(i\), both of its subtrees are already heaps.
          • 
      
        • The leaves cost nothing. Indices \(n/2+1\) to \(n\) are leaves: one-node subtrees are already heaps, and percolateDown returns at once. The first index that can move is \(n/2\).
          •

        Why buildHeap is \(\Theta(n)\)
        
  
        
    
        Key idea. A node can only percolate down as far as the height of its subtree, and most nodes sit near the bottom. Adding up "most moves × how many nodes" gives at most about \(n\) moves, so buildHeap is \(\Theta(n)\), not \(\Theta(n\log n)\).
        
  
        

  
        Count by level
        
  
        
    
        "\(n\) calls, each up to \(\log n\)" gives \(O(n\log n)\), which is true but not tight. Count more carefully, by height above the bottom:
        
    
          
      
        • When \(i\) is a leaf: 0 moves. About \(\frac n2\) nodes are leaves.
          • 
      
        • Second-from-last level: at most 1 move. About \(\frac n4\) nodes.
          • 
      
        • Third-from-last level: at most 2 moves. About \(\frac n8\) nodes.
          • 
      
        • …and the root: at most \(\log_2 n\) moves, 1 node.
          • 
    
        
    
        \[0\cdot\frac n2 + 1\cdot\frac n4 + 2\cdot\frac n8 + \dots + \log_2 n\cdot 1 \;=\; n\sum_{i=0}^{\log_2 n}\frac{i}{2^{i+1}} \;\le\; n\sum_{i=0}^{\infty}\frac{i}{2^{i+1}} \;=\; n.\]
        
    
        Each move costs at most two comparisons (one between the children, one with the moving item), so that's at most \(2n\) comparisons: the \(2n\) in the lecture's bound. Either way it's \(O(n)\). And buildHeap has to look at every item at least once, so it's \(\Omega(n)\) too. So \(\Theta(n)\).
        
  
        

  
        See the levels

        The bars show where the work is: in the low levels, which have many nodes but few moves each, and the high levels, which have big moves but few nodes. Neither end adds up to much.

        Definitions
        
      
        \(f\in O(g) \iff \exists c>0\ \exists n_0>0\ \forall n\ge n_0:\ f(n)\le c\, g(n)\)
        
      
        \(f\in \Omega(g) \iff \exists c>0\ \exists n_0>0\ \forall n\ge n_0:\ f(n)\ge c\, g(n)\)
        
      
        \(\Theta(g) = O(g)\cap\Omega(g)\). Read them as \(\le\), \(\ge\), \(=\) for large \(n\), up to constants. \(c\) ignores scale; \(n_0\) ignores small inputs.
        
      
        Write \(3n^2+17 \in O(n^2)\) or \(= O(n^2)\), never \(O(n^2) = 3n^2+17\).
        
    
        
    
        
      
        Writing a proof
        
      
          
        
        1. Scratchwork: from \(f(n) \le c\,g(n)\), pick a convenient \(c\), solve for \(n\).
          2. 
        
        2. Proof: "Let \(c = \_\), \(n_0 = \_\). Let \(n \ge n_0\) be arbitrary." Then reversible steps, or a chain of \(\le\).
          3. 
        
        3. If \(c\) fails for every \(n\) (like \(-50 \ge 0\)), change \(c\), not \(n_0\).
          4. 
        
        4. \(\Theta\): an \(O\) proof and an \(\Omega\) proof, each with its own \(c, n_0\).
          5. 
      
        
      
        By parts (for \(O\)): bound each term by \(c_i\,g\), use \(c = \sum c_i\), \(n_0 = \max n_i\). Squeeze: \(f \le f' \le c\,g\).
        
    
        
    
        
      
        Drop / keep
        
      
        Drop: lower-order terms, multiplicative constants, log bases.
        
      
        Keep: exponents (\(n^3 \notin O(n^2)\)), bases of exponentials (\(3^n \notin O(2^n)\)), the logs themselves.
        
      
        \(2^{n+1} = 2\cdot2^n \in \Theta(2^n)\), but \(2^{2n} = 4^n \notin \Theta(2^n)\). Test: is \(f/g\) bounded?
        
    
        
    
        
      
        Growth ladder (slowest first)
        
      
        \(1 \;<\; \log n \;<\; n^{1/10} \;<\; n \;<\; n\log n \;<\; n^2 \;<\; n^3 \;<\; n^{50} \;<\; 1.1^n \;<\; 2^n \;<\; 3^n\)
        
      
        Each is \(O\) of the next but not \(\Omega\) of it.
        
    
        
    
        
      
        Case vs. bound
        
      
        Case (best, worst, average, amortized) picks which function. \(O/\Omega/\Theta\) say what you know about it. Any pairing is allowed. Prefer \(\Theta\) when you know it. Use asymptotics for algorithms, timing for implementations.
        
    
        
    
        
      
        Priority queue ADT
        
      
        insert(item, priority), extract (smallest priority first), isEmpty. Ties: any order.
        
      
        Unsorted array/list: insert \(\Theta(1)\), extract \(\Theta(n)\). Sorted: insert \(\Theta(n)\), extract \(\Theta(1)\). BST: \(\Theta(n)\) both. Heap: \(\Theta(\log n)\) both.
        
    
        
    
        
      
        Binary min-heap
        
      
        Shape: complete tree, height \(\lceil\log_2(n+1)\rceil - 1 \in \Theta(\log n)\). Order: every node \(\le\) its children; min at the root.
        
      
        insert: next open spot, then percolate up (swap with parent while smaller). extract: save root, move last item to root, size−−, percolate down (swap with the smaller child while bigger).
        
      
        Change key (min-heap): decrease → up, increase → down. Max-heap: the reverse.
        
    
        
    
        
      
        Array layout (root at index 1)
        
      
        parent \(i/2\) · left \(2i\) · right \(2i+1\) · leaves \(n/2 + 1\) to \(n\) (integer division). Index 0 unused.
        
      
        buildHeap: for (i = size; i > 0; i--) percolateDown(i); Moves \(\le 0\cdot\frac n2 + 1\cdot\frac n4 + 2\cdot\frac n8 + \dots \le n\): \(\Theta(n)\). Repeated insert: \(\Theta(n\log n)\).
