Run. A run of a program is a single execution of it, from the first line of main to the exit, on one particular input.

    
Counterexample. A single run on which a claim about every run is false. It shows that the claim does not hold.

  

  

    
A program that reads input has as many runs as there are things a user might type, so infinitely many. "It reads a list of numbers and prints them and their sum" is a claim about every run. One run can only confirm it for that run. One run where it is false refutes it.

Specification. A specification says what a piece of code must do on every run, as seen from outside it. It says nothing about how the code does it.

    
For a whole program, outside means the user, and the specification is a precise version of the user manual.

  

  

    
    
      
  • On every run is what the first sentence got wrong. One run where a specification is false refutes it. When there are infinitely many runs, no number of runs where it happens to be true can establish it.
    • 
      
  • As seen from outside is why the specification never mentions list, sum, hasNextInt or line 15. A user manual is for someone who will never see the code.
    • 
      
  • Must: a specification states what the code is required to do, and the code meets it or fails it. Here we described an existing program. More often the specification comes first and the program has to live up to it.

Assertion. An assertion is a true or false claim about the program's state (the values of variables and memory) at a particular point in the program.

    
An assertion holds if the claim is true at that point on every run. One run where it is false, and it does not hold.

  


  

    
We write an assertion in double braces at the point it describes. Three things it is not:

    
    
      
  • Not Java. The braces never execute. Java's own assert statement checks a condition on the one run that reaches it.
    • 
      
  • Not a print statement, which shows only what particular runs do.
    • 
      
  • Not a test, which checks only the runs you chose to try.
    • 
    

    
Like a specification, an assertion claims something about all the runs at once. The stepper above checks the claim on one run. Knowing it holds takes an argument about the code, which comes next.

At (2), the obvious claim is about sum. Line 20 also depends on a second claim that often goes unstated: list still holds what it held at (1). It holds because the summing loop only reads list. A program that changed list while summing it could print two lines that disagree.

Reasoning between assertions


  
Outside and inside

  

    
The specification makes two promises after the prompt. The assertions say why the code keeps them. Click a printed line.

  

  

    

    
Click "Got …" or "The sum of your list was: …" above.

  

  

    
Specification · what the user will see. Outside the program, on every run.

    
Assertions · why the code delivers it. Inside the program, at one point, on every run. The user never sees them.

  


  
The rule

  

    
Both arguments about Sum had the same shape: a claim before some code, the code, and a claim after it. This is the pattern of nearly every argument about programs this quarter.

  

  

    
Before{{ P }}

    
The codesome code

    
After{{ Q }}

  

  

    
Reasoning between assertions. Suppose P holds at its point. Suppose also that running the code from any state in which P is true ends in a state in which Q is true. Then Q holds at its point.

  

  

    
The rule is powerful because of what it leaves out. To establish Q we needed only P and the few lines between them, nothing about how the program got to P. Whatever happened earlier is summarized by P. That is why a large program can be understood a few lines at a time.

    
Our two arguments were in prose ("the loop added each element once"). That is fine for a loop this obvious. Making it precise for any loop is the work of the reasoning lectures later in the course.

  


  
The two arguments in Sum

  

    

      
P{{ nothing yet: list is empty, the user may type anything }}

      
codelines 10–12: the input loop

      
Q = P′{{ (1): list holds, in order, every number typed before the end or a non-int }}

      
codelines 14–18: print, sum = 0, the summing loop

      
Q′{{ (2): sum is the wrapped sum of list }} {{ list unchanged }}

    

    
The second argument starts from (1). It needs nothing about the input loop, because (1) summarizes it.

  


  

    
Quick check: the summing loop on lines 16–18 reads list but never writes it. Does the claim at (1) about list still hold at (2)?

    

    

  


  

    Teaching notes
    
    
      
  • Say the mapping in one breath: line 14 keeps the first promise because of the assertion at (1); line 20 keeps the second because of both assertions at (2).
    • 
      
  • The {{ P }} code {{ Q }} shape is Hoare's (1969), building on Floyd (1967). Students will meet it formally as Floyd-Hoare logic in week 3.
    • 
      
  • Ask: "What would we have to re-check at (2) if someone changed the input loop?" Only the claim at (1). That is the point of "summarized by P".

The edge of the program


  

    
Everything a program knows about the world arrives through its input. At that edge there is no one to make promises. The person at the keyboard may type a word, nothing at all, or a whole pasted file. They did not read the code and owe it nothing. So a whole-program specification must not begin "assuming the user types numbers". It has to say what happens on every input.

    
Sum's answer to a word is to stop reading and print what it has. Complaining about the word, or skipping it and going on, would be reasonable too. Having no answer at all is not.

hasNext only checks that more input is waiting. hasNextInt checks that the next thing is an int. With hasNext, nextInt runs on hello and throws.

    
A stack trace is a message from the language to the programmer: the exception, the method that threw it, and the line of our code that led there. To someone who can read the code it is the start of a repair. To the person who typed hello it says nothing they understand, nothing about what to do next, and it ends the run without the output they came for.

  


  

    
Our standard, all quarter. Every input a user can produce gets a response the specification describes. A stack trace is never that response. It is a message meant for someone else.

How do you come to know


  

    
The lecture ended with two kinds of claim about every run: a specification from outside and assertions from inside. It has not said how anyone comes to know such a claim holds. That question is what the rest of the course is about. We have already used all three ways.

  


  

    
Run it
Run the program and watch, as we did with 3 4 5.
Tells you about that run, and nothing about any other.

    
Test it
Choose runs on purpose, ordinary ones and the ones a user manual might forget, and check each against the claim: a word, nothing, the top of the int range.
Can refute a claim about every run. Can never confirm it.

    
Reason about it
Argue from the code that the claim is true on every run at once, as we did at (1) and (2).
Can confirm a claim about every run, if the argument is right. A test that refutes the claim refutes the argument too.

Exercise 3: saying more, saying less

    
Compare statement B from exercise 2 with the course's specification for Sum. Which tells a user more, and does that make the other one useless? Then ask the same two questions of these two assertions, both of which hold at point (2):

A specification for a method

  

    
A method's runs are its calls. So a method's specification says what every call must do, as seen from the code that makes the call. Code that calls a method is a client of the method: main is a client of sumList.

  

  

    
A program's user owes it nothing. They may type anything at all, so the user manual has to cover every input.

    
A method's client can be held to a promise. It is code, written by a programmer who can read the specification. So a method's specification has two parts: what it asks of its client, and what it promises in return.

  

  

    
Method specification. A method specification has a precondition, an assertion at the point where the method is called, and a postcondition, an assertion at the point where it returns or throws. The client must make the precondition true. The implementer must make the postcondition true and may assume the precondition.

    
A method meets its specification if every call that begins with the precondition true ends with the postcondition true.

  

  

    
On a call that breaks the precondition, the specification promises nothing: the method may return any value, throw any exception, or never return, and it still meets its specification. A whole program can't ask that of its user, since no one can hold a user to a promise. That's why last lecture's exercise 7 rejected a specification that began "the user must type only whole numbers". Put a client in place of the user, and the same sentence is an ordinary precondition.

    
Homework 1 says an implementation satisfies its specification where these notes say meets. The two words mean the same thing.

A specification that promises more is met by fewer implementations. That gives a way to compare two specifications directly.


  

    
Stronger and weaker. An assertion P is stronger than an assertion Q if Q is true whenever P is. A specification S1 is stronger than a specification S2 if every implementation that meets S1 also meets S2.

    
In either case the second is weaker than the first, and two that are neither stronger nor weaker than each other are incomparable.

  

  

    
Last lecture's exercise 3 made this comparison without the name. Every program that meets our specification for Sum also meets statement B ("it prints the numbers it read, and then a whole number"), and not the reverse. So our specification is the stronger one.

  


  

    
The rule. S1 is stronger than S2 when S1's precondition is weaker than or the same as S2's, and, on every call where S2's precondition is true, S1's postcondition is stronger than or the same as S2's.

Which is better?

  

    
A stronger specification promises more, so the strongest can seem best. But every promise binds the implementer. B obliges indexOf to find the first match; D lets it search from whichever end suits the arrays it will see. A weaker specification leaves the implementer more choices, and every choice it allows is a case the client must handle.

  

  
A good specification rules out exactly the implementations its clients cannot use.

    Motto
    
      
    Your job is to deliver code that you know works.
    
      
    Works: meets its specification on every run, not only the runs you tried.
    
    
    
    
    
      
    Runs
    
      
    Run: one execution, first line of main to exit, on one input.
    
      
    Counterexample: one run where a claim about every run is false. It refutes the claim.
    
    
    
    
    
      
    Specification
    
      
    What code must do on every run, as seen from outside. Nothing about how.
    
      
    Whole program: outside = the user; spec = precise user manual.
    
    
    
    
    
      
    Assertion
    
      
    A true/false claim about program state at one point, written {{ … }}.
    
      
    Holds = true at that point on every run. Not Java's assert, not a print, not a test.
    
    
    
    
    
      
    Reasoning between assertions
    
      
    {{ P }} code {{ Q }}: if P holds and the code takes any P-state to a Q-state, then Q holds. Needs only P and the code between.

    Java facts used
    
      
    Math.abs(Integer.MIN_VALUE) is Integer.MIN_VALUE (−2147483648).

    hasNextInt(): is the next token an int? hasNext(): is there any token? nextInt() on a non-int throws InputMismatchException.
    
    
    
    
    
      
    The standard
    
      
    Every input a user can produce gets a response the specification describes. A stack trace is never that response.
    
    
    
    
    
      
    Method specification
    
      
    Client: code that calls a method. Precondition: the client makes it true. Postcondition: the implementer makes it true, and may assume the precondition.
    
      
    Meets: every call that begins with the precondition true ends with the postcondition true. A call that breaks the precondition gets no promise.
    
    
    
    
    
      
    Javadoc tags
    
      
    
        
    @param, @requiresprecondition
    
        
    @return, @throwspostcondition (result, exception)
    
        
    @modifies, @effectspostcondition (which parameters change, how). No @modifies = changes nothing.
    
      
    
    
    
    
    
      
    Procedural abstraction
    
      
    Use a method through its specification alone. Clients rely on nothing it doesn't promise; the implementer may change anything it doesn't promise. The specification is the abstraction barrier.
    
      
    Across a call: {{ pre }} call {{ post }}, last lecture's P, code, Q rule.
    
    
    
    
    
      
    Stronger and weaker
    
      
    S1 stronger than S2: every implementation meeting S1 meets S2. Rule: S1's precondition weaker or same, and where S2's precondition holds, S1's postcondition stronger or same.
    
      
    Strengthening can break the implementation, never a client. Weakening can break a client, never the implementation.
    
      
    Correct client: works with every implementation that meets the specifications it relies on.
