Lecture 12 · JavaScript in the page · Mon Oct 26 · notes: Two programs

Two programs

<!DOCTYPE html>
<html>
<head>
  <title>Guestbook</title>
</head>
<body>
  <h1>Guestbook</h1>
  <ul id="messages">
  </ul>
  Name: <input id="name">
  Message: <input id="message">
  <button id="post">Post</button>
  <script src="app.js"></script>
</body>
</html>

The second guestbook keeps the same book on the server and moves the work of building the page into the browser. Line 13's <script> tag points at app.js: the browser asks for it and runs it. So the guestbook is now two programs, the Java server and a JavaScript program in the page. The page holds no messages; the list arrives empty to every visitor.

One visit prints four requests: GET /, GET /app.js, GET /api/messages (from app.js, asking for the messages), GET /favicon.ico. Posting prints POST /api/messages, and the server sends no page back: the program changes the page already drawn, in place.

Three questions follow. How does a program change a page the browser has already drawn? What does it do while the server is slow? What does the program in the browser know about the server?

Quick check: how many requests does one visit to the second guestbook send (with a browser that asks for its icon)?

Lecture 12 · Mon Oct 26 · notes: The page is a tree

The page is a tree

DOM (Document Object Model). The page as the browser keeps it: a tree with one node per tag, that a program in the browser can read and change. When the tree changes, the browser redraws the page from it.

An id names a tag so a program can find it. In the browser's console, document.getElementById("messages") finds the list, and setting its innerHTML = "<li>hi</li>" replaces its children: the page shows hi, and no request is sent. The change is in your browser's tree and nowhere else.

// Puts the messages on the page, one list item each, in place of
// whatever the list held before.
function show(messages) {
  const list = document.getElementById("messages");
  list.innerHTML = "";
  for (const message of messages) {
    const item = document.createElement("li");
    item.textContent = message;          // line 13
    list.appendChild(item);
  }
}

Read as Java: function starts a function with no types; const declares a variable that will not be reassigned; the loop says of where Java says :. Line 13 sets textContent, not innerHTML: the characters go into the tree as text, so a tag in a message shows as typed and nothing is parsed. Setting text and not HTML closes the cross-site scripting hole of the first guestbook for free.

Quick check: a message is <b>hi</b>. With line 13 as written, what does the page show?

Teaching notes
  • Have students open the console on a news site and change a headline's innerHTML: nothing on the server changes, and nobody else sees it.

Lecture 12 · Mon Oct 26 · notes: Asking the server, What fetch returns

Asking the server

// Asks the server for the messages, and shows them.
async function load() {                              // line 19
  const response = await fetch("/api/messages");     // line 20
  const messages = await response.json();            // line 21
  show(messages);                                    // line 22
}

fetch sends a request to the server the page came from: here GET /api/messages. The server answers this path with the messages as data: curl shows ["ada: hello"].

JSON. A way of writing a value as text (a list in square brackets, a string in double quotes, …) that programs in any languages can read back as a value.

Promise. A value that stands for a result that may not have arrived yet. await before a promise waits until the result arrives and gives the result itself. Inside a function, await is allowed only if the function is declared async.

In the console, fetch("/api/messages") prints Promise {<pending>}: it returns at once, before any response. Reading the body is slow too, so response.json() returns a promise as well: two awaits. Leave async off load and the browser refuses the whole file (Uncaught SyntaxError: await is only valid in async functions…): nothing in it runs. A response also has a status (200, or 404 for a path the server lacks), and a request can get no answer at all; each is a different failure the program must decide how to handle.

Quick check: after ada posts hello and bob posts hi, what does curl http://localhost:9331/api/messages print? (The server's json joins with a comma and a space.)

Teaching notes
  • The console is looser than files: it allowed await outside any function. The rule is for code you write and turn in.

Lecture 12 · Mon Oct 26 · notes: Posting

Posting

// Sends the name and message typed in, and shows what comes back.
async function post() {
  const fields = new URLSearchParams();
  fields.append("name", document.getElementById("name").value);
  fields.append("message", document.getElementById("message").value);
  const response = await fetch("/api/messages", {
    method: "POST",
    body: fields,
  });
  const messages = await response.json();
  show(messages);
  document.getElementById("message").value = "";
}

document.getElementById("post").onclick = post;      // line 39
load();                                              // line 40

A URLSearchParams is a map from names to strings; .value is what the user typed. fetch's second argument, an object in braces, says the method is POST and the body is the fields, encoded as the first guestbook's form encoded them, so the server reads them with the same parseForm. The server answers a POST with the messages, so post redraws from the answer.

Line 39 sets the button's onclick to the function post itself, with no parentheses: handed to the browser as a value, as main handed handle to HttpServer. A click is then an event, and post is what the browser runs for it. Line 40 calls load once; after that, nothing runs until an event. Refresh after posting now sends three GETs and no POST: the page came from a GET.

Quick check: you post a message, then press refresh. How many POST requests does the refresh send?

Teaching notes
  • load and post are both async because each has an await; show is ordinary.

Lecture 12 · Mon Oct 26 · notes: One thing at a time

One thing at a time

Slow the server down by ten seconds on /api/messages. The page appears at once with an empty list; during those ten seconds, while load waits at line 20, you can type and press Post, and post runs and sends its POST. Yet the browser runs your program on one thread, never two functions at once. How can both be true?

Event loop. The browser runs a program in the page from a loop: wait for an event, run the function registered for it (its callback), wait again. A click is an event; a response arriving is an event.

Concurrency. A program is concurrent when more than one task is in progress at once and the order of their steps is not the program's to choose. In the browser one callback runs at a time, and a function gives up its turn only at an await.

At an await, the function returns to whoever called it (for a callback, the loop), with its place marked; it returns a promise, as every async function does. When the result arrives, the rest of the function runs as a callback. So await cuts a function in two, and load, with two awaits, runs in three pieces. Choose an order of events below.

Three things follow. At an await, control goes back to the loop and then to whatever event is next; you know only where your function will resume. After an await, anything another callback can reach (a global, an object both can see, the page's tree) may have changed. And the figure is one possible run: each order of events is another run, and a test that posts and sees the message confirms one order only. So treat an await as a method boundary in disguise: make the invariant true before it, and assume only the invariant after it, as with a class's RI.

Quick check: into how many pieces do post's awaits cut it?

Teaching notes
  • Half sheet, question 1 (3 minutes): JavaScript runs one thing at a time. Yet while load waits for the server, a click on Post runs post. How? The server is a loop too; so is the browser.
  • The widget draws each function's last two pieces as one box, as the notes' figure does.

Lecture 12 · Mon Oct 26 · notes: Who is the client?

Who is the client?

For the request load sends, the program in the browser is the client: it calls the server as code calls a method, with a request for a call and a response for a return value. The server is the implementation, and the specification between them is the server's manual:

 * Four kinds of request reach the program:
 *   GET /               the page, index.html, as it is on disk
 *   GET /app.js         the page's program, app.js, as it is on disk
 *   GET /api/messages   the messages posted so far, as JSON
 *   POST /api/messages  adds the message the fields send, then the
 *                       messages posted so far, as JSON

handle now answers by path: files for / and /app.js (read the bytes, send the bytes), JSON for /api/messages, and 404 for anything else, the icon included. The JSON is written by hand: each message in double quotes with backslash, quote and newline escaped, joined with commas inside brackets.

The client knows only the manual. And the manual promises "as JSON", not that the JSON is a list, of strings, each a name, a colon and the message. show relies on all three: on what the server happens to send. Change the server to a list of objects and it still satisfies the manual, the old app.js still runs, and every list item reads [object Object]. No compiler sees both programs. A good manual promises the shape; many teams write it in a form a tool can check, a schema.

Quick check (the half sheet's question 2): line 20 of app.js sends a request. Which program is the client?

Teaching notes
  • Web systems often break exactly this way: the spec leaves the shape open, clients rely on what the server sent, the server changes it.

Section 4 · ADTs · Tue Oct 27 · Task 1, with the official solution

Task 1: MutableIntSet's specs

/** Represents a **mutable** integer set, or a collection of distinct integers. */
public class MutableIntSet {
    /** @return true if n is in the set, false otherwise */
    public boolean contains(int n);
    /** Adds n to the set if not already present.
     *  @modifies this
     *  @effects this is unchanged if this_0 contains n
     *           otherwise, this contains all of this_0 and n */
    public void add(int n);
    public boolean remove(int n);   // spec to write
}

Let T have the abstract state {1, 2, 3}.

  • T.add(3). It changes nothing. @modifies says what may change; it is not a promise that anything does.
  • A static add(old, n) that returns a new set and has no @modifies promises not to change old; the instance add changes this.
  • Forward reasoning: after T.add(4); T.add(2); T.add(0); the state is {0, 1, 2, 3, 4}.
  • remove's spec, one solution: @modifies this; @effects if this_0 contains n, this = this_0 with n removed, otherwise this = this_0; @return true if this_0 contains n, false otherwise.

Quick check: from {1, 2, 3}, after add(4), add(2), add(0), how many elements does T have?

Teaching notes
  • The spec writes this_0 for the abstract state at the call, as Lecture 11's rule did.

Section 4 · Tue Oct 27 · Task 2, Rich AF

Task 2: three representations

All three use private int[] elems; private int size; and the same AF, this = this.elems[0 .. size] (the first size elements, as an ArrayList would). They differ in the RI:

(1)no RI
(2)RI: elems[0..size] contains no duplicates
(3)RI: elems[0..size] is sorted by <=

For each method, which representations make it satisfy MutableIntSet's spec (and keep the RI)?

contains by Arrays.binarySearch(3) only: on an unsorted array binary search may miss an element that is there.
contains by a loop(1), (2) and (3): it needs no RI.
add (append if not contained, growing the array)(1) and (2): trivially for (1); it never adds a duplicate, so (2)'s RI holds. Not (3): appending breaks sortedness.
remove (shift left over the first match)(2) only: it preserves no-duplicates. (1) and (3) can hold duplicates, so removing one occurrence may leave another copy in the set.

Quick check: for which representations does the binarySearch contains satisfy its spec? (Type the numbers, e.g. 1, 2.)

Teaching notes
  • The same AF with different RIs: the RI decides which method bodies are correct, as in Lecture 11's "which method is wrong?".
  • The answers here were checked by brute force on every small array the RI allows.

Section 4 · Tue Oct 27 · Task 3, Almond Joy

Task 3: removeUntil

// AF: AF(this) = this.snacks[0 .. size] and top = this.snacks[size - 1]
// RI: 0 <= this.size <= this.snacks.length
/** Removes snacks from the top of this until an "Almond Joy" is encountered.
 *  The "Almond Joy" is not removed.
 *  @modifies this
 *  @effects removes all elements above the first occurrence of "Almond Joy"
 *           (from the top); if no "Almond Joy" exists, removes all elements
 *  @return true if an "Almond Joy" was encountered, false otherwise */
public boolean removeUntil() {
  {{ P0: 0 <= size <= snacks.length and size = size_0 }}
  {{ Inv: this.snacks[size .. size_0] does not contain "Almond Joy"
      and 0 <= size <= snacks.length and size <= size_0 }}
  while (size != 0) {
    String top = this.snacks[size - 1];
    if (top.equals("Almond Joy")) {
      {{ P1: Inv and size != 0 and top = snacks[size - 1] and top = "Almond Joy" }}
      return true;
    }
    size--;
  }
  {{ P3: Inv and size = 0 }}
  return false;
}
  1. Check (1). With size = size_0, snacks[size .. size_0] is empty, so it contains no Almond Joy; the bounds come from P0.
  2. P1 implies the postcondition. top = snacks[size - 1] is an Almond Joy, and by Inv nothing in snacks[size .. size_0] is: it is the first from the top. By the AF, AF(this_0) = snacks[0 .. size_0] and AF(this) = snacks[0 .. size]: exactly the elements above it are gone. The RI holds by Inv.
  3. Check (2). After size--, snacks[size .. size_0] is [top] ++ snacks[size_1 .. size_0], and top is not an Almond Joy; 0 < size_1 gives 0 <= size.
  4. Check (3). With size = 0, Inv says snacks[0 .. size_0], all of AF(this_0), held no Almond Joy, and AF(this) is empty: all removed, return false.

Quick check: snacks = {"Kit Kat", "Almond Joy", "Twix", "Mars"} and size = 4. What is size after removeUntil()?

Teaching notes
  • The official write-up justifies the last fact, size <= size_0, "from size = size_0 in P2", but P2 has size = size_1 - 1; the fact follows from size_1 <= size_0. Worth pointing out when you walk check (2).

Lecture 13 · Exceptions · Wed Oct 28 · notes: Where does control go from here?

Where does control go from here?

An exception is a second way for a call to end, and it changes where control goes, and so where a run can be when it reaches a line. In Trace, main calls f twice, f calls g, and g divides 12 by its argument, throwing when it is 0. Nothing catches. Write down what it prints, then step through it.

Call stack. A frame is what Java keeps for one call while it runs: its variables and the line it is at. The call stack is the frames of the methods called and not yet returned, newest on top. A call pushes a frame; a return pops the top frame, and the method below continues after the line its frame recorded.

After the exception, most people expect f: done or main: done to print. Neither does. The trace is the stack: g at line 27, the throw; f at line 21, where it called g; main at line 15. Stand on line 21: control can go to line 22 (when g returns) or leave f (when g throws), and nothing on the line says which. Every call is a place control can come back to, and a place it can leave through.

Quick check (the half sheet's question 1): how many lines does Trace print on standard output, before the exception's trace?

Teaching notes
  • Half sheet, question 1 (3 minutes): Write what Trace prints, one line of output per line. Two minutes alone, then one with a neighbor.
  • A stack trace is a message from the language to the programmer, never one a user should see. Now students can read it frame by frame.

Lecture 13 · Wed Oct 28 · notes: How can control reach this point?

How can control reach a catch?

TraceCatch puts main's two calls in a try with a catch (ArithmeticException e) that prints the message. While control is inside the try, main's frame carries a handler, drawn as a tab. Predict the output, then step.

How a throw finds its catch. A throw looks for a handler frame by frame down the stack, starting with its own frame. If the line that frame is at sits inside a try with a catch for the exception's class, control goes to that catch block, and the method goes on after the try statement. Otherwise the method ends, its frame comes off, and the frame below is next. If no frame is left, Java prints the stack trace and the program stops.

So control can reach line 13 one way only: a throw of an ArithmeticException from somewhere inside main's try: from f, from g, or anything they call. Where the catch sits on the page does not matter; the stack does. Two easy things to miss: a method can be ended by an exception it never mentions (f has no throw and no catch), and after the catch block, nothing after the try can tell whether the block finished or was cut short.

Quick check (the half sheet's question 2): in TraceCatch, does f: done print for the call f(0)?

Teaching notes
  • Half sheet, question 2: Does f: done print for f(2)? For f(0)? Does main: done print? (Yes, no, yes.)

Lecture 13 · Wed Oct 28 · notes: A block that runs either way

A block that runs either way

TraceFinally puts f's call to g in a try with no catch, only a finally that prints f: finally. main keeps its catch.

On the first call, g returns, the try block ends, and the finally block runs: f: finally before f: done. On the second, g throws; f has no catch for it but has a finally, which runs on the way out, whichever way out it is: f: finally prints with the exception still in flight, then the exception goes on to main's catch, and f: done never prints.

That is what a finally is for: work that has to happen whether the try block finished or threw, such as closing a file. A try with a resource in its parentheses (Lecture 3's Sum) is a finally that closes it, written for you. For reasoning, a finally block is a point with two ways in: a claim at its top holds only if it is true both ways.

Quick check: how many times does TraceFinally print f: finally?

Teaching notes
  • Ask how control can reach line 23: by g returning, or by g throwing.

Lecture 13 · Wed Oct 28 · notes: The class in a catch

The class in a catch

A catch for a class takes an exception of that class or of any class that extends it. That one fact makes a catch a design decision.

One catch for a family. The calculator is redone with every user-caused failure an exception: CalcStack's specs name StackEmptyException, TooFewOperandsException and DivideByZeroException, all nested in the interface and all extending one class, CalcException (which extends RuntimeException). The specs and tests use the three subclasses; the app's main catches only CalcException, around one call per command, step(stack, token): the one place a user's mistake becomes a message. Without that try, 6 0 / ends in Exception in thread "main" CalcStack$DivideByZeroException (Java writes a nested class's name with $).

The first catch that matches takes it. With several catch blocks, Java takes the first whose class matches, in written order. A catch for a subclass after one for its superclass can never run, and the compiler says so: error: exception DivideByZeroException has already been caught. Put the narrow class first.

The widest catch takes everything. TraceSwallow catches Exception with an empty block. Step it: the division by zero is gone, with no message, no trace, exit status 0, and main: done at the end, as on a good run. The error is still there for the next person. Reading 3's paper on production failures (Yuan et al., OSDI 2014) found that in 35% of the catastrophic failures it studied, the handler was trivially wrong: empty, a log line and nothing else, a catch of everything followed by an exit, or a TODO.

Lecture 13 · Wed Oct 28 · notes: What is true at a catch?

What is true at a catch?

A catch block is a point with many ways in: every throw of its class under its try, in the method and in every method it calls. So a claim at a catch holds only if it is true at every one of those throws.

divide's spec describes two exits: @effects for the normal one, and for each exceptional one a @throws clause ending "and leaves the stack unchanged": a postcondition for the exceptional exit. ListStack keeps it by checking before it changes anything: it asks top() before it pops. A first draft, DraftStack, pops both numbers and then checks the divisor:

ListStack.divide

if (items.size() < 2) {
    throw new TooFewOperandsException(
        "need two numbers to divide");
}
if (top() == 0) {
    throw new DivideByZeroException("cannot divide by zero");
}
int b = pop(); int a = pop();
push(a / b);

DraftStack.divide

if (items.size() < 2) {
    throw new TooFewOperandsException(
        "need two numbers to divide");
}
int b = pop(); int a = pop();
if (b == 0) {
    throw new DivideByZeroException("cannot divide by zero");
}
push(a / b);

On a zero divisor the draft throws the right exception with the right message, and four of the five spec tests pass. divideByZeroThrowsAndLeavesTheStack fails: expected: <[6, 0]> but was: <[]>. The user types 6 0 /, reads "cannot divide by zero", types p, and sees [].

A try with a catch. In {{ P }} try { body {{ Q }} } catch (X e) { {{ E }} handler {{ Q }} } {{ Q }}, E must be true at every throw of an X that can reach this catch, in body and every method it calls; Q must come out of both exits. So a method that throws owes its callers at the throw, as at a return, and its @throws clause says what it owes. Check first when you can: then there is nothing to undo.

Readings

Reading 3 asks about the course motto: how much of that knowing happens before the first line of code, and how much of it is worth writing down? Choose one article, read it, and write a reflection. The three answer differently.

About 25 minutes

Parnas 1972, "On the Criteria To Be Used in Decomposing Systems into Modules"

One small system, a KWIC index, built twice: once split by processing step (input, shift, sort, output), once by decision, each module hiding one design decision such as how the lines are stored. Of five likely changes, two touch every module of the first version; each touches one module of the second. Begin not with a flowchart but with "a list of difficult design decisions or design decisions which are likely to change", and hide each inside a module. (Lecture 11 cites it.)

About 35 minutes

Brooks 1986, "No Silver Bullet: Essence and Accidents of Software Engineering"

Accidental difficulties come from the tools of the day; the essential difficulty is the idea of the program itself, a "construct of interlocking concepts", with four properties: complexity, conformity, changeability, invisibility. Past gains removed accidents, so no tool can give a tenfold gain on what remains. Instead, grow software by prototypes and increments, since no client can specify a system completely before trying a version of it.

About 15 minutes

Lamport 2015, "Who Builds a House Without Drawing Blueprints?"

A program's blueprint is its specification. Writing down what you are about to do shows how sloppy your thinking is. A spec need not be formal: about 95% of code can be specified by a couple of prose sentences. It should say everything one needs to know to use the code. Tests catch coding errors and miss design errors. "Thinking does not guarantee that you will not make mistakes. But not thinking guarantees that you will."

Week 5 cheat sheet

The page is a tree

DOM: one node per tag; a program can read and change it, and the browser redraws. getElementById, createElement, appendChild. Set textContent, not innerHTML, for a user's text.

fetch and JSON

fetch(path) returns a promise at once. await it for the response, and await response.json() for the value. await only inside async functions. Check the status.

The event loop

Wait for an event, run its callback, wait again. One callback at a time; a function gives up its turn only at an await. Each order of events is another run. Treat an await as a method boundary.

Two programs

The browser program is the client; the server is the implementation; the server's manual is the spec. Promise the JSON's shape (a schema).

ADTs (Section 4)

@modifies is permission, not a promise. Same AF, different RIs: the RI decides which bodies are correct.

Call stack

A frame per call not yet returned: variables and current line. A stack trace lists the frames, top first.

Throw → catch

Down the stack frame by frame; first matching handler wins; else the method ends. Uncaught: trace, exit status 1. A finally runs either way.

The class in a catch

A catch takes its class and subclasses. Narrow first (else "has already been caught"). catch (Exception e) {} swallows bugs.

At a catch

True at every throw that can reach it. @throws is a postcondition for the exceptional exit. Check before you change anything.
