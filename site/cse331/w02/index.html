Lecture 3 · Mon Oct 5 · first 15–20 minutes

Reading 1 discussion

The course motto is "Your job is to deliver code that you know works." Reading 1 asked what "know" means there. Each student read one of three articles and wrote a reflection before Friday. Today the room compares the answers.

The question. When you say you know your code works, what do you actually know? How did you come to know it?

Willison 2025Watch your code work, then write a test for it. "Proven" here means evidence you can show someone else; neither step is optional, even when a coding agent wrote the code.
Fishman 1996The strict process of the space shuttle's software team: 260 people, three versions of 420,000 lines with one error each, and a process even their manager says stifles creativity.
Hoare 1996Reliable software, though almost none of it is proven. His answer is careful engineering, with testing a large part of it.

Two kinds of testing

Manual testing. You run the program and watch what it does.

Automated testing. Another program runs it and checks the result, every time. A JUnit test is automated, and no AI is involved.

Willison asks for both: first watch the change work, then write an automated test that fails if the change is undone. Lecture 1 gave the other side: testing never confirms a claim about every run, because a test tries only the runs you chose.

Stronger and weaker, again

Lecture 3 returns to the end of Lecture 2 before starting on the new program. The ideas come back in exercise 4, where two user manuals for Sum are compared the same way two method specifications were.

Stronger and weaker. An assertion P is stronger than an assertion Q if Q is true whenever P is. A specification S1 is stronger than a specification S2 if every implementation that meets S1 also meets S2. In either case the second is weaker than the first, and two that are neither stronger nor weaker than each other are incomparable.

The rule. S1 is stronger than S2 when S1's precondition is weaker than or the same as S2's, and, on every call where S2's precondition is true, S1's postcondition is stronger than or the same as S2's.

A specification that promises more is met by fewer implementations. For Lecture 2's indexOf: B (the smallest matching index, or −1) is met by one of the four implementations, D (some matching index, or −1) by two, and A (some match, where one must exist) by all four.

Which is better? Every promise binds the implementer. Strengthening a specification can't break a client, but it can break the implementation. Weakening it can't break the implementation, but it can break a client that relied on a dropped promise. A library with a thousand clients can only make its specifications stronger.

Promises about one run

The same comparison works for a whole program. Take the run java Sum -a with nothing typed, and five programs that respond to it differently. Pick a manual to see which programs keep its promise, then pick a second to compare the two.

Batch programs

  

    
Batch program. A batch program reads its input, computes, writes its output, and exits.

  

  

    
Lecture 1's Sum and this one are both batch programs. A web browser is not: it keeps running and responds to whatever the user does next, until the user tells it to stop. A later lecture takes up programs of that kind.

  


  
Input: more than the numbers

  

    
The words typed after java Sum are input too. The user chooses them, and they change what Sum does. These are Sum's command-line arguments. Java hands them to main as the array args, in the order they were typed, and the loop on line 28 reads them one at a time.

    
    
      
  • An argument that starts with a dash, such as -a or --precision=2, is an option.
    • 
      
  • Any other argument is the name of a file to read the numbers from.
    • 
      
  • With no file named, Sum reads from standard input, by default the keyboard. Lines 89 and 90 make that choice.

    Results go to standard output, and messages go to standard error. fail exits with status 1. Java sets a status even for a program that never chooses one: 0 if main finishes, and 1 if the program ends in a stack trace. In a terminal, though, results and messages look the same, and the exit status does not show at all.
    
  
    

  
    Why keep them apart?
    
  
    
    
    > sends only standard output to a file. The file bad.txt contains 3 x. Predict what each run shows on the terminal and leaves in total.txt, then run the lines one at a time. echo $? prints the status of the last command (on macOS and Linux; in Windows PowerShell, $LASTEXITCODE holds it).
    
  
    
  
    
  
    
    
    The first run shows nothing and leaves 12 in total.txt. The second still shows its message, and leaves total.txt empty. Either way, the file never contains a message where a sum should be. The exit status says which run failed.
    
  
    

  
    Why standard error exists
    
  
    
    
    macOS and Linux are both modeled on an older operating system, Unix. At first, every Unix program printed its messages on standard output. That caused trouble when output went to a file, and worse trouble once pipes let one program's output flow straight into another program as input. At Bell Labs a program's output could go to the lab's typesetter, and its messages went there too. Once, several people typesetting documents got back "a single, beautifully typeset line": cannot open file foobar. Soon after, Dennis Ritchie added standard error.
    
    
    Standard error alone was not quite enough. With several programs in one pipeline, a message also had to say which program wrote it. Sum follows that convention: each of its messages begins with Sum:.
    
  
    
  
    

  
    What a user sees
    
  
    
    
    Three parts. What a user sees of Sum is its standard output, its standard error, and its exit status. Sum's specification has to say what each one is, on every run.
    
  
    
  
    
    
    A person at the terminal reads the first two. A script, a program that runs other programs, can read all three. A script that runs Sum cannot make sense of a message where it expected a number. Such a script is like a client in Lecture 2: it relies on what Sum promises, and it is correct if it works with every version of Sum that keeps those promises. Unlike a method's client, though, the script owes Sum nothing. Like any user, it may give Sum anything at all.
    
  
    
  
    
    
    Expect the output of every program to become the input to another, as yet unknown, program. Don't clutter output with extraneous information.
    
    
    M. D. McIlroy, E. N. Pinson and B. A. Tague, 1978 (often credited to McIlroy alone)
    
  
    
  
    
    
    A message among Sum's results would be that clutter, and standard error keeps it out. "As yet unknown" matters too: Sum's author cannot know which programs will read its output, so whatever they rely on has to be in Sum's specification.

    Checks at the edge
    
  
    
    
    Sum does a lot of checking. Lines 28 to 55 check its arguments, line 61 checks each word of its input, and lines 73 to 75 check that there is something to average. What are those checks for? Take one away and see. The lecture made two changed copies of Sum, each with one check removed and its lines left blank, so every other line keeps its number.
    
  
    

  
    
    
    Remove a check, run the same command
    
    
    
      
      
    
    
    
    
      
    
      
    
    
    
    
    
  
    

  
    A negative precision
    
  
    
    
    With the check, Sum answers a negative precision with a message at once, before it reads any input. Without lines 40 to 43, the negative precision reaches the printf on line 78, which builds its format from the precision. A precision of 2 gives the format %.2f, which prints two digits after the decimal point. A precision of −1 gives %.-1f, which is not a format printf accepts. So the call throws, and the user gets a stack trace.
    
  
    

  
    Nothing to average
    
  
    
    
    Without lines 73 to 75, java Sum -a on empty input does not crash. It prints NaN, short for "not a number," which is what the division on line 76 gives when it divides 0 by 0. Worse, the exit status is 0, so the run reports success. A script that runs java Sum -a and checks the status would take NaN for an average. A crash would at least have said that something went wrong.
    
  
    
  
    
    
    No single right answer, but one wrong one. What should the average of no numbers be? Sum refuses and prints a message; printing 0 would be just as reasonable. But "the one guaranteed wrong answer is to ignore the problem" (Kernighan and Pike). What matters is that the manual says which answer Sum gives, and so far it says neither.
    
  
    
  
    
    
    A program that ignored the problem once stopped a Navy cruiser, the USS Yorktown, at sea for a couple of hours, after a crew member entered a zero and the program divided by it.
    
  
    

  
    Where the checks stand
    
  
    
    
    Checks at the edge. Each check stands at the edge of the program, between the user and the computation. The user owes Sum nothing, so the checks take whatever arrives and pass on only what the computation can handle: a precision that is not negative, and a count that is not zero.
    
  
    
  
    
    
    The userowes Sum nothing; may type anything
    
    
    →
    
    
    main: checks at the edgearguments, each word, the count; a message and status 1 on a mistake
    
    
    →
    
    
    The computationa method whose client is main: it may have a precondition
    
  
    
  
    
    
    That suggests a way to organize a program like Sum: keep the code that deals with the user (the arguments, the messages, the exit status) apart from the code that computes the answer. Sum does nearly all its work in main, both kinds together. For a program of 99 lines, keeping the work there and splitting it up can both be defended.
    
    
    Split it, and Lecture 2 says what the pieces should be: methods with specifications. The checks stay at the edge, in main. A method inside may then have a precondition, such as a count that is not zero, since its client is main, code that can be held to a promise. (Lecture 2's exercise 6 made the same argument; exercise 3 below asks you to do the split.) Homework 1's Task 4 has the same shape: Gradebook is a batch program with its manual at the top of its source.
    
  
    

  
    Nearly every run
    
  
    
    
    The checks pass on only what the computation can handle, nearly. Given any numbers, java Sum -a --precision=2147483647 ends in an OutOfMemoryError and a stack trace at line 78: the format asks for more digits than a Java string can hold. Specifications leave out runs on a computer without the memory to finish, but this run fails on every computer. So the precision has a limit, like the range of an int, and the manual has to state it. Try it in the lab above.
    
  
    

  
    
    
    Quick check: in the copy without lines 73–75, what exit status does java Sum -a leave when nothing is typed?
    
    
    
    
    
  
    
  
    
    
    Quick check: with every check in place, does java Sum -a --precision=-1 bad.txt ever read bad.txt?

    What a test is
    
  
    
    
    The motto asks for code you know works. Code is correct if it meets its specification, so "correct" always means correct against some spec. There are three ways to gain that knowledge: testing (run chosen inputs and check each run), tools (such as a type checker), and reasoning. This lecture is testing.
    
  
    
  
    
    
    Test. A test runs code on a chosen input and checks the actual behavior against the expected behavior, which is what the spec says must happen on that input. It passes if they match and fails if not. A failing test is a counterexample: it refutes the claim that the code works on every run.
    
  
    
  
    Four steps
    
  
      
    
    1. Choose an input.
      2. 
    
    2. Use the specification to find the expected behavior.
      3. 
    
    3. Run the code and observe the actual behavior.
      4. 
    
    4. Compare. Pass if they match.
      5. 
  
    
  
    
    
    Example under spec D with Lecture 2's implementation 1: input {3, 0, 7}, range 0 to 3, x = 7. D promises some index holding 7, and only index 2 holds it, so the expected answer is 2. The code returns 2: pass.
    
    
    Expected behavior first. If you run the code, see 2 and write down 2, the test only checks that the code still returns what it returned before. That has some value (it fails if the answer later changes) but it does not check that 2 is right. A test means as much as its expected answers, and those must come from the spec.
    
    
    An automated test is code that does steps 3 and 4. In Java, @Test marks a JUnit test method, and assertEquals(expected, actual) compares, with the expected value first. A unit test checks one method apart from the rest; an integration test checks pieces together; an end-to-end test runs the whole program.
    
  
    
  
    @Test
void findsTheOnlyMatch() {
    int[] a = {3, 0, 7};
    assertEquals(2, IndexOf.indexOf(a, 0, 3, 7));
}
    

  
    
    
    Quick check: where must a test's expected answer come from: the specification, or the code's output?

    Lecture 4 · Testing · Wed Oct 7
    
  
    Specification-based tests
    
  
    
    
    On {5, 1, 5, 2, 5}, range 0 to 5, x = 5, D allows 0, 2 or 4. Implementation 1 searches from the front and returns 0; implementation 4 returns 4. Two tests:
    
  
    
  
    @Test void findsTheFirstMatch() {
    int[] a = {5, 1, 5, 2, 5};
    assertEquals(0, IndexOf.indexOf(a, 0, 5, 5));
}
@Test void findsSomeMatch() {
    int[] a = {5, 1, 5, 2, 5};
    int i = IndexOf.indexOf(a, 0, 5, 5);
    assertTrue(0 <= i && i < 5 && a[i] == 5);
}
    
  
    
    
    Specification-based test. Checks only behavior the spec promises, so it passes on every correct implementation. An implementation-based test also checks behavior the spec does not promise, so it can fail on a correct implementation. findsTheFirstMatch expects 0, fails implementation 4 (expected: <0> but was: <4>) even though 4 meets D.
    
  
    
  
    
    
    A test is a client too. Exercise 2: under B (smallest), findsTheFirstMatch is specification-based; under C (largest) it fails every correct implementation; under D it is implementation-based. findsSomeMatch is specification-based under all three but checks less than B or C promise. No set of tests confirms a claim about every run: testing can refute, never confirm.

    Lecture 5 · Coverage · Fri Oct 9
    
  
    Statement, branch and loop coverage
    
  
    
    
    The lecture opens on isPrime(n) with eleven tests (2 through 12) chosen from the spec. All pass, and the method is wrong: every input is below 100, so every test is the table lookup and the loop never runs. Line 22 reads k * k < n where it should be k * k <= n, so the square of a prime (121) passes as prime. The number of tests is not what matters; which parts of the method the tests run is. That is coverage. Choosing tests from the code is clear-box testing; from the spec alone, black-box. A method's tests need both.
    
    
    One test is never enough (a method that always returns true passes a test expecting true), so every method needs at least two.
    
  
    

  
    Three measures
    
  
    
    
    Statement coverage. Every statement that some allowed input reaches is run by some test.
    
    
    Branch coverage. Every branch that some allowed input takes is run by some test. An if with no else still has a (empty) false branch.
    
    
    Loop coverage. For every loop, some test runs the body zero times, some once, and some more than once.
    
  
    
  
    
    
    minBody r = a; if (a <= b) r = a; returns a always. min(1, 2) alone has statement coverage and passes; min(2, 1) (false branch) returns 2 and finds the mistake. Branch coverage asks for it.
    
    
    quadrantTwo ifs. Tests (1, 1) and (−1, −1) run every branch and pass, but (1, −1) returns 2 where 4 is promised. Branch coverage misses a combination; every path would find it, but paths multiply (ten ifs give 210 paths).
    
    
    powLoop body is r = b instead of r = r * b. pow(2,0) and pow(2,1) have statement and branch coverage and pass; pow(2,3) returns 2, not 8. A value carried from one run of the body to the next is only checked when the body runs at least twice.
    
    
    recursionCount calls like loop runs: zero, one, more than one. powRec discards the recursive result and returns b; only powRec(2, 3) (more than one call) returns 2 instead of 8.
    
  
    
  
    
    
    Lecture 4's IndexOfTest has statement and branch coverage but no test runs the loop body zero times: the input it lacks is an empty range such as lo = hi = 1.
    
  
    

  
    
    
    Quick check: what is the fewest tests any method needs, whatever its code?
    
    
    
    
    
  
    
  
    
    
    Quick check: the faulty pow has body r = b. What does pow(2, 3) return? (The correct answer is 8.)

    Lecture 5 · Coverage · Fri Oct 9
    
  
    When to stop, and what coverage doesn't tell you
    
  
    
    
    Enough. A method's tests are enough when there are at least two and, between them, they run: every statement; both branches of every if; every loop's body zero, one and more than one times; and every recursive method with zero, one and more than one recursive call. Until the list is complete, it says which test to write next. Only allowed inputs count: a check that a precondition holds is not on the list, because no test may reach it.
    
  
    
  
    
    
      
      
    • The measures nest: loop coverage usually gives branch coverage, and branch gives statement.
      • 
      
    • Coverage is not correctness. Add 100 and 10,007 to the eleven isPrime tests: statement, branch and loop coverage hold and every test passes, yet 121 is still wrong. The test that finds it sits on a boundary read off the code: a perfect square, where k * k == n.
      • 
      
    • A mistake of omission (a case the spec describes that the code never handles) has no statement to run. Tests for it come from reading the spec case by case.
      • 
      
    • Some mistakes are outside the list: the Therac-25's came from the timing of two tasks.
      • 
      
    • The floor. The list, plus Lecture 4's cases and boundaries, is the least testing that any code you deliver gets. Above it, how much more depends on the cost of a mistake. Apple's goto fail (statement coverage would have shown the unreachable lines) and Heartbleed (a boundary test would have found the unchecked length) are the lecture's examples of skipping it.
      • 
      
    • Test code is code. Keep tests simple: one call and one assertEquals. Write methods that are easy to test: one job each, nothing read or written outside the arguments and return value (Lecture 2's sumList split).
      • 
    
    
  
    

  
    Exercises
    
  
    
    
    1. Tests of count that complete the list. Lecture 5's set: {3, 0, 7} with some x absent; one with x = 7; {5, 1, 5, 2, 5}; and {}. Four tests is at least two, the test that runs the body once runs every statement, and the only branch is the while condition, so branch coverage comes with loop coverage. The tests pass with implementation 1, but count is still wrong against D: coverage is not correctness.
    
    
    2. isPrime returns the wrong answer on squares of primes from 11 up (121, 169, 289, …): for 121 the loop's k stops at 10, and no k divides 121. Not on 100 (k = 2 divides it on the first run) or 101 (prime, so true is right).
    
    
    3. Under spec A, whose precondition promises x occurs, implementation 2 (which throws instead of returning −1) has every statement reachable except the throw: only an input that breaks the precondition reaches it, so statement coverage is complete without it. Under B, C or D the throw is reachable and a test must run it.
    
  
    

  
    
    
    Quick check: if a method's tests pass and have statement, branch and loop coverage, does that show the method is correct?
    
    
    
    
    
  
    
  
    
    
    Quick check: what is the smallest n where the faulty isPrime (stopping at k * k < n) wrongly returns true?

    Week 2 cheat sheet
    
  
    
    
    
      
    Batch program
    
      
    Reads its input, computes, writes its output, and exits. (A web browser is not one.)
    
      
    Input: command-line arguments (options start with -; anything else names a file), a file, or standard input (the keyboard by default).
    
    
    
    
    
      
    What a user sees
    
      
    
        
    standard outputresults · System.out
    
        
    standard errormessages · System.err
    
        
    exit status0 success, nonzero failure · System.exit(n)
    
      
    
      
    Java's own status: 0 if main finishes, 1 after a stack trace. A specification says what all three are on every run.
    
    
    
    
    
      
    Shell
    
      
    
        
    cmd > fstandard output to f (emptied first)
    
        
    cmd >> fappend standard output
    
        
    cmd 2> fstandard error to f
    
        
    cmd < fstandard input from f
    
        
    a | ba's standard output is b's input
    
        
    echo $?last exit status (PowerShell: $LASTEXITCODE)
    
      
    
    
    
    
    
      
    Sum's responses
    
      
    
        
    a sum12 · status 0
    
        
    -a4.0 (a double) · status 0
    
        
    -a --precision=24.00 · status 0
    
        
    any mistakeSum: … on standard error · status 1
    
      
    
      
    Mistakes: unknown option; two files; bad or negative N; --precision without -a; unreadable file; a word that isn't an int; -a with nothing to average.
    
    
    
    
    
      
    Lecture 1's standard
    
      
    Every input a user can produce gets a response the specification describes, and a stack trace is never that response.
    
    
    
    
    
      
    Checks at the edge
    
      
    The user owes the program nothing, so main checks whatever arrives and passes on only what the computation can handle. A method whose client is main may have a precondition.
    
      
    Without a check: %.-1f → stack trace; 0 / 0 → NaN with status 0 (worse: it reports success).
    
    
    
    
    
      
    Stronger and weaker
    
      
    S1 is stronger than S2 if every implementation meeting S1 meets S2: precondition weaker or same, and postcondition stronger or same where S2's precondition holds.
    
      
    Strengthening can't break a client; weakening can't break the implementation.
    
    
    
    
    
      
    Unix style
    
      
    "Expect the output of every program to become the input to another, as yet unknown, program. Don't clutter output with extraneous information."
    
      
    Messages name their program (Sum: …). Rule of Repair: fail noisily and as soon as possible.
    
    
    
    
    
      
    Testing (Lecture 4)
    
      
    Code is correct if it meets its spec. Test = chosen input, expected behavior from the spec, run, compare. Tips: allowed inputs only; each method separately; exhaustive when few inputs; each case and each boundary.
    
      
    Specification-based tests pass every correct implementation; implementation-based ones may fail a correct one. Testing refutes, never confirms.
    
    
    
    
    
      
    Coverage (Lecture 5)
    
      
    At least two tests, plus: every statement; both branches of every if; every loop body 0, 1 and more than 1 times; recursion 0, 1 and more than 1 calls. Only allowed inputs count. This is the floor, not proof of correctness.
