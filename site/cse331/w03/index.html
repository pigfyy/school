Lecture 6 · Error handling and interactive programs · Mon Oct 12

A calculator

Today's program is a calculator, in two halves: main, which talks to the user, and CalcStack, which does the arithmetic. The calculator keeps a stack, a list of numbers that grows and shrinks at one end, its top. Typing a number pushes it onto the top. An operation such as + pops the top two numbers, combines them, and pushes the answer. Writing the operation after its numbers, as in 1 2 +, is called reverse Polish notation.

For - and / the order matters: the number second from the top goes on the left. So 1 2 - computes 1 − 2 = −1. p prints the whole stack, bottom first; . pops the top number and prints it; t prints the top without removing it; q quits.

In the longer run, 42 went onto the stack with no output: the calculator shows its stack only when asked. + added the top two numbers, 10 and 17. - then subtracted the top number from the one below it: 3 minus 27, not 27 minus 3. The bar under the terminal shows the stack, which the user never sees unless they type p.

Quick check: on an empty stack you type 5 1 2 + * .. What exactly does the calculator print?

Teaching notes
  • Ask the room to read both halves before anything runs (the full listing is on Six ways to say no). The stack is not the point of the lecture; it is a small program with state that lasts and several operations that can fail.
  • Have someone predict 1 2 - before running it. The class comment says the second-from-top number is on the left, which is why it prints −1 and not 1.

Lecture 6 · Mon Oct 12 · notes: Interactive programs

Interactive programs

Lecture 3's Sum read all its input, computed, wrote its output, and exited: a batch program. The calculator is the other kind.

Interactive program. An interactive program responds to each input as it arrives, and keeps running until the user tells it to stop.

main's loop, on lines 41 to 109, never ends on its own. Each time around, it prints the prompt >, reads one line, and responds to each word on the line, each token. The loop ends in only two ways: q returns from main (line 52), or the user ends the input (Control-D on macOS and Linux, Control-Z then Enter on Windows), which makes hasNextLine on line 43 false, and break leaves the loop.

The difference shows when the user makes a mistake. Sum stopped at the first mistake, with a message on standard error and exit status 1. A user who types + with one number on the stack expects to keep the stack and fix the mistake. So the calculator prints a message and keeps going. The operation that failed leaves the stack alone.

For that to work, main has to learn of every operation that could not be done, so that it can tell the user and go around the loop again.

Quick check: on an empty stack you type 4 0 /, then p. What does p print?

Teaching notes
  • Press end input on the terminal to show the second way out: the last prompt prints, then the program ends with status 0.
  • The quick check is the point of the section: the failed / leaves both numbers on the stack (line 203 pushes them back before throwing).

Lecture 6 · Mon Oct 12 · notes: When a method cannot do its job

When a method cannot do its job

Three kinds of trouble matter here:

A user's mistakeThe user typed something the program cannot use, such as x. Lecture 3 met these with checks and messages at the edge of the program, and never with a stack trace: one of this course's rules.
A programmer's mistakeSome code breaks a promise, such as a precondition. The code may be ours, a coworker's or a library's. The specification promises nothing about what happens next.
A request that cannot be carried outA client asks a method for something it cannot do: popping a number off an empty stack, or asking Lecture 2's indexOf for a value that is not in the array.

Separation of concerns. Giving each concern one home. main owns the conversation with the user: the prompt, the tokens, the messages. CalcStack owns the stack and its arithmetic, and knows nothing of users.

The price is paid at the boundary. The user's + on a stack of one number (a user's mistake) crosses into CalcStack as a request it cannot carry out. CalcStack cannot print a message, since its client is main, not a person. So it has to tell main that the operation failed, and main, at the edge, tells the user. The only words the two halves share are CalcStack's specifications, so every way of saying no is a clause in one.

The question for the rest of the lecture: when a method cannot do its job, how does it say no to its client?

Quick check: the user's + on one number reaches CalcStack.add. From add's point of view, what kind of trouble is it?

Teaching notes
  • Half sheet, question 1 (4 minutes): The user types 1 +. Which method first decides that the operation cannot be done? How does it say so, and who tells the user? Now 1 *: does it go the same way? Why might it not? (It is problem 6 on the Problems page.)
  • "In the calculator, the first leads to the third": a user's mistake at the edge becomes a request that cannot be carried out inside.

The six, one at a time

  

    
opwaywhat the method does

    
*preconditionThe method itself never says no: the client checks before the call. Suits a client that can check cheaply; here size() makes it one comparison. Checking a precondition anyway, inside the method, is defensive programming; multiply doesn't, on purpose.

    
.special valueA value the method returns only when it could not do its job. It must be a value never returned otherwise: −1 works for indexOf (an index is never negative), but not for a stack of numbers, whose top could be −1. pop returns Integer, a reference type that can hold null; int is a primitive type and cannot.

    
+flagadd has no answer to give, so a boolean says whether it worked. Java's List.remove(Object) works the same way.

    
twrappertop has an answer and also needs a way to say there is none. An OptionalInt either holds one int or is empty: a list of length zero or one.

    
/exceptionThe method does not return at all. Throwing ends it at once; Java looks for code that catches that kind. Only if there is none does the program stop with a stack trace. Each failure has its own exception, so a client can tell them apart. @throws is part of the postcondition.

    
-checked exceptionLike /, plus two lines: throws StackException on the signature, and extends Exception instead of RuntimeException. See When the client forgets.

  

  

    
A try statement. Java runs the try block. If no line in it throws, the catch blocks are skipped. If a line throws, Java leaves the block at that line and runs the first catch whose kind matches, with the exception in its variable e; e.getMessage() is the message given when it was thrown. Either way the program goes on after the statement. Think of a try as an if whose condition is whether the block threw.

Lecture 6 · Mon Oct 12 · notes: When the client forgets, A checked exception

  
When the client forgets

  

    
All six ways work when the client checks. A second question tells them apart: what happens when the client forgets to check? Decide what you would want to happen. The notes took main's check out of copies of the calculator, leaving blank lines so every other line keeps its number. Pick a copy and try the operation.

  

  


  

    
flagNothing happens, silently. add left the stack unchanged, as its spec says, but nobody told the user; to the user, the missing number acted like 0.

    
preconditionAnything may happen; here a confusing NullPointerException about a null the client never saw (the second pop returned it, and line 182 stored it in an int). The spec promised nothing about this call.

    
special valueWith Integer kept, null is printed to the user. Stored in an int (line 56), it meets the same conversion and stops the program. Java converted silently, so nothing warned the programmer.

    
exceptionThe program stops with a stack trace, which the course's rule forbids, but the trace gives divide's own message and the line that threw.

    
wrapperAsking getAsInt without isEmpty throws NoSuchElementException: No value present at the ask. Storing the wrapper in an int does not compile.

    
checked exceptionThe compiler refuses the program: unreported exception StackException; must be caught or declared to be thrown. Declaring throws StackException on main satisfies it, and then 1 - ends in a stack trace.

  


  
Checked and unchecked

  

    
An unchecked exception extends RuntimeException. A method may throw one without saying so in its code, and its client may catch it or not. A checked exception extends Exception but not RuntimeException. A method that may throw one must say so in a throws clause, and every client must catch it or declare it in its own throws clause.

  

  

    
The names do not help: RuntimeException is itself a kind of Exception. Lecture 3's Sum caught a FileNotFoundException, which is checked. Lecture 4 named three ways to know code works: testing, tools and reasoning. The compiler is a tool that confirms a claim about every run, but only the claims it was built to check. A checked exception gives it one more: every caller of subtract catches StackException or declares it. A mistake the compiler catches never reaches a run, a user or a test. When you can, let the compiler find the mistake.

Lecture 6 · Mon Oct 12 · notes: Choosing a way

  
Choosing a way

  
None of the six is best everywhere. Three questions help:

  
    
    
  1. Can the client check first, cheaply? Then a precondition is simplest, as for multiply, and the check puts the condition in front of whoever reads main. When checking costs as much as the work, as for parseInt (scan the digits, work out whether it fits), the method should check and say what it found.
    2. 
    
  2. How convenient is the answer to use? A flag or special value is checked with a plain if; an exception needs a try. A checked exception makes every client catch or declare it, even one that knows the failure cannot happen: every client pays, and in return the compiler checks every client before any run.
    3. 
    
  3. What happens when a client forgets? Silence, a confusing crash, a stack trace with the method's own message, or a compile-time error. Only the last comes before any run.
    4. 
  

  

    
Bloch's rule of thumb (Effective Java, item 70). A problem a careful client should expect and recover from, such as a missing file, suits a checked exception. A problem only a programmer's mistake can cause suits an unchecked exception. A wrapper sorts beside the checked exception (both make the client ask); a precondition beside the unchecked one (both leave a careless client to a crash).

  

  

    
Strength. A method that promises an exception on a bad call has a stronger specification than one that requires a good call. A library's specifications can only grow stronger, so once it publishes a @throws clause it cannot replace it with a precondition.

  


  
The seventh way

  

    
A bad one: say nothing, and make up an answer. The program keeps running and the made-up answer travels on, so the mistake may show far from its cause, or never. Common made-up answers: JavaScript's undefined (reading past an array's end; undefined + 1 is NaN); Java's NaN and Infinity for doubles (0.0 / 0.0, 1.0 / 0.0); and a null the spec does not allow. "The one guaranteed wrong answer is to ignore the problem" (Kernighan and Pike).

    
The calculator ignores one problem itself: 2147483647 1 + p prints [-2147483648]. That is a bug, not a way of saying no: add promises the sum, and nobody decided what to do when it does not fit, so Java's arithmetic decided. The fix is a decision: say no in one of the six ways (problem 2), or promise less and say the sum wraps.

  


  

    
Quick check: spec X says @throws StackEmptyException if the stack is empty; spec Y says @requires the stack is non-empty; otherwise they are the same. X is ___ than Y.

Lecture 6 · Mon Oct 12 · notes: Interactive programs are harder

  
Interactive programs are harder

  
Most programs you use every day are interactive: an editor, a browser, a phone app. Three things make them harder to get right than a batch program:

  
    
    
  • State that lasts. The stack outlives each line. A bug may show only after one particular sequence of inputs: the crash on the eleventh click, but only after a certain file was opened.
    • 
    
  • A user who chooses the order. The program must respond sensibly to any input at any moment, and keep running afterward.
    • 
    
  • State the user cannot see. The calculator shows its stack only on p. A user who forgets, or a tester reproducing a bug, has to reconstruct it.
    • 
  

  

    
Separation of concerns makes the state easy to test on its own. Lecture 5's Testable by design: a method that reads the keyboard is hard to test; one that takes values and returns one is easy. A test of add needs no keyboard:

  

  
@Test
void addReplacesTwoNumbersWithTheirSum() {
    CalcStack stack = new CalcStack();
    stack.push(2);
    stack.push(3);
    assertTrue(stack.add());
    assertEquals("[5]", stack.toString());
}

@Test
void divideOnOneNumberThrows() {
    CalcStack stack = new CalcStack();
    stack.push(1);
    assertThrows(TooFewOperandsException.class,
        () -> stack.divide());
    assertEquals("[1]", stack.toString());
}

  

    
The second test checks divide's @throws clause, which assertEquals cannot: a call that throws returns nothing to compare. assertThrows takes the exception's class, then the code to run, written as a lambda, () -> stack.divide(): a piece of code handed over to be run later. It passes if that code throws an exception of the class named. The last line checks the failed divide left the stack alone.

Testing heuristics

  

    
Black-box testingLook at the spec, and test all expected behaviors.

    
Clear-box testingLook at the code, and test all paths.

    
Boundary casesInputs on the edge of a behavior (an empty array, a value at an end of a range).

    
Exhaustive testingIf there are only a few inputs (10 or fewer), test them all.

  

  
Coverage

  

    
StatementEvery statement executed at least once.

    
BranchEvery branch (both sides of every if, including an implicit else) executed at least once.

    
LoopEvery loop (and recursive call) run 0, 1, and 2 or more times.

    
PathEvery path through the code executed at least once.

// @modifies a
// @effects if x does not occur in a[0..n], leaves a
//   unchanged; otherwise, if x occurs k > 0 times in
//   a[0..n], then remove all k occurrences of x,
//   leaving remaining elements in the same relative
//   order as before; the new value of elements in
//   a[n-k..n] is unspecified
// @return n - k

    
public static int removeValue(int[] a, int n, int x) {
    int w = 0;
    for (int r = 0; r < n; r++) {
        if (a[r] != x) {
            a[w] = a[r];
            w++;
        }
        // implicit else
    }

Lecture 7 · Wed Oct 14 · notes: What is true after each line, A claim at a point

  
What is true after each line

  

    
When the program runs, a line changes the values of the variables. When we reason, a line changes what we know about those values. A claim sits in double braces beside the code. The braces are not Java, and what they hold is math: = means equals, != not equal, combined with and, or, not. A client must make the precondition true, so we may assume it at the top.

  

  
static long seconds(int h, int m, int s) {
    {{ 0 <= h and 0 <= m and 0 <= s }}
    long t = h;
    {{ 0 <= h and 0 <= m and 0 <= s and t = h }}
    t = t * 60 + m;
    {{ 0 <= h and 0 <= m and 0 <= s and t = 60 * h + m }}
    t = t * 60 + s;
    {{ 0 <= h and 0 <= m and 0 <= s and
       t = 3600 * h + 60 * m + s }}
    return t;
}

  
    
    
  1. Line 17 sets t to h. Nothing about h, m, s changed, so the precondition is still true, and now t = h too.
    2. 
    
  2. Line 18 changes t, so t = h is no longer true. The new value is the old value times 60, plus m, and the old value was h: t = 60 * h + m.
    3. 
    
  3. Line 19 does the same with s: t = 3600 * h + 60 * m + s.
    4. 
    
  4. Line 20 returns t, and the last claim says t is exactly what the postcondition promises. So every run that starts with the precondition true returns the right value, shown without running the method once.
    5. 
  

  

    
Assertion. A true or false claim about the program's state (the values of variables and memory) at a particular point in the program. It holds if the claim is true each time a run reaches its point. A point in a branch is reached only by runs that take the branch; a point in a loop may be reached many times on one run.

  

  

    
The claims treat * and + as integer arithmetic. Java's int wraps at the top of its range, and the seconds in 596524 hours already pass it, so seconds computes in a long: no line wraps, and the claims may use integer arithmetic. Going from a claim before a line to a claim after it is forward reasoning. With the rules written down, an argument whose every step follows a rule is a proof.

Lecture 7 · Wed Oct 14 · notes: A triple

  
Hoare triples

  

    
Hoare triple. {{ P }} code {{ Q }}: a claim P (its precondition), a piece of code, and a claim Q (its postcondition). The triple is valid if every terminating run of the code from a state in which P is true ends in a state in which Q is true.

  

  

    
Floyd and Hoare worked this out in the late 1960s: Floyd-Hoare logic. A method satisfies its specification exactly when the triple of its precondition, body and postcondition is valid and every call that begins with the precondition true terminates. Pick a triple below: each square is a starting state; blue ones make P true. The second row shows the variable after the line, green where Q holds and red where it does not.

  

  
One-line triples, checked on every state from −3 to 8

  

    
{{ true }} x = 5; {{ x = 5 }}Valid: whatever the state, the line makes x 5.

    
{{ x = 3 }} y = x + 1; {{ y = 4 }}Valid.

    
{{ x = 3 }} y = x + 1; {{ 0 < y }}Valid too: a postcondition may say less than all that is true afterward.

    
{{ true }} y = x + 1; {{ y = 4 }}Not valid: from x = 0 the line makes y 1.

    
{{ 0 < x }} x = x - 1; {{ 0 < x }}Not valid: from x = 1 the line makes x 0.

    
{{ false }} x = 0; {{ x = 1 }}Valid: no state makes false true, so the triple asks nothing, as a spec says nothing about a call that breaks its precondition.

  

  

    
A triple's code may be empty: {{ P }} {{ Q }}, two claims at one point. It is valid exactly when P implies Q, that is, P is stronger than Q. Claims written one under another read as a chain of implications.

Lecture 7 · Wed Oct 14 · notes: Stronger claims say more, Two directions

  
Stronger claims, two directions

  

    
Think of a claim as the set of states in which it is true. P implies Q means P's set is inside Q's. "Stronger" sounds bigger, so it is easy to get backward: the stronger claim has the smaller set, rules out more states, and so says more. The weakest claim is true (every state); the strongest is false (no state).

    
Among the claims that hold at a point, one implies all the others: the strongest. Forward reasoning keeps it, because a weaker claim may not be enough. Had we written only 0 <= t after line 18, we could not say what t is after line 19, and the argument about seconds would fail though the method is right.

  

  

    
Forward{{ P }} code {{ ? }}: the strongest claim that makes the triple valid, the strongest postcondition. The triple {{ P }} code {{ Q }} is valid exactly when it implies Q.

    
Backward{{ ? }} code {{ Q }}: the weakest claim that makes it valid, the weakest precondition: the least that must be true beforehand. The triple is valid exactly when P implies it.

Lecture 7 · Wed Oct 14 · notes: The rules for an assignment, a sequence, consequence

  
Assignment, sequence, consequence

  

    
Assignment, forward.
{{ P }}
x = e;
{{ P[x ↦ x0] and x = e[x ↦ x0] }}
Everything P said is still true once we write x0, a fresh name, for the old value of x; and the new x is e computed from the old values. The strongest claim after the line.

    
Assignment, backward.
{{ Q[x ↦ e] }}
x = e;
{{ Q }}
Read from the bottom up: whatever Q claims about x after the line had better be true of e before it. Just a substitution. The weakest claim before the line.

  

  

    
Two habits keep fresh names out of the claims: if P and e never mention x, the claim after is just P and x = e; and if the old value can be written without x0 (after x = x + 1 it is x - 1), substitute it and drop the fact it came from.

  

  
Backward through seconds

  
    
    
  1. Before line 19, replace t by t * 60 + s: {{ t * 60 + s = 3600 * h + 60 * m + s }}.
    2. 
    
  2. Before line 18, replace t by t * 60 + m: {{ (t * 60 + m) * 60 + s = 3600 * h + 60 * m + s }}.
    3. 
    
  3. Before line 17, replace t by h: {{ (h * 60 + m) * 60 + s = 3600 * h + 60 * m + s }}.
    4. 
    
  4. Both sides are the same number, so the claim at the top is true in every state, and the precondition implies it: the triple is valid. Three substitutions and one check. (Neither argument used the precondition's three facts.)
    5. 
  

  
Sequence. {{ P }} first; second {{ Q }} is valid exactly when some claim R between them makes {{ P }} first {{ R }} and {{ R }} second {{ Q }} valid. Forward picks the strongest R; backward the weakest.

Lecture 7 · Wed Oct 14 · notes: The rule for a conditional

  
Conditionals

  

    
{{ P }}
if (b) {
    {{ P and b }}
    first
    {{ A }}
} else {
    {{ P and not b }}
    second
    {{ B }}
}
{{ A or B }}
{{ Q }}

    
A run takes one branch or the other, and we reason without knowing which, so the claim after the if covers both: A or B, the strongest claim there. The triple is valid exactly when both A and B imply Q. An if with no else still has a false branch; it is empty, so B is P and not b.

  

  
abs, with a ghost variable

  
/** @requires -2147483647 <= n
 *  @return n if 0 <= n, and -n if n < 0 */
static int abs(int n) {
    {{ n = n0 }}
    if (n < 0) {
        {{ n = n0 and n < 0 }}
        n = -n;
        {{ n0 < 0 and n = -n0 }}
    }
    {{ (n0 < 0 and n = -n0) or (0 <= n0 and n = n0) }}
    {{ 0 <= n and (n = n0 or n = -n0) }}
    return n;
}

  

    
In the spec, n means the number the caller passed; after line 18 overwrites it, a claim about n alone can no longer say anything about that number. So we name it n0, a ghost variable: a name used only in the claims, for a value the method started with. (Just 0 <= n would not be enough: a method that always returned 0 would make that true.)

  

  
Branches that return

  
static int compare(int a, int b) {
    {{ true }}
    if (a < b) {
        {{ a < b }}
        return -1;
    }
    {{ b <= a }}
    if (a == b) {
        {{ b <= a and a = b }}
        return 0;
    }
    {{ b <= a and a != b }}
    return 1;
}

  

    
No run comes out of a branch that returns. A claim holds at a point if it is true each time a run reaches it; at a point no run reaches, every claim holds, even false. So that branch's A is false, and A or B is just B: b <= a. At each return, check the claim against what the @return clause promises in that case. And when a claim implies false, reasoning has found code that never runs.

static int quadrant(int x, int y) {
    int q = 1;
    if (x < 0) { q = 2; }
    if (y < 0) { q = q + 1; }
    return q;
}

  
Forward, after the second if the claim has four cases, the four paths. Three match the spec; the fourth, 0 < x and y < 0 and q = 2, promises 4: the implication fails exactly on the lower right quadrant.

  
quadrant(x, y) on every point from −4 to 4

  

    
Backward through a conditional, the claim before the if is (b and A) or (not b and B), where A and B are the weakest claims before the branches. Backward from quadrant's postcondition, quadrant 4's row asks for 1 = 3 before int q = 1, which is false, so it drops. The claim at the top keeps quadrants 1, 2 and 3: exactly the inputs that get the right answer. The precondition allows quadrant 4, so the triple is not valid.

    
An argument built from the rules is a proof, and unlike prose it says where it fails: with the strongest claims forward (or the weakest backward), the false implication names the inputs on which the method is wrong.

  

  

    
What can still go wrong. A false implication (a person can believe one, so we still test: a test that refutes the claim refutes the argument too). Arithmetic that is not Java's (claims are about integers; int wraps). And a loop: these rules cannot carry a claim through a loop that may run any number of times. That is Friday.

A loop

  

    
Lecture 7's rules are mechanical: given the claim on one side of a line, a rule writes the claim on the other side, with no decision to make ("turning the crank"). The one step that is not mechanical is the rule of consequence's implications. A loop adds a second question: does the code terminate?

  

  
/** @return a[0] + ... + a[a.length - 1], the sum of the elements */
static long sum(int[] a) {
    long s = 0;              // line 14
    int i = 0;               // line 15
    while (i < a.length) {   // line 16
        s = s + a[i];        // line 17
        i = i + 1;           // line 18
    }
    return s;                // line 20
}

  

    
Forward through one pass, the rules give i = 1 and s = a[0]; through two, i = 2 and s = a[0] + a[1]. A run may make any number of passes, so a claim at line 20 built pass by pass would need one case for each number of passes, and no finite list has one for every number. In general, no rule can compute the strongest postcondition or weakest precondition of a loop (it would decide the halting problem). So we write a claim at the loop by hand.

The rule for a while loop

  

    
{{ P }}
{{ Inv: I }}
while (b) {
    {{ I and b }}
    body
    {{ I }}
}
{{ I and not b }}
{{ Q }}

    

      
{{ P }} while ... {{ Q }} is valid if three checks pass:

      
    
        
  1. (1) P implies I.
    2. 
        
  2. (2) {{ I and b }} body {{ I }} is valid.
    3. 
        
  3. (3) I and not b implies Q.
    4. 
      

      
I is a claim the programmer supplies.

    

  

  

    
Why they suffice. A run reaches the first condition check with P true, so (1) makes I true there. Every later check comes at the end of a pass that began at the check before with b true; if I was true then, (2) makes it true again. So I is true at every check. The last check finds b false, so I and not b holds after the loop, and (3) gives Q.

    
Checks (1) and (3) are uses of the rule of consequence. Check (2) is a triple about the body, which Lecture 7's rules settle when the body has no loop. What is new is I.

Finding the invariant

  

    
In general, finding an invariant takes creativity. In simple cases, read it off the postcondition: the postcondition says what is true when the loop is done; the invariant says what is true when it is part way done. For sum, put i for a.length in Q. An invariant has two kinds of facts:

    
  • What has been done so far: s = a[0] + ... + a[i - 1].
  • How far along the loop is: 0 <= i and i <= a.length, from where i starts and where it stops.

  

  
max

  
/** @requires 0 < a.length
 *  @return the largest element of a */
static int max(int[] a) {
    int m = a[0];
    int i = 1;
    {{ Inv: 1 <= i and i <= a.length and
            m is the largest of a[0], ..., a[i - 1] }}
    while (i < a.length) {
        if (m < a[i]) { m = a[i]; }
        i = i + 1;
    }
    return m;
}

  
A claim may be in words, as long as it is true or false in each state. Check (2) goes through the if with Lecture 7's conditional rule: in both branches m becomes the largest of a[0], ..., a[i], then i = i + 1 restores I.

  
sumTo

 *  @return 1 + ... + n */

        s = s + i;
    }

}

  
Invariant: 0 <= i and i <= n and s = 1 + ... + i (or, equally, s = i * (i + 1) / 2). Not every invariant comes from putting i for a bound: quotient's says what the loop keeps equal (problem 1).

Readings

  

    
Each reading asks a question about the course motto, "Your job is to deliver code that you know works." Reading 2's question: knowing takes work (saying exactly what a method must do, testing it, and reasoning about whether it does that). Is that work the job itself, or a tax on the job? Choose one article, read it, and write a reflection. The three take three positions.

  

  

    

      
About 10 minutes

      
Gabriel 1991, "The Rise of Worse is Better"

      
Two ways to design software. The MIT way, "the right thing", puts the interface first: simple, correct, consistent and complete, whatever it costs the implementation. The New Jersey way puts the implementation first and lets users do the extra work. Gabriel caricatures the second on purpose, then argues it won: Unix and C gave people half of what they wanted and were easy to port. Ship half of the right thing, if that half is basically right, and improve it once people depend on it.

    

    

      
About 20 minutes

      
Lamport 2003, "The Future of Computing: Logic or Biology"

      
"Logic" is Floyd and Hoare's idea: a program is a mathematical object, so you can ask what it means and whether you could prove it. He asks you to ask yourself, not to write the proof. "Biology" is treating programs as mysterious, met with superstition and left to evolve and fight off viruses; software nobody understands cannot be made dependable. His way back: keep systems simple enough to understand, with logic as the tool. (Lecture 7 quotes him.)

    

    

      
About 10 minutes

      
Dijkstra 1978, "On the foolishness of "natural language programming""

      
On the wish to instruct a machine in English. Moving work across an interface does not divide a fixed amount of labor; the work of communicating across it is added, often on both sides. Formal notation is a privilege: with it schoolchildren do what once took a genius. The ease of a natural language is the ease of "making statements the nonsense of which is not obvious."

Week 3 cheat sheet

  

    

      
Interactive program

      
Responds to each input as it arrives, and keeps running until the user tells it to stop. Harder: state that lasts, a user who chooses the order, state the user cannot see.

    

    

      
Three kinds of trouble

      
A user's mistake (checked at the edge, never a stack trace); a programmer's mistake (a broken promise: the spec promises nothing); a request that cannot be carried out.

    

    

      
Six ways to say no

      

        
preconditionclient checks first; forgotten: anything

        
special valuenull, −1; forgotten: printed, or NPE

        
flagboolean; forgotten: silence

        
wrapperOptionalInt; forgotten: crash at the ask

        
exceptionunchecked; forgotten: stack trace

        
checked exceptionforgotten: does not compile

      

      
Seventh (bad): make up an answer (NaN, undefined, null, overflow).

    

    

      
Exceptions

      
Unchecked: extends RuntimeException. Checked: extends Exception only; callers catch or declare throws. Bloch: recoverable → checked; programmer error → unchecked. @throws is stronger than @requires.

    

    

      
Testing (Section 2)

      
Black-box, clear-box, boundaries, exhaustive if ≤ 10 inputs. Coverage: statement, branch, loop 0/1/2+, path. Coverage is the floor; add spec-derived cases; then judgment. Check mutated state too.

    

    

      
Hoare triple

      
{{ P }} code {{ Q }} is valid if every terminating run from a P-state ends in a Q-state. {{ P }} {{ Q }}: P implies Q. Stronger claim = smaller set of states.

    

    

      
Assignment rules

      
Forward: {{ P }} x = e; {{ P[x ↦ x0] and x = e[x ↦ x0] }} (strongest postcondition). Backward: {{ Q[x ↦ e] }} x = e; {{ Q }} (weakest precondition).

    

    

      
Sequence, consequence, if

      
Sequence: some R between. Consequence: P ⇒ A, {{A}} code {{B}}, B ⇒ Q. If: P and b / P and not b at the tops, A or B after; a branch that returns contributes false. Backward: (b and A) or (not b and B). Ghost variable n0: the value at the call.

    

    

      
While loop

      
(1) P ⇒ I. (2) {{ I and b }} body {{ I }}. (3) I and not b ⇒ Q. Plus a variant: integer, ≥ 0 at each check, smaller each pass.

      
Find I from Q: what's done so far (put i for the bound) + how far along (bounds on i). Too weak: (3) fails. Too strong: (1) fails.
