Lecture 9 · Programs on the web · Mon Oct 19 · notes: A guestbook

A guestbook

A web page where a visitor leaves a name and a message, and every later visitor sees it: the web of the 1990s, one page, one form, no JavaScript. java Guestbook prints Serving at http://localhost:9331/, then nothing happens: the program is waiting for someone to visit. Below, open the page in browser A, post Ada's message, then open the same address in browser B.

  1. Browser A sends GET /: a few lines of text asking for the page at the path /. The terminal prints it.
  2. The guestbook runs handle, which builds the page from its book, the messages so far, and sends it back as text. A draws it, then asks on its own for /favicon.ico, an icon for its tab, and gets the page again.
  3. Pressing Post sends POST /, whose text ends with name=Ada&message=hello+world. handle adds the message and sends the page back. It is a new page, so the boxes are empty again.
  4. Browser B's GET / prints the same line as A's did. There is one book, so B's first page shows a message nobody typed in B.

Every arrow is a message, and every message is text. The guestbook only answers: it sends nothing until a browser asks. A window shows the page that last came back to it. Stop the program and start it again: the message is gone, since messages last only while the program runs.

Quick check: you open the page in A, post a message from A, and open the page in B. How many request lines does the terminal print?

Teaching notes
  • On the slide: "Then nothing happens. What is the program doing?" Ask before visiting. Then ask the room to predict the terminal after each visit.
  • The calculator was interactive too, but its user was at its keyboard. Here the users sit at browsers, maybe on other machines, and reach it over a network in messages of a fixed form.

Lecture 9 · Mon Oct 19 · notes: Servers and browsers, The book, One book for everyone

Servers, browsers, one book

Server. A program that waits for requests and answers each with a response.

The browser relies on what the guestbook promises (a page for a GET, a message added for a POST), as Lecture 3's script relied on Sum. The guestbook can assume nothing about what arrives: its author can hold no browser to a promise. (The web calls the browser the server's client; in Lecture 2's words it is a user.) The browser's side is the frontend; the server's side, the backend.

/** The messages posted so far, oldest first. */
class Book {
    private List<String> messages = new ArrayList<String>();
    /** @modifies this
     *  @effects adds the message, signed with the name, after the messages already posted */
    public void add(String name, String message) {
        messages.add(name + ": " + message);
    }
    /** @return the posted messages, oldest first, in a new list */
    public List<String> messages() {
        // A copy, so that a client cannot change the book through it.
        return new ArrayList<String>(messages);
    }
}

Book knows nothing about the web: separation of concerns again, so a test of Book needs no browser, as a test of CalcStack needed no keyboard. The notes' second test, messagesIsACopy, adds to the list it got back and checks the book is unchanged. Change line 113 to return messages; and that test fails: any client holding the list could post without calling add.

One book for everyone. Lecture 6's three hard things get harder with other people: state lasts across people; the order is the order requests arrive, chosen by nobody; and what a visitor cannot see is what others changed since they last looked. A fourth is new: the server does not know who it is talking to. A's GET / and B's print the same line; nothing in the text says who sent it. (Cookies, a later lecture.)

Quick check: from the requests it receives, can the guestbook tell browser A's GET / from browser B's?

Teaching notes
  • "Why does messages return a copy?" is put off until Lecture 11, which names the problem representation exposure. Plant the question now.

Lecture 9 · Mon Oct 19 · notes: A request is text, Where is the loop?

A request is text

the request (first two lines)

GET / HTTP/1.1
Host: localhost:9331

the response (without its Date line)

HTTP/1.1 200 OK
Content-type: text/html; charset=utf-8
Content-length: 178

<html><body>
<h1>Guestbook</h1>
<ul>
</ul>
<form method="POST" action="/">
Name: <input name="name">
Message: <input name="message">
<button>Post</button>
</form>
</body></html>

The rules for this text are HTTP. The request's first line gives its method (HTTP's word), GET; the path; the version. A blank line ends it. The response's first line carries a status: 200 means understood and answered; a status in the 400s means the server thinks the request was a mistake. Then headers, each a name, a colon and a value; a blank line; the body, the page in HTML: text with tags saying what each part is.

handle builds that response: page() builds the text fresh from the book; line 55 turns it into bytes, since a character can take more than one byte and Content-length counts bytes; lines 56 to 60 send the header, the status and length, and the body. handle declares the checked IOException rather than catching it. Start a second copy while the first holds the port, and it ends in java.net.BindException: Address already in use.

Where is the loop?

public static void main(String[] args) throws IOException {
    HttpServer server =
        HttpServer.create(new InetSocketAddress(9331), 0);
    server.createContext("/", Guestbook::handle);
    server.start();
    System.out.println("Serving at http://localhost:9331/");
}

Guestbook::handle is not a call: it is the method itself, handed to the server as a value, as Lecture 6 handed code to assertThrows. main returns, and the program keeps running. The loop is inside HttpServer: wait for a request, call the method it was handed, wait again. Each request is an event; a program whose methods are called by a loop it does not own is event-driven. A library is code you call (Scanner, ArrayList); a framework is code that calls you. To know when handle runs, read the framework's specification.

Quick check: after Ada posts hello world, the page gains the line <li>Ada: hello world</li> and a newline. The first page was 178 bytes. What is the new Content-length?

Teaching notes
  • Bytes vs characters: a message with é makes the page one byte longer than its character count. Try posting café in the guestbook and read the Content-length.

Lecture 9 · Mon Oct 19 · notes: GET asks, POST changes

GET asks, POST changes

<form method="POST" action="/">
Name: <input name="name">
Message: <input name="message">
<button>Post</button>
</form>
POST / HTTP/1.1
Host: localhost:9331
Content-Length: 28
Content-Type: application/x-www-form-urlencoded

name=Ada&message=hello+world

Pressing the button collects the fields into one line of text: each field is its name, =, and what the user typed, joined by &. Inside a value, a space becomes +, and most characters other than letters and digits become % and two hexadecimal digits. parseForm undoes it: split at each &, split each pair at its first =, decode each half with URLDecoder. HTML's first standard (1995) already defines the form.

GET asks, POST changes. A GET asks for a page and must not change the server's state. A POST asks the server to do something and may change it. Browsers and other programs send GETs on their own (the favicon; a search engine's crawler follows every link), so the standard calls GET safe: a crawler may send one "without fear of causing harm."

Quick check: the name is Bob and the message is hi there. What body does the form send?

Teaching notes
  • Two encodings meet here: the form's (undone by parseForm) and HTML's (exercise 2). Each place text goes has its own spelling.

Lecture 9 · Mon Oct 19 · notes: The whole program, The manual, on every request

The manual, on every request

What is good is the shape: two classes keep two concerns apart, and handle stays short because parseForm parses and page builds the text. What is not good: Lecture 1's standard applies to a server too. Every input a user can produce gets a response the spec describes, and a stack trace is never that response. The manual names GET / and POST /, but a browser sends other requests on its own, and curl can send anything. Try the four cases on the curl line below, then turn on the notes' two fixes.

Another pathGET /favicon.ico gets the page: HttpServer sends a request to the handler whose path is the longest prefix, and / is a prefix of every path. Harmless, but undescribed.
A POST with no fieldsAdds null: null: a map's get returns null for a missing key. Lecture 6's seventh way, on every visitor's page.
A body that is not a formname=%&message=x gets no response at all: parseForm requires a form's body, nothing checks, URLDecoder throws, and HttpServer closes the connection. The only one of the four with no response.
A message holding a tag<b>hello</b> goes into the page as it is, and every later browser shows it bold. A <script> tag could run code in every later visitor's browser: cross-site scripting, from treating a user's text as part of the page's text.

The lesson is Lecture 3's: a program's inputs are whatever a user can send it, not whatever its author pictured.

Quick check: which of the four cases gets no response at all?

Teaching notes
  • The widget shows the response as text and rebuilds the drawn page from safe tags only; a <script> shows as a warning instead of running. That is a teaching aid, not how a browser works: a real browser would run it.
  • Exercises 1 and 2 close three of the four gaps (all but the body that is not a form).

Lecture 9 · Mon Oct 19 · problems

Lecture 9: problems

Problems 1 to 4 are the notes' exercises 1 to 4, with their official answers; problem 5 practices the encodings. You can try every request on The manual, on every request.

1. A missing field

The manual describes GET / and POST / only. Write the sentence it should have for a GET of another path and for a POST with a field missing. For the missing field, decide what the guestbook should do instead of adding null, and change handle to do it.

  1. A map's get returns null for a key it does not hold. Where should the check live: in handle or in Book.add?
  1. The manual: "Any other path gets the page too. A POST adds a message only if it has both a name field and a message field."
  2. The code: String name = fields.get("name"); String message = fields.get("message"); if (name != null && message != null) { book.add(name, message); }
  3. The empty POST now gets the empty book's page, 178 bytes, and nothing is added. (Answering with a status in the 400s would be reasonable too; either way the manual must say which.)
  4. The check is at the edge, where the request arrives, as Sum's were. Book would otherwise have to know that a field can be missing, which is the web's concern.
  5. Today it adds null: hi; with the fix, the empty POST gets the 178-byte page.

2. Escape the message

Change page so a message is shown as typed: a tag in it appears as text and is never read as a tag.

  1. In HTML, < is written &lt;, > is &gt;, and & is &amp;. What would replacing & second do to &lt;?
  1. escape(text) returns text.replace("&", "&amp;").replace("<", "&lt;").replace(">", "&gt;"), and page writes "<li>" + escape(message) + "</li>\n".
  2. The & must be replaced first, or it would replace the & that &lt; just introduced.
  3. Book stores the message as typed, and page escapes on the way out. Escaping in add would store HTML in the book, and a test of Book that adds < would get &lt; back.
  4. <li>Eve: &lt;b&gt;hello&lt;/b&gt;</li>; & first; in page.

3. A form that GETs

Change the form's method to GET, and press Post with the same name and message. What does the browser send, and what does the guestbook do?

  1. A GET's fields go in the path after a ?. Which line of handle decides whether to add?
  1. The browser sends GET /?name=Ada&message=hello+world HTTP/1.1, with the same encoding; the address bar shows it.
  2. handle prints the path, fields and all, but line 46 sees a GET and skips adding: the page comes back unchanged.
  3. A GET's fields are in the address, so they land in history and server logs: never a password. A POST's are in the body. Neither hides them from the network; HTTPS does.
  4. That first line; nothing is posted; no password in a GET.

4. Refresh after posting

Post a message, then press the browser's refresh button and agree to send again. What does the terminal print, what does the page show, and how do many sites avoid it?

  1. Refresh repeats the request the page came from.
  1. The page on screen came from the POST, so refresh sends the POST again, with the same body, and handle adds the message again: twice in the list. The browser asks first because repeating a POST is not safe.
  2. Many sites answer a POST with a redirect, 303 See Other, telling the browser to GET the page; refresh then repeats a GET.
  3. POST /; twice; 303.

5. Two encodings

Bob types the name Bob and the message café & tea.

  1. é is two bytes in UTF-8, C3 A9; & is 26.
  2. The page grows by the bytes of <li>, the message line, </li> and a newline.
  1. The form encodes each byte that is not a letter or digit as % and two hex digits, and a space as +: name=Bob&message=caf%C3%A9+%26+tea.
  2. parseForm decodes it back, and add stores Bob: café & tea.
  3. The line Bob: café & tea is 15 characters but 16 bytes (é is two). With <li> (4 bytes), </li> (5) and a newline (1), the page grows by 26 bytes: 178 + 26 = 204, the same as Ada's 16-character, 16-byte line.
  4. name=Bob&message=caf%C3%A9+%26+tea; Bob: café & tea; 204 bytes.

Section 3 · Reasoning · Tue Oct 20 · from the section slides

Warm-up and review

Section 3 practiced Lectures 7 and 8. The handout, solution and slides are the source for these pages, lightly condensed. The warm-up: is each triple valid? If not, give a counterexample.

A{{ x > 0 }} x = x - 1; {{ x > 0 }}
B{{ x >= 10 }} if (x < 5) { y = -100; } else { y = x; } {{ y >= 10 }}
C{{ x = a and y = b }} x = x + y; y = x - y; x = x - y; {{ x = b and y = a }}
D{{ x = a and y = b }} x = y; y = x; {{ x = b and y = a }}
E{{ n >= 0 }} i = 1; while (i <= n) { i = i + 1; } {{ i = n + 1 }}
F{{ x + 1 > 0 }} if (x < 0) { y = -x; } else { y = x; } {{ y > 0 }}

Three are invalid (practice problem 1 asks which).

Forward reasoning: two tools

SubscriptsAppend new facts, naming old values x0, x1, …. Gets messy, but represents everything.
Invertible operationsUse algebra to write the old value in terms of the new: after x = x + 1, {{ x = y }} becomes {{ x - 1 = y }}. More readable, but not everything inverts: after x = x / 2, both x = 8 and x = 9 give x = 4.

A common error. Dropping a fact too early, or substituting away a variable's relationship: after y = 3 * x; z = y + 1;, keep y = 3 * x and z = y + 1 rather than writing only z = (3 * x) + 1. Do not drop a fact while it still says something useful.

Backward reasoning is substitution: start with the postcondition, plug and chug up through each line, end at the precondition, and check that the given precondition implies it.

Quick check: is triple B valid?

Tasks 1–4

Task 1: forward reasoning

{{ y > 5 and z > 2 }}
x = 4 * y - 3;
{{ y > 5 and z > 2 and x = 4y - 3 }}
y = y - 5;
{{ y0 > 5 and z > 2 and x = 4y0 - 3 and y = y0 - 5 }}
z = z * y;
{{ P: y0 > 5 and z0 > 2 and x = 4y0 - 3
      and y = y0 - 5 and z = z0 * y }}
{{ Q: x < 2z + 20 }}
// @return (x + 1)^2
public static int nextSquare(int x) {
  int y = x * x;
  {{ y = x^2 }}
  y = y + (2 * x);
  {{ y - 2x = x^2 }}
  y = y + 1;
  {{ P: y - 2x - 1 = x^2 }} <--> {{ y = x^2 + 2x + 1 }}
  {{ Q: y = (x + 1)^2 }}
  return y;
}

The first uses subscripts; the solution also gives the invertible version, ending {{ y + 5 > 5 and z / y > 2 and x = 4(y + 5) - 3 }}. In nextSquare, Q comes from the @return clause, since y is what is returned, and P implies Q by algebra.

Task 2: backward reasoning

{{ Q: 2x - 8 < 4w }} <--> {{ x < 2w + 4 }}
y = 4 * w;
{{ 2x - 8 < y }}

{{ x - 8 < y }}
z = x - 8;

c = c - 1;

Task 4: a loop

// @requires x >= 0
// @return The largest integer y such that 10 * y <= x_0
public static int divideByTen(int x) {
  {{ x = x_0 and x_0 >= 0 }}
  int y = 0;
  {{ P1: x = x_0 and x_0 >= 0 and y = 0 }}
  {{ Inv: x_0 - 10y = x and x >= 0 }}
  while (x >= 10) {
    {{ x_0 - 10y = x and x >= 0 and x >= 10 }}
    y = y + 1;
    {{ x_0 - 10(y_0) = x and x >= 0 and x >= 10 and y = y_0 + 1 }}
    x = x - 10;
    {{ P3: x_0 - 10(y_0) = x_1 and x_1 >= 0 and x_1 >= 10 and y = y_0 + 1 and x = x_1 - 10 }}
    {{ Q2: Inv }}
  }
  {{ P2: Inv and x < 10 }}
  {{ Q1: 10y <= x_0 and x_0 < 10(y+1) and x = x_0 - 10y }}
  return y;
}
  1. Check (1). x_0 - 10y = x - 10y = x since x = x_0 and y = 0; and x = x_0 >= 0.
  2. Check (3). 10y = x_0 - x <= x_0 since x >= 0; x_0 = x + 10y < 10 + 10y = 10(y + 1) since x < 10; the third fact restates the invariant.
  3. Check (2). x = x_1 - 10 = x_0 - 10y_0 - 10 = x_0 - 10(y_0 + 1) = x_0 - 10y; and x = x_1 - 10 >= 10 - 10 = 0.

Section 3: practice

Five problems on the section's warm-up and tasks; every validity verdict and number was checked by brute force or by running the code.

1. The warm-up

Which of triples A to F (on the warm-up page) are invalid? Give a counterexample for D and for F.

  1. For each, try small values that make the precondition true, especially at its edge (x = 1 for A; x = 0 for F).
  2. D: after x = y;, what is the old x?
  1. A: from x = 1, the line makes x 0. Invalid.
  2. B: x >= 10 takes the else branch, so y = x >= 10. Valid. C: the arithmetic swap leaves x = b and y = a. Valid.
  3. D: x = y loses the old x; then y = x leaves both equal to b. Any a != b, such as a = 1, b = 2, is a counterexample. Invalid.
  4. E: the loop ends with i = n + 1 (for n = 0 it never runs and i = 1). Valid.
  5. F: for integers, x + 1 > 0 means x >= 0, so the else branch sets y = x; from x = 0, y = 0, and y > 0 is false. Invalid.
  6. A, D and F; for F, x = 0.

2. Task 1, checked

For Task 1's first part, does P imply Q: x < 2z + 20? For nextSquare, what does y equal at P, in terms of x?

  1. With integers, y0 > 5 means y0 >= 6 and z0 > 2 means z0 >= 3.
  1. From P: x = 4y0 - 3 and z = z0(y0 - 5) with y0 - 5 >= 1 and z0 >= 3, so 2z + 20 >= 6(y0 - 5) + 20 = 6y0 - 10.
  2. 4y0 - 3 < 6y0 - 10 exactly when 7 < 2y0, true since y0 >= 6. So P implies Q.
  3. nextSquare: y = x^2 + 2x + 1, which is (x + 1)^2.
  4. Yes; y = x^2 + 2x + 1.

3. Task 2, by substitution

Reason backward through each snippet.

  1. Substitute from the bottom: x - 8 for z, then 2x for x, then 4w for y.
  1. {{ z < y }} ← {{ x - 8 < y }} ← {{ 2x - 8 < y }} ← {{ 2x - 8 < 4w }}, that is x < 2w + 4.
  2. P gives x < w + 1, and w + 1 < 2w + 4 whenever w > -3, so P implies it.
  3. Second: {{ a >= c }} ← {{ b + 1 >= c }} ← {{ b + 1 >= c - 1 }} ← {{ 2c + 1 >= c - 1 }}, that is c >= -2.
  4. x < 2w + 4; yes; c >= -2.

4. Task 3: what is w?

From P1 or P2, say what the method returns in one expression, and run it on s = 3, d = 5, len = 6.

  1. In P1, s + d <= len means d <= len - s. In P2, the other way.
  1. P1: w = d and d <= len - s, so w is the smaller. P2: w = len - s and len - s < d, so again the smaller.

Lecture 10 · Abstract data types · Wed Oct 21 · notes: The help queue

The help queue

/**
 * The queue for office hours: the students waiting for help, in
 * the order they joined. A student is named by their NetID, and a
 * student is in the queue at most once.
 */
public interface HelpQueue {
    /** @return the number of students waiting */
    int size();
    /** @modifies this
     *  @effects adds the student at the back of the queue
     *  @throws IllegalArgumentException if the student is already in
     *      the queue, and leaves the queue unchanged */
    void join(String netid);
    /** @modifies this
     *  @effects removes the student at the front of the queue
     *  @return the NetID of the student removed
     *  @throws NoSuchElementException if the queue is empty */
    String next();
    /** @return the students waiting, front first, in a new list */
    List<String> waiting();
}

An interface is a specification with no fields and no method bodies. A class implements it by giving each method a body. Every specification here is written about the queue of students; none can mention a field.

Abstract data type (ADT). A specification for the operations available to access and modify the underlying data, written in terms of the abstract state, how the client should think about the object. Data abstraction means using a type only through its specification, which hides how the data is represented.

Representation. How the objects are implemented: the class's fields and what each holds. The spec never mentions it, so the implementer may change it as long as each method still satisfies its spec.

Abstract invariant. A claim about the abstract state true of every object whenever no method is running. Here: a student is in the queue at most once. The specs keep it true (join throws on a repeat; next only removes), so every client can rely on it with every implementation.

Procedural abstraction drew the line around a method; data abstraction draws it around a whole type.

Quick check: which is HelpQueue's abstract invariant?

Teaching notes
  • "Joining at the back" is a promise of one method (join's spec); "at most once" is a claim about every queue (the abstract invariant). Students blur these.

Lecture 10 · Wed Oct 21 · notes: Three readings of "returns the students waiting"

Three readings of waiting

Suppose waiting's spec said only "returns the students waiting". A client could read it three ways:

  1. A new list, the students waiting at the call; the client may do anything with it. What HelpQueue promises ("in a new list").
  2. The queue's own list, shared: the client sees later joins without calling again, and anything it does to the list happens to the queue.
  3. A list the client may read but must not change or keep, so the implementer may hand back either.

The first two are incomparable: each can break a client written for the other. The third is weaker than both. Under the second, a client could add a NetID already waiting, and the queue would hold that student twice without join ever running: outside code breaking the abstract invariant, as Shortcut did. The copy costs a walk of the queue on each call; in return, only join and next can change the queue.

FastQueue: which method is wrong?

A spec is written about the abstract state; a body about the concrete state, its fields. Between them is a gap. Wednesday's half sheet asked how to make join's check faster: keep the students twice, in a list for the order and in a HashSet for a check that takes the same time however long the queue. private List<String> queue;     // line 14: the students waiting, front first

//     the NetIDs in queue.
// AF(this) = the help queue of the students in queue, front first.
…
public void join(String netid) {          // lines 50–58
    checkRep();
    if (members.contains(netid)) { throw new IllegalArgumentException(netid + " is in the queue"); }
    queue.add(netid);                     // line 55

Lecture 11 · Fri Oct 23 · notes: Representation invariants, Checking the representation invariant with checkRep

Representation invariants and checkRep

Representation invariant (RI). A claim about a class's fields that is true of every object whenever no method of the class is running. The constructor makes it true; every method may assume it when called and must make it true again before it returns. Document it as // RI: ... beside the fields.

The RI is not the abstract invariant: that is about the abstract state, for the client; the RI is about one class's fields, for the implementer. Like a loop invariant, it may be false in the middle: FastQueue's is false between lines 65 and 66.

private void checkRep() {
    if (!members.equals(new HashSet<String>(queue))) {
        throw new IllegalStateException("members is not the queue");    // line 38
    }
    if (members.size() != queue.size()) {
        throw new IllegalStateException("someone is in queue twice");   // line 41
    }
}

checkRep checks the RI in code and throws if any clause is false; it is private and changes no field. It is Lecture 6's defensive programming, turned on the class's own fields. With the checks on, the forgetful next fails on its own call, line 67, with members is not the queue: the report names the method that is wrong. Try "FastQueue without line 66, checkRep on" below.

Where to call it (the course's code quality guide): at the end of each constructor; at the beginning and end of every mutator; at the beginning of every non-mutator. Never at the start of a constructor (the fields are still null), and not in private helpers, which may run while the RI is false. Each call walks the whole queue, so in production keep only the fast checks.

Lecture 11 · Fri Oct 23 · notes: A faster next, Abstraction functions

FasterQueue and the abstraction function

queue.remove(0) shifts every later element left, so next takes longer the longer the queue. Removing the last element moves nothing. So keep two lists, each used only at its end: join adds at the end of the inbox; next removes from the end of the outbox, which holds the front of the queue last; when the outbox runs dry, next refills it with the inbox reversed. The set stays, for join's check.

// RI: no NetID is in inbox or outbox twice, or in both, and
//     members holds exactly the NetIDs in inbox and outbox.
// AF(this) = the help queue of the students in outbox, last to
//     first, then the students in inbox, first to last.

Abstraction function (AF). Maps each value of the fields that the RI allows to the abstract state it stands for. A mathematical function, not code; document it as // AF(this) = .... It goes one way: several values of the fields can stand for one queue, so no function goes back.

Join ada, bob and eve, then call next: inbox = [], outbox = [eve, bob], and by the AF the queue is bob, eve. Another route gives inbox = [eve], outbox = [bob]: the same queue. Fields like inbox = [bob], outbox = [bob] break the RI and stand for nothing. Every RI must guarantee the abstract invariant: RI(this) implies AI(AF(this)).

The draft waiting copies the outbox as stored. Wednesday's five tests all pass on it (none has two students in the outbox when it calls waiting); FasterQueueTest's three-student test fails, expected: <[bob, eve]> but was: <[eve, bob]>. The AF says what it got wrong: it read the outbox in the wrong order.

Quick check: inbox = [eve], outbox = [bob]. By the AF, who is waiting, front first?

Lecture 11 · Fri Oct 23 · notes: What correct means for an ADT method

What correct means for an ADT method

Rule. A method with precondition P and postcondition Q, written about the abstract state, is correct exactly when the triple

{{ RI and P(AF(this)) }}
the method's body
{{ RI and Q(AF(this_0), AF(this)) }}

is valid and every call that begins with the precondition true terminates. this_0 is the object as it was at the call. The body may assume the invariant and the precondition, and must leave the invariant true and the postcondition true of what the fields now stand for.

  1. size on FasterQueue. {{ RI }}; checkRep changes nothing; by the RI, the lists hold inbox.size() + outbox.size() NetIDs, each once, and members holds exactly those; by the AF, that is the number of students in AF(this). No field changes, so AF(this) is AF(this_0) and the RI still holds. Correct.
  2. next, the refill case. The outbox is empty, so AF(this_0) is the inbox first to last. The refill puts the inbox reversed in the outbox and empties the inbox: read last to first, the same queue. Line 80 removes the outbox's last, the front; line 81 removes it from the set. RI true; AF(this) is AF(this_0) without its front, which is returned.
  3. The forgetful next. After line 65 removes the front, line 66 is blank, so members holds a NetID not in queue: the RI is false at the end, and the argument stops in next, at the missing line. Reasoning finds the mistake in the method that made it.

Quick check: may the RI be false between two lines in the middle of a correct method?

Copy in, copy out

Monday's question: why does Book's messages return a copy? Make it return messages;, and the test's copy.add posts a message without calling add. The list in the field is Book's representation; handing it out lets outside code change it.

A class can also take a list in. FastQueue(List<String> netids) keeps new ArrayList<String>(netids) (line 31), not the client's list. A draft with queue = netids; fails aQueueMadeFromAListIsItsOwn with members is not the queue: the test's netids.add("eve") changed the field through the client's name, and no method of FastQueue ran. Two names for one object is aliasing. A second draft, waiting returning queue, fails waitingIsACopy the same way.

Why checkRep at the start of a method (the half sheet's second question)? Between two calls, code outside the class may have changed the fields through an alias, after the last check ran. The start check catches it on the next call.

Representation exposure. A reference, held by code outside a class, to a changeable object among its fields. Through it, the RI and every spec can be broken by code the class does not control. Prevent it: copy in a changeable object a client passes that becomes part of the fields, and copy out a changeable field a method returns. A String field exposes nothing (strings cannot change), nor an int (a copy of the number).

A class is correct when every method is correct by the rule and the class has no representation exposure.

Week 4 cheat sheet

Server

Waits for requests, answers each with a response. Frontend (browser) / backend (server). Event-driven: a framework (HttpServer) owns the loop and calls your handler. Library: you call it.

HTTP is text

Request: METHOD path HTTP/1.1, headers, blank line, body. Response: HTTP/1.1 200 OK, headers (Content-length counts bytes), blank line, body (HTML). 400s: the request was a mistake.

GET and POST

GET asks and must not change state (safe; sent on their own by browsers and crawlers); POST may change state. Form body: name=Ada&message=hello+world, %XX for other bytes.

Every request

Inputs are whatever a user can send. Missing fields → null; bad % → no response; a user's text joined into HTML → cross-site scripting. Escape & first, then < >.

Reasoning (Section 3)

Forward: subscripts or invertible operations (integer division does not invert). Backward: substitute. Don't drop useful facts.

ADT

A spec of operations in terms of the abstract state. Representation: the fields, private. Abstract invariant: about the abstract state, kept by the specs.

Tests

Spec-based tests use only the interface (abstract test class + subclass per implementation). Implementation-based tests check choices the spec left open.

RI and checkRep
