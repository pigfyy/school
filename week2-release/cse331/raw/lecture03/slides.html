Batch programs

A batch program reads its input, computes, writes its output, and exits.
  • Lecture 1's Sum and this one are both batch programs
  • A web browser is not: it keeps running until told to stop
    • A later lecture takes up programs of that kind

Input

  • Command-line arguments: the words after java Sum
    • Input too: the user chooses them, and they change what Sum does
  • Options: arguments that start with a dash, like -a
  • A file: named by any other argument
  • Standard input: otherwise; by default, the keyboard
    • Lines 89 and 90 choose between them

A command line, word by word

$ java Sum -a --precision=2 nums.txt

java Sum: starts Sum's main

-a: an option, since it starts with a dash

--precision=2: an option with a value

nums.txt: any other argument is a file to read

main gets args: "-a", "--precision=2", "nums.txt"

Output

  • Standard output: the results (lines 78 to 83)
  • Standard error: the messages (line 96, in fail)
  • Exit status: a number that says whether the run succeeded
    • 0 means success; anything else, failure
    • fail exits with status 1 (line 97)
  • In a terminal: results and messages look the same
    • And the exit status does not show at all

Where the output goes

Why keep them apart?

> sends standard output to a file.

$ java Sum nums.txt > total.txt
$ echo $?
0

Nothing on the terminal, and 12 in total.txt

Exit status 0: the run succeeded

The last exit status: echo $? on macOS and Linux, $LASTEXITCODE in Windows PowerShell.

When a run fails

$ java Sum bad.txt > total.txt
Sum: not an integer: x
$ echo $?
1

The message skips the file, and total.txt is empty

Exit status 1: the run failed

bad.txt contains 3 x.

Why standard error exists

  • At first, every message went to standard output
    • Pipes then sent the messages into the next program
    • Typesetting runs printed only cannot open file foobar
  • Soon after, Dennis Ritchie added standard error
  • Then each message had to name its program
    • With several programs in a pipeline, who said it?

Stephen Johnson, 2013; M. D. McIlroy, 1987.

What a user sees

  • Three parts: standard output, standard error, exit status
    • Sum's specification has to say what each is, on every run
  • A person at the terminal reads the first two
  • A script: a program that runs other programs
    • It can read all three
    • Like a client in Lecture 2: it relies on Sum's promises
    • Unlike a method's client: it owes Sum nothing

A maxim from 1978

Expect the output of every program to become the input to another, as yet unknown, program. Don't clutter output with extraneous information.
  • Clutter: a message among the results
    • Standard error keeps it out
  • As yet unknown: Sum's author cannot know its scripts
    • What scripts rely on has to be in the specification

M. D. McIlroy, E. N. Pinson, and B. A. Tague, 1978; often credited to McIlroy alone.

The average of no numbers

  • No single right answer: refuse, as Sum does, or print 0
  • One answer is always wrong: ignore the problem
    • As the copy without lines 73 to 75 does
  • USS Yorktown: a crew member entered a zero
    • A program divided by it, and the cruiser stopped for hours
  • Sum's manual should say which answer Sum gives

Brian Kernighan and Rob Pike, 1999.

Checks at the edge

  • Each check stands between the user and the computation
    • The user owes Sum nothing
    • The computation should get only what it can handle
  • Split main into methods with specifications, as in Lecture 2
    • The checks stay at the edge, in main
    • A method inside may then have a precondition
